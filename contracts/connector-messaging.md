# Messaging and SMS connector

Version: 0.1.0
Status: draft (ADR-0078 Proposed)
Owner: eldon

How a tenant's business talks to its own customers on WhatsApp, Instagram and Facebook Messenger (Meta's business platform) and SMS, through one conversation model. A specialisation of the [connector interface](connector-interface.md) (tier 1 for Meta APIs, tier 4 trust rules for inbound text) that adds a send path. Objects: [connector-messaging.schema.json](connector-messaging.schema.json) (`kind` picks one of six); examples `examples/connector-messaging-*.json`, negative examples `examples/invalid/connector-messaging-*.json`. Decision: [ADR-0078](../docs/decisions/ADR-0078-messaging-and-sms-connector.md).

**Not the chat channel.** [OPR-015](../docs/product/opr-015-messaging-channel.md) lets a tenant's *staff* reach the Seshna chat over WhatsApp through a verified `channel_binding`. This contract is the *business-to-customer* inbox. A customer contact is never a principal: it gets no role, runs no tool and never reaches the chat runner. A number bound under OPR-015 is refused as a contact on the same channel account (MSG-010).

## 1. Channel capability declaration (`kind: capability`)
Each connector instance declares, per tenant and channel account: `connectorId` (`msg.meta_whatsapp`, `msg.meta_instagram`, `msg.meta_messenger`, `msg.sms`), `serviceWindowHours` (24 for the three Meta channels, null for SMS, which has none), `templatesRequiredOutsideWindow`, `inboundContent` (v1: `["text"]` only; media is refused with a fixed reply, as in OPR-015 section 6.3), `maxTextLength`, `readReceipts`, `credentialRef` (its tenant segment must equal `tenantId`, MSG-014), `sandbox`, `siteClass` (`sandbox` or `production`; a sandbox capability in production is refused) and `webhook` (`signedTimestamp`, `replayWindowSeconds`, `payloadTimestamp`, `maxEventAgeHours`, `dedupRetentionHours`, `dedupStore`; section 8). The SMS adapter is provider-agnostic: one port, providers behind it, chosen per market by a later row.

## 2. Conversation and inbound message
- **Conversation** (`kind: conversation`): one thread per tenant, channel account and contact. `windowOpenUntil` is computed by platform code from the provider timestamp in the signed body of the latest inbound message (`providerSentAt`, capped at our `webhook.receivedAt`) plus `serviceWindowHours`, never from our receive time alone and never from payload text; `lastInboundAt` is that `providerSentAt`. A replayed old body therefore cannot reopen a closed window (#394 re-review M7). A message with no `providerSentAt` never opens or extends a window. `state` is `open`, `closed` or `blocked` (contact blocked the business or was blocked). `windowOpenUntil` is always null on SMS.
- **Inbound message** (`kind: inbound_message`): `trust` is always `"untrusted"` (L3, [prompt-injection-defence](../docs/security/prompt-injection-defence.md) 2.1). Text is sanitised before labelling (3.3: control and bidi-override characters stripped, length capped) and flagged (`instruction_like`, `link`, `opt_out_keyword`, ...); `flags` is always present, empty when the scan found nothing, so "clean" and "never scanned" differ. `contentHash` is the sha256 of the sanitised text, computed by platform code. `retentionClass` is `transcript` (section 11). `providerSentAt` is the provider's message time read from the signed body and derived from `providerTimestampRaw` (the raw string, exactly 10 or 13 digits, section 8; both required on Meta channels; null only for an SMS provider whose payload has none). A thread holding any inbound message is tainted for every model run over it (2.4). Links are never fetched. `webhook.signatureVerified` is always true: an unverified call never becomes an object.

## 3. Send request (`kind: send_request`)
| Mode | When | Needs |
|---|---|---|
| `session_reply` | Inside an open service window (Meta channels only; never SMS) | `conversationId`, `text` (or, for `auto_reply`, `approvedTextId`); no template or consent ref (the contact wrote first). A null `windowOpenUntil` refuses it (MSG-003): use a template |
| `template` | Outside the window, every SMS, every business-initiated message | `template` (approved id, `utility` or `marketing`, `ar` or `en`, capped params) and `consentRef` to a granted consent of a purpose that covers the category |

Every send also carries `country` (the consent key, section 6), `tainted`, `sandbox` and `payloadHash` (sha256 of the canonical send without `payloadHash`, `confirmationId`, `approvalId` and `sentBy`, so it covers the content that was approved and stays the same when the confirming user is recorded; recomputed at confirmation and execution, a mismatch voids both, action-policy section 5).

**Who sent it.** `origin` is `human`, `agent_draft` or `auto_reply`:
- `human`: `sentBy` (the user) and `confirmationId` (the gesture over the rendering of `payloadHash`) are required.
- `agent_draft`: `draftedBy` (agent id) plus `sentBy` (the human who confirmed) and `confirmationId`. An agent only drafts; the draft sits in the inbox and sends only on that gesture. JSON Schema cannot compare two values, so `sentBy` differing from `draftedBy` is made structural instead: `sentBy` must be a user id (`usr_`) and `draftedBy` an agent id (`agt_`), so they can never be equal; the validator also checks that `sentBy` resolves to a human user of the tenant.
- `auto_reply`: none of the three; it carries `autoReplyPolicyRef`, `approvedTextId`, `classifiedIntent`, `confidence` and `confidenceThreshold` instead (section 5).

These sit beside the Tool API section 8 envelope (`user_id`, `agent_id`, `arguments_hash`, `approval_id`), which must agree with them. Authentication templates are not used (OPR-015 section 4.5).

**Tainted threads (prompt-injection-defence 4.5).** Platform code sets `tainted`, never the caller: it is true for any send to a contact whose conversation on that channel account holds inbound content, whatever the mode or template category. The schema forces `tainted: true` on every send that carries a `conversationId` (so on every session reply); the validator checks the rest. A tainted send is a saved draft that executes only on a human's confirmation gesture over the canonical payload; that is why `human` and `agent_draft` both need `confirmationId`. `auto_reply` is the one path with no gesture, so it stays off until a SEC row allows it (section 5).

**Risk classes: interim, SEC rows pending (Q-720).** Action-policy section 4 defines R1 as a change with no external effect, and every send reaches a person outside the tenant, so no send is R1. R3 is the only class whose meaning includes an external send, so until SEC accepts the AP-MSG rows (proposed in [action-policy-table](../docs/security/action-policy-table.md) section 12) every human or agent-draft send is `riskClass: R3` (fail closed; the row may be stricter, never looser):
- `message.send_reply` and utility `message.send_template` to one contact (AP-MSG-01, AP-MSG-02 proposed): R3 interim, recipient selected by `contactRef` only (prompt-injection-defence 5.1).
- `message.send_template` with category `marketing`, any batch or campaign (AP-MSG-03 proposed): R3, `origin: human`, `approvalId` a required ref (never null), step-up per the row; never agent-creatable.
- `auto_reply`: **no class until the SEC row** (`riskClass: null`, schema-forced). R3 means a human submits, and auto-reply is the one send with no gesture, so R3 does not fit it. A send with a null class is refused, so auto-reply cannot run until AP-MSG-04 (enabling auto-reply, proposed) and its per-send rule are accepted; `session_reply` on a Meta channel only; see section 5.

**How `riskClass` migrates.** Today it holds `R3` or `null`. When SEC accepts the AP-MSG rows, `riskClass` becomes a row reference (`AP-MSG-01` and so on, pattern `^AP-[A-Z]+-\d{2}$`) and the validator reads approver, step-up and expiry from the row. That is a change to accepted values, so it ships as a contract version bump at that time (0.2.0; while the major is 0 a minor may break, contracts README rule 1, said in the superseding ADR), with the AP-MSG rows accepted first. No bump is needed now: this contract is unreleased at 0.1.0 and the null value for auto-reply is part of 0.1.0.

All sends are writes: `idempotencyKey` (ULID) is required; same key with other arguments is `idempotency_conflict` (Tool API section 6).

## 4. Delivery status (`kind: delivery_status`)
`costMicroUsd` (integer, null until the provider reports it) feeds `meter.message_sent`. Statuses: `accepted` (provider took the request; not delivery), `sent`, `delivered`, `read`, `failed` (with `errorCode`), `expired` (no delivered status before the provider's time-to-live). Status order is not guaranteed; consumers keep the highest seen state per message and never go back from `delivered` to `sent`.

## 5. Auto-reply (per tenant, off by default)
1. A tenant admin opts in per channel account and lists intents from the platform's fixed list: `greeting_ack`, `opening_hours`, `location`, `handoff_ack`. No other intent, no figures, no records, no links except the tenant's own allowlisted domain.
2. The model only classifies the intent. The send carries no `text`: it names `autoReplyPolicyRef` (the tenant's opt-in for that channel account) and `approvedTextId` (the tenant-approved fixed text, L1 configuration, for that intent), which platform code resolves and sends byte for byte. It records `classifiedIntent`, `confidence` and the `confidenceThreshold` applied (schema floor 0.8, placeholder with Q-156). Below the threshold, or on any flag, the message goes to a human as unanswered.
3. Meta channels only (SMS has no service window), only inside the service window, at most one auto-reply per conversation per intent per window, and per-tenant daily caps (placeholders, Q-156). A cap or an error stops auto-replies and alerts; it never falls back to a model-written send.
4. Cannot be enabled until the action-policy table has a row for it (ADR-0078 decision 4): its sends carry `riskClass: null` and are refused until AP-MSG-04 is accepted and a later contract version names the row (section 3).

## 6. Consent records (`kind: consent_record`)
One record per contact, channel, country and purpose (`utility`, `marketing`), with `capturedAt`, `method`, `textVersion` and `language` of the wording shown, and `evidenceHash` of the capture (form submission, signed paper scan reference, keyword message). Records are keyed by tenant, `contactRef`, `channel`, `country` and `purpose`, and are append-only: a revoke or a re-grant is a **new record** with a new `consentId` and `supersedes` set to the record it replaces (a revoke always supersedes one).
- **Order is `recordedAt`, set by the platform** when it appends the record, strictly later than the key's latest record. `capturedAt` is tenant-supplied evidence of when consent was given and never orders records, so backdating or postdating it changes nothing.
- **`supersedes` must name the latest record for the key** (by `recordedAt`) at the moment of appending, and may be null only for the key's first record. Anything else is refused and not appended; in particular a tenant user's grant with `supersedes: null` after a STOP is refused (#394 re-review M3; validator fixtures in `contracts/tests/test_messaging_contracts.py`). A grant whose superseded record is a revoke must carry the platform-copied `afterRevocation` of that revoke.

The latest record by `recordedAt` for the key decides; a send's `consentRef` must be that record, granted, for the send's `country` (MSG-005, MSG-006). `capturedBy` says who captured it (`contact`, `tenant_user`, `provider`).
- STOP and its Arabic equivalents in an inbound message, or a provider block, revoke at once (OPR-015 section 9), as `revokedBy` `contact_keyword`, `contact_request` or `provider_block`.
- **Re-grant after a contact's revoke:** only the contact's own opt-in lifts it (`capturedBy: contact`, method `web_form`, `chat_keyword` or `sms_keyword`), never a tenant user, an import or a spreadsheet. Platform code copies the superseded revoke into `afterRevocation`; the new `capturedAt` must be after its `revokedAt`, with new evidence.
- A tenant user may record consent captured elsewhere when no contact-initiated revoke stands; the platform never infers consent from a conversation. Consent records are kept while the contact exists plus the audit minimum.

## 7. Tenancy binding and credentials
- A `channel_account` (WhatsApp phone number id, Page id, Instagram account id, SMS sender id) is bound to exactly one tenant by the control plane. A second tenant claiming it is refused (MSG-011).
- Inbound webhooks resolve the tenant only from the verified recipient account id. Unknown account: drop, alert, no object (MSG-002).
- Provider tokens and app secrets live in the secret store per tenant ([secrets-management](../docs/security/secrets-management.md)); objects carry only `credentialRef`. Never in the Blueprint, events, logs or prompts.

## 8. Webhooks
1. **Verified:** Meta calls carry `X-Hub-Signature-256` (a SHA-256 signature of the payload keyed with the app secret; that it is HMAC is UNVERIFIED from the page read, see ADR-0078); the adapter compares in constant time before parsing. SMS providers are accepted only with their documented signature or a per-tenant secret path plus an IP allowlist. Fail closed: 401, nothing processed (MSG-001).
2. **Idempotent:** WhatsApp retries a failed delivery "with decreasing frequency until the request succeeds, for up to 7 days", and every subscribed app is retried, so duplicates happen ([WhatsApp webhooks, "Webhook delivery failure"](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/set-up-webhooks), accessed 2026-11-27; the generic Graph API page says 36 hours, [getting started, "Frequency"](https://developers.facebook.com/docs/graph-api/webhooks/getting-started), accessed 2026-11-27; the WhatsApp page governs here, which one Meta applies in practice is UNVERIFIED, Q-721). `dedupKey` is the hash of provider, account and `providerEventId`; a repeat is acknowledged and dropped. Seen keys are kept for `webhook.dedupRetentionHours` (schema minimum 192 = 7 days plus a 24 h margin; default 192; and never below `maxEventAgeHours`, a validator rule) in a **durable** store (`dedupStore: durable`), never an in-memory or evictable cache; if the store is lost, inbound processing stops (fail closed) until it is restored.
3. **Replay-protected by dedup plus payload age for Meta:** Meta signs the payload with `X-Hub-Signature-256` (`sha256=` prefix, keyed by the App Secret, over the raw body) and the docs mention no signed timestamp or nonce, which is read as none ([webhooks getting started, "Validating Payloads"](https://developers.facebook.com/docs/graph-api/webhooks/getting-started), accessed 2026-11-27; the WhatsApp page does not cover signatures; that it is HMAC-SHA256 over the raw body is the usual reading but UNVERIFIED as wording). So Meta capabilities have `signedTimestamp: false` and `replayWindowSeconds: null`. The body carries a per-message `timestamp` as a **string** (`messages[].timestamp`, `statuses[].timestamp`; [WhatsApp webhook components, "Payload structures"](https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/components), accessed 2026-11-27), so Meta capabilities have `payloadTimestamp: true`. The adapter parses it as a string, keeps it as `providerTimestampRaw`, and **fails closed unless it is exactly 10 or 13 digits** (dropped, alerted, audited); that the digits are unix seconds is UNVERIFIED (the examples are 10-digit values), and `providerSentAt` is derived only after that check. `maxEventAgeHours` ranges 37 to 192, default 192 for WhatsApp, so a legitimate late retry inside the 7-day period is not dropped, and `dedupRetentionHours` must be at least `maxEventAgeHours` (a validator rule, as JSON Schema cannot compare two values). A message whose `providerSentAt` is older than `maxEventAgeHours`, or more than 300 seconds in the future, is dropped, alerted and audited. Every replay is then either inside dedup retention or too old. An opt-out keyword is still processed as a revoke, never dropped for age (a replayed STOP only fails safe), never opens a window, and an old STOP cannot end a later grant (section 6). Only a provider that signs a timestamp header gets `replayWindowSeconds` (60 to 3600 seconds, placeholder 600, Q-698).
4. **Unknown types fail closed:** a verified call whose `eventType` is not in the schema list (v1: `message`; statuses map to `delivery_status`) is acknowledged, dropped, alerted and audited, and becomes no object (MSG-013).

## 10. Audit and events
Every inbound and send writes an audit record: the Tool API section 8 fields plus these, each read from an object field. Direction is the `kind` (`inbound_message` or `send_request`); channel is `channel`; template id and language are `template.templateId` and `template.language`; consent ref is `consentRef` (with `country`); taint is `tainted` (always true inbound); who sent is `sentBy`, `draftedBy`, `confirmationId` and `payloadHash`, or the auto-reply fields; cost is `delivery_status.costMicroUsd`. Content bodies never enter events: only `contentHash`. Contract 4 types added in [events.md](events.md): `message.received`, `message.send_requested`, `message.status_changed`, `consent.recorded`, `consent.revoked`, `meter.message_sent`.

## 11. Data minimisation and retention
Contact phone numbers and handles are stored sealed with a keyed hash for lookup (as OPR-015 section 5.1); objects carry `contactRef`. Message bodies (`retentionClass: transcript` on every inbound message) follow the transcript class in [data-retention](../docs/security/data-retention.md), with the period set per market by the country pack; until counsel sets it the shortest placeholder applies. Meta and the SMS provider are sub-processors on the tenant's DPA; cross-border transfer is per market and UNVERIFIED (LEG-003).

## 12. Sandbox rules
`sandbox: true` connectors use provider test numbers and accounts, synthetic contacts and data only (RULES 46). They send only to a per-tenant test allowlist (MSG-012): a send with `sandbox: true` must name `testAllowlistRef`, and the validator refuses a `contactRef` not on it; a production send names none. They never spend on live templates, and never run in a production site class (the schema refuses `siteClass: production` with `sandbox: true`). Customer Meta business verification, display names, template approvals and SMS sender registrations are go-live items, not build items (ADR-0076 decision 11).
