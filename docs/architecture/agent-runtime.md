# Agent runtime

Status: draft. Before this can be accepted, an ADR on agent authority is required (taint leads to approval, R3 and R4 are recorded and never run, refusal and needs-approval semantics, ADR-0043 call-time enforcement, the propose pre-flight). This doc does not number it.
Owner: eldon

Plan row OPR-001. Code: `services/operate/runtime/`. It is the agent-runtime port that `services/operate/agui` expects ([ADR-0044](../decisions/ADR-0044-ag-ui-agent-to-screen-transport.md)). Model-agnostic, no model calls and no network inside it. Security basis: [prompt-injection-defence](../security/prompt-injection-defence.md), [ADR-0027](../decisions/ADR-0027-human-floor-action-policy-and-agent-authority.md), [ADR-0043](../decisions/ADR-0043-department-assistants.md), [Tool API](../../contracts/tool-api.md).

## Turn state machine
Plan (build request) -> call model -> parse tool calls -> classify each call -> execute through the Tool API port only -> observe -> repeat. It ends on an answer (no tool calls), an interrupt, a cap, a cancel or a failure. Ids and the clock are injected, so one model script gives one trace.

## Ports (all injected)
`ModelPort.complete(request) -> ModelReply`; `ToolPort.call(request) -> ToolResponse` (contract sections 3 and 7) with `supports_propose`; `TraceStore`; `EventSink`; `Ids`; `Clock`; `CancelToken`. `GatewayModelPort` wraps `MeteredGatewayRouter` (tier routing, budget precheck, metering stay in the gateway; live providers are PLT-009). Callers: tenant, user, roles and session come from the verified principal; the model supplies only a tool name and arguments.

Tenant binding: a `GatewayModelPort` holds one `GatewayContext`, so it is built per request. `gateway_model_for(router)` gives the `model_for(principal, run_id)` factory the AG-UI adapter takes; the context comes from the principal and the correlation id is the run id. A port exposes `tenant_id`; the loop fails a run closed (`internal_error`) when it differs from the caller's tenant, or when the allow-list roles differ from the caller's. Every reply is checked at the boundary (a `ModelReply`, non-negative integer usage).

Session taint: `stream(..., taint=TaintState)` takes the session's taint and `RunResult.taint_state` returns it. The chat service (OPR-010) must store it with the session and pass it to the next run, so tool data summarised in earlier turns cannot come back untainted. Domain error params from a tool also taint the run.

## Controls
| Control | Rule |
|---|---|
| Allow-list | Per run, from the principal's roles and the optional assistant config: role overlap, `agent_creatable`, at most R2, never `approval.decide` or `blueprint.propose_change`; an assistant needs `confirm: true` for each R2 tool. No roles or an unreadable tool set gives an empty list; no roles fails the run. |
| Assistants (ADR-0043, at call time) | `authority.py`, whatever the config says: approve, reject, submit, cancel, amend and delete verbs, protected tools and `blueprint`/`role`/`grant` domains are refused; on ledger or stock entities only get, list, create, update and export. A transition must be on the assistant's own `transitions` list for that tool (none listed: none allowed) and is never an approve, reject, cancel or reversal move, never a move with its own approval rule. The Blueprint validator checks the same at publish time. |
| Risk | R0 and untainted R1 run. R2, and R1 once the run is tainted, are sent to the Tool API with `propose=true` (a pending approval) and the loop stops at an interrupt. R3 and R4 never run: recorded as `needs_approval`; when they reach the refusal cap the run stops with the policy outcome `needs_approval`, not a permission error. A transition tool takes the risk, agent flag and `allowed_roles` of the chosen transition. |
| Propose pre-flight | The loop sends an R2 or tainted R1 call only to a port with `supports_propose = True`; otherwise nothing is dispatched and the run stops with `propose_unavailable`. A propose call that comes back `ok` still fails the run (tripwire). The real control must sit in the Tool API: it must refuse to execute any agent-class R2 call and any tainted R1 call without an approval, whatever flag the runtime sends. That is a dependency of OPR-004 and a contract question (open questions), not settled here. |
| Writes | Each dispatch carries a deterministic idempotency key from (run, step, tool, canonical args), so a replayed step is de-duplicated by the Tool API. An identical write (R1 or above) is dispatched once per run; identical reads up to `max_repeat_calls`. The repeat guard is bypassed by changing an argument; only the step and tool-call caps bound that. |
| Untrusted data | Tool results become `DataItem`s (trust L3, source, hash, sanitise flags) in `ModelRequest.data`, never in instructions, the user turn or observations. Flags come from the discovery sanitise and detect functions; `instruction_like` also writes `agent.output_flagged`. Every tool result taints the run (Q-231). |
| Caps | Steps, tool calls (an assistant's `max_tool_calls`, including 0), tokens, cost, wall clock (injected clock), repeat calls, refusals; plus the gateway precheck inside `GatewayModelPort`. A cap stops the run with `budget_exceeded` and `agent.budget_exceeded` with a budget kind. The cost cap projects the next call (the dearest call so far, or `est_call_cost_micro_usd`); the gateway precheck sizes the input estimate from the serialised request. Text from a reply that crosses a cap is still streamed (partial spend). |
| Errors | Tool errors keep only a Tool API class code or an ADR-0036 catalog id with typed params; free text, exception text and stack traces never reach the model, the trace or the wire (`errors.py`). Any exception in a run, from a port or not, goes through the firewall and ends with a run span and `agent.run_failed` (`internal_error`). |
| Engine names | Tool results: exact internal identifiers on word boundaries (the engine names, `DocType`, `tab` plus a capital, a Python traceback header, `site_config.json`) are replaced span by span; ordinary words such as table, SQL or report.py pass. The Tool API output schema is the main guard. |
| Cancel | `CancelToken` is checked before each step and each call; no further tool call starts. |

## Trace and events
One `Span` per model call, per tool call (tool, risk class, outcome, redacted args, args hash, tokens, cost, approval and audit ids) and one for the run. Redaction masks sensitive key names (including national id, iqama, passport, card, OTP, date of birth) and sensitive values under any key (e-mail, IBAN, phone-like and long digit runs); `args_hash` is an HMAC with an injected per-tenant salt, and no salt means no hash. Audit events and spans carry a tool name only when it is in the tenant's tool set, else `unknown`. Spans go to a tenant-scoped `TraceStore` (in-memory here). Events through `EventSink`: `agent.run_started`, `agent.run_completed`, `agent.run_failed`, `agent.tool_proposed`, `agent.budget_exceeded`, `agent.output_flagged`. `tool.called` is written by the Tool API and `meter.ai_usage` by the gateway, not here. Under agui the endpoint already writes `agent.run_*`, so the adapter sets `emit_run_events=False`, and yields `RuntimeUsage` only when the usage was not already metered by the gateway.

## agui adapter
`AguiRuntimeAdapter.run(ctx)` yields text, tool call and `approval.pending` events and `RuntimeUsage`; tool results are not streamed. It takes `model_for(principal, run_id)` (the shared `model=` remains for unbound fakes), `hash_salt_for(tenant)`, `taint_for(ctx)` and `on_taint(ctx, state)`. Only the no-roles case raises the endpoint's auth failure; `internal_error` raises a plain error (generic wire error); `budget_exceeded`, `needs_approval` and `propose_unavailable` yield their `errors.*` key as text (Q-233). It appends this run's approval ids to `ctx.run_approvals` and sets `reports_approvals`, so the endpoint interrupts only on approvals this run created.
