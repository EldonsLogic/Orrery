# Simulator (replay a month)

Status: draft
Owner: eldon

BPL-018. Replays one month of the owner's own records on the compiled tenant and compares what the tenant reports with totals computed from the source. Optional for G1 ([ADR-0026](../decisions/ADR-0026-phased-delivery-and-market-pack-track.md)); planned for G2 ([GATES](../GATES.md)). Code: [services/blueprint/simulator/](../../services/blueprint/simulator/__init__.py). The report is rendered by BPL-019 and measured by QA-011.

## Pipeline
1. **Input model** (`model.py`). The `accepted` rows of a pre-validation report (DSC-019, fed by DSC-011 and DSC-014) are grouped by (type, number) into source records: `stock_in`, `purchase_invoice`, `payment_out`, `stock_out`, `sales_invoice`, `payment_in`, `payroll_run`. Each record keeps its provenance (connector, sheet, row, row SHA-256) and the intake's finding codes. Amounts are exact decimals: a float, an unparseable amount or date, or an unknown currency drops the record (SIM-114).
2. **Source checks** (`anomalies.py`). Flags, never corrections: date outside the month (excluded), missing or unknown tax code, unmapped account, negative stock, duplicate document number (excluded), possible duplicate, payment not allocated to an invoice of the month, document-total rounding.
3. **Replay planner** (`plan.py`). Records in order of posting date, then a fixed same-day kind order (receipts before issues, bills before payments). Each record becomes a `create` call and, when the mapping says so, a posting call (`submit` or a named transition). Calls are Tool API calls from the tenant's generated tool set ([contract 3](../../contracts/tool-api.md)), never raw writes. Risk comes from the tool set: R0 to R2 run, R3 and R4 are recorded as "would need approval" and never sent; an unknown risk is R4. The caller is the replay user with the tenant's own roles; a tool that none of those roles may call is refused at planning (the gateway re-checks). Arguments are checked against the tool's input schema before anything is sent. Idempotency keys are UUIDv5 of (tenant, period, run epoch, source record, stage): a rerun sends the same keys and converges; a changed record under the same key gets `idempotency_conflict` and stops the run. Payments reference the invoice by the engine record id the create call returned (`$ref` resolved by the runner), never by the source number; with no earlier invoice in the plan no reference is sent (SIM-113, SIM-127). A rerun after an abort uses the same `run_epoch` and `on_existing="resume"`. A fresh `run_epoch` re-creates every document, so it needs a reset tenant (Q-242): by default (`on_existing="refuse"`) the runner reads the totals first and aborts with SIM-129 if the tenant already reports data; `allow` runs anyway and flags SIM-130.
4. **Runner and port** (`runner.py`). `EnginePort` has two operations: `execute(ToolCall)` returning a Tool API response, and `report_totals(tenant, caller, period)` returning `{metric: {currency: decimal string}}`. Fail closed: an exception, an `error` response or a malformed response stops the run, later steps are `not_run`, totals are not read and nothing is compared (`aborted`). A port exception is recorded as `in_doubt` (ADR-0028): the call may have been applied, the document is listed in the report's `inDoubt`, the run stops (SIM-128) and a rerun with the same keys converges. A call parked by a Blueprint approval rule (`pending_approval`) is recorded, not executed. There is no durable journal of sent steps yet (Q-245).
5. **Comparison** (`compare.py`). Expected totals from source: sales and purchases (net), VAT output and input, receivable and payable aging buckets at month end, stock value (moving average per item and warehouse), payroll gross, deductions and net. Per-document rounding half up at the currency exponent, integers in minor units. Arithmetic runs in an exact Decimal context (80 digits, inexact and invalid operations raise; amounts are capped at 18 integer and 9 decimal digits); stock uses exact fractions, so there is no dust (an oversell, negative quantity or negative price makes that item `negative_stock`: SIM-104, metric not compared). Aging: age is period end minus due date (or posting date); age 0 or less is `not_due`, 1 to 30 `0_30`, then `31_60`, `61_90`, `over_90` (`aging.py`, one function shared with the simulated port). Tolerance per metric (or family, or `default`; first rule present wins, an empty rule is an error, values are capped): `abs_minor + per_document_minor x documents + per_line_minor x lines`, zero when no rule is given. Tax and net are likely rounded per line by the engine, so use `per_line_minor`. A reported metric or currency outside the known sets is dropped with one SIM-122 anomaly. A document total differing by more than one minor unit per line is SIM-131, not a rounding note (SIM-102). A metric that needs a held R3 or R4 step is `blocked_by_approval`, not compared.
6. **Report** (`report.py`, [report.schema.json](../../services/blueprint/simulator/report.schema.json)). Steps with action and outcome, comparison rows, SIM-xxx anomalies with i18n message keys, excluded records, summary counts, a computed `verdict` (`pass`, `pass_with_warnings`, `blocked`, `aborted`) and empty owner and accountant sign-off fields. No timestamps and no model-written text: same inputs give the same report and `simulationId` (it identifies the plan, not the outcome). Params and ids can carry source text; every such string and every port string is sanitised (`safe.py`: control and bidirectional characters stripped, length caps, allow-listed error codes, record ids, metric and currency keys), and `simulate` validates its report against the schema before returning it. `blueprintRevision` is optional.

## Anomaly codes
SIM-101 unmapped account, SIM-102 rounding difference, SIM-103 missing tax code, SIM-104 negative stock, SIM-105 duplicate document, SIM-106 possible duplicate, SIM-107 date outside month, SIM-108 no tool for the record, SIM-109 needs approval, SIM-110 caller lacks role, SIM-111 invalid arguments, SIM-112 intake quality flag, SIM-113 unallocated payment, SIM-114 invalid source value, SIM-115 inconsistent document, SIM-116 unknown record kind, SIM-117 step blocked by an earlier step, SIM-118 parked by an approval rule, SIM-120 port error (run aborted), SIM-121 total mismatch, SIM-122 metric not compared, SIM-123 invalid reported amount, SIM-124 negative amount, SIM-125 payment currency differs from invoice, SIM-126 overpayment, SIM-127 payment before invoice, SIM-128 in doubt (exception during a call), SIM-129 tenant not empty (refused), SIM-130 tenant not empty (allowed), SIM-131 document total mismatch. SIM-119 is unused. Severities and keys live in `codes.py`. BPL-019 renders params as escaped data.

## Real engine versus simulated port
CI has no real tenant. `SimulatedPort` stands in: tool lookup, role pre-check, R3 and R4 parked, idempotency, draft and posted documents, line-level tax from the tenant's tax rates, moving-average valuation and aging on posted documents. It models behaviour only and is no evidence about the engine (UNVERIFIED). A gateway-backed port (Tool API calls on the replay user's session, totals through `report.run` or `metric.query`) replaces it without changing the planner, runner or comparison. The G2 exit must not treat the simulated port as evidence (Q-242). Open points: [open questions](../open-questions.md) Q-240 to Q-246.

## BPL-019: review and owner sign-off
Code: `review.py` (derived rules, view model, labels) and `signoff.py` (records, gate evidence); labels in `labels.json` (en and ar). The BPL-018 report is never changed; the review layer reads it (after validating it against the schema, so a hostile or malformed report is refused) and produces a view model.
- **Expected versus actual**: one row per metric with expected, actual, difference and tolerance as plain decimal strings built from minor units (`minor_to_str`), never floats; status and reason are i18n keys. Numerals are localised by the screen, not here.
- **Derived anomalies** (integer maths, flags only): SIM-132 sign flipped, SIM-133 tenant reports zero where an amount is expected, SIM-134 difference exactly at the tolerance limit, SIM-135 nothing compared, SIM-136 difference of 10 percent or more (basis points, integer floor). A blocking one turns the verdict to `blocked`. Thresholds are defaults (Q-273).
- **View model** (`build_view`): header, headline counts, rows, anomalies (message key, severity key, sanitised params as data, a fingerprint), sign-off state, `toAcknowledge` (fingerprints of every warning), and a `gate` block that is evidence only. Free text only appears as params; the screen must render them as escaped data.
- **Sign-off** (`record_decision`): a signed-in human (agents and service principals are refused) with the role, a caller-supplied timezone-aware time (the module never reads a clock), a decision with no default, a note, and the warnings acknowledged. Accepting is refused when the verdict is `blocked` or `aborted`; rejecting is always allowed. Accepting with warnings needs every warning acknowledged and a note. Records are append-only, final per role, bound to a digest of the exact report (a changed report makes earlier records stale and they do not count), and one person cannot hold both roles. `apply_signoffs` fills the report's `signOff` fields.
- **Gate**: `gate_evidence` returns who accepted which digest. It is evidence for the draft-to-live human gate (BPL-020, [ADR-0027](../decisions/ADR-0027-human-floor-action-policy-and-agent-authority.md)); it never promotes a tenant and nothing here auto-approves. Required roles are a parameter (Q-271).
- **Follow-up, no web row yet**: the screen, persistence of records, the gateway supplying `actor` and the clock, and merging the label keys into the web bundles (Q-272).
