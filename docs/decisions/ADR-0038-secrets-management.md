# ADR-0038: Secrets management: one store interface, keys that sign stay in the KMS, nothing secret reaches a log, the repo or a model

Status: Proposed
Owner: partner
Approved by: pending (cross-model review, then both founders; security review required by RULES 42)

Plan ID: SEC-002. Design only; no code until this is reviewed and accepted. Detail (inventory, access matrix, rotation table, requirements SEC2-001 to SEC2-047, test cases SEC2-T01 to SEC2-T39) is in [../security/secrets-management.md](../security/secrets-management.md). References ADR-0042 (ZATCA Phase 2, CMP-033, open PR #124), ADR-0039 (ERP-008, open PR #129), and ADR-0040 (PLT-003, open PR #144).

## Context
- Every C4 item in [data-classification.md](../security/data-classification.md) needs a home, an access rule, a rotation rule and a guarantee that it never leaks. The threat model lists the gaps: T4 (connector credentials), T10 (ZATCA signing keys), T53 (control plane holds engine admin credentials for every tenant), T60 (coding agents leaking secrets) ([threat-model.md](../security/threat-model.md)). Security baseline control 6 ("secret manager only; rotation runbook") is due at G1.
- Today secrets exist only on the dev bench: `scripts/provision_tenant_site.py` (ERP-003) generates the database and Administrator passwords and forwards them into the container environment, **where its shell invocation still passes `--db-root-password`, `--admin-password`, and `--db-password` on container `argv`** (`sh` inside the container, visible in `/proc/<pid>/cmdline` inside the container namespace; non-host argv only, a known gap that must be replaced by file/fd/stdin or post-create SQL before production). The engine writes the site database password and per-site `encryption_key` into `site_config.json` (standard engine behaviour, UNVERIFIED for every version we pin). Nothing is persisted in a secret store yet.
- The ZATCA keys are the critical case. ZATCA e-invoicing requires an ECDSA key on the `secp256k1` curve per e-invoice generation unit, a CSR, a compliance CSID and then a production CSID obtained with a one-time password (~60-minute OTP window, multi-year CSID lifetime per ZATCA Technical Guideline search excerpts; exact Developer Portal Manual PDF pages UNVERIFIED directly due to timeout, to be confirmed under CMP-004 alongside ADR-0042).
- Hosting is not chosen (INF-001, open question Q-129). Where the store physically runs, which KMS exists in-country and whether it offers hardware-backed keys all depend on that choice.

## Decision
1. **Everything in the inventory is C4 and lives in one logical secret store per environment and region**, reached only through two internal interfaces: `SecretStore` (get, put, rotate, destroy, list metadata; values typed `SecretValue`) and `Signer` (sign a canonical payload or non-ZATCA digest with a named key; the key is never returned). Concrete products sit behind these interfaces, so the hosting choice changes a backend, not callers. Production tenant secrets sit in the tenant's region (data-classification section 3); dev, staging and preview have their own stores and never hold a production secret (ADR-0018). Key hierarchy separates regional master KEKs (`S10a`) from per-tenant DEKs/backup DEKs (`S10b`) so no tenant payload or backup is ever encrypted directly under a shared key ([data-retention.md](../security/data-retention.md) section 8).
2. **Keys that sign stay inside the KMS or HSM wherever the backend supports the algorithm**: identity token signing keys (`S02`), internal service CA (`S03`), compiled-artifact integrity key (`S15`, engine-adapter 16.8), audit-chain export key (`S16`, SEC-008) and ZATCA keys (`Z1`).
3. **ZATCA signing: target is a non-exportable `secp256k1` key held by the KMS or HSM, behind a separate signer service; fallback in-process key is permitted for the first pilot only.**
   - **Verified/UNVERIFIED KMS landscape:** AWS KMS offers `ECC_SECG_P256K1` for signing (https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html, accessed 2026-11-18). Azure Key Vault offers `P-256K` (`ES256K`) on `EC-HSM` (https://learn.microsoft.com/en-us/azure/key-vault/keys/about-keys-details, accessed 2026-11-18). Google Cloud KMS `EC_SIGN_SECP256K1_SHA256` (`HSM`) appears in search summaries, direct doc HTTP fetch UNVERIFIED (`"OK"` stub returned 2026-11-18). HashiCorp Vault and OpenBao transit engines list only P-256, P-384, P-521 and Ed25519 (https://developer.hashicorp.com/vault/api-docs/secret/transit, https://openbao.org/docs/api/secret/transit/, accessed 2026-11-18), so they cannot sign `secp256k1` non-exportably.
   - **No blind digest-signing oracle:** The signer service **never** acts as a bare digest-signing oracle taking caller-supplied tenant/digest pairs. Instead:
     1. It takes the **canonical invoice or `<xades:SignedProperties>` input** and recomputes the hash itself.
     2. Before signing, it checks the request against the unit's own **ICV counter and PIH hash chain** (held by the signer or compliance submission store per ADR-0042, not trusted from a caller-asserted field).
     3. Callers authenticate by **mTLS workload identity (`S03`)**. The signer signs only for units of tenants placed by the control plane on that caller's bench pool (or named in a gateway-signed assertion), **never** a caller-supplied `tenantId`.
     4. It enforces a **per-unit rate cap and anomaly alert**.
   - **CMP-004 proof & pilot-only fallback policy (`ADR-0042` dated note `2026-11-18`):** `CMP-004` **must test a non-exportable `Z1` key inside KMS or HSM** end-to-end against ZATCA vectors/sandbox (`SEC2-005`). Per founder decision (`2026-11-18`), if hosting for the **first pilot only** lacks in-country KMS/HSM `secp256k1` signing, the fallback in-process signer key is permitted strictly under all of: (a) `Z1` is **encrypted at rest** in `SecretStore` wrapped under `S10a`/KMS, (b) decrypted **readable only by an isolated per-tenant (or single-tenant enclave) signer process**, decrypted into memory for **a single signature and immediately zeroized** (never shared in batch worker memory across tenants), and (c) **replaced with non-exportable KMS/HSM signing before G3**. The engine database, web workers, files and logs never hold `Z1` in clear in either path.
4. **One key and one CSID per e-invoice generation unit per tenant; no key is shared between units, tenants or environments.** Renewal always generates a new key pair (no CSR re-use with an old key); the prior `Z1`/`Z3` remain enabled strictly for the bounded drain window of in-flight 24-hour reporting retries, then disable and destroy after `D-3`. The Fatoora **OTP (`Z4`) is accepted only through the dedicated onboarding UI form**, never prompted for or entered in chat, used in one onboarding call, and **the plaintext OTP is never stored**. To enforce `SEC2-T10` deterministically across multiple workers and replicas within the ~60-minute window, onboarding persists only a short-lived (TTL ≥ 90 min), tenant/unit-scoped **keyed HMAC replay marker** of `(tenantId, unitId, otp)`.
5. **Least privilege by workload identity and honest pool boundary.** Each service authenticates to the store with its own short-lived workload identity (`S03`), never a shared static credential. Workload identities are bound to the **narrowest viable unit**: **per tenant** for connector jobs (`S11`), pilot fallback signers (`Z1`), and support sessions (`S17`); **per bench pool** only for shared engine workers (`S05`, `S07` unless per-tenant Redis ACL users are enabled). **Plain statement of enforcement:** for pool-shared engine workers (`S05`, `S07`), the store itself enforces **pool workload identity**, not per-request tenant claims; the `stamped tenant == path tenant` check (`SEC2-018`) is an **application guard** inside the engine worker/adapter. Key administration (create, rotate, disable, schedule destruction, change policy) and key use are **separate identities** (`SEC2-019`); provisioning secret metadata uses a separate admin identity from the ephemeral `provisioning-site-init` job identity that holds `S06` and generates/sets `S05`, `S08`, and `S21` during `create_site`/`harden_site` and is then discarded (`engine-adapter` workers never hold `S06` or `S08`).
6. **No human reads a C4 value in production; refined `ADR-0007` item 7 break-glass boundary.** Support can trigger a rotation, never view (`data-classification` section 3). **Refinement of `ADR-0007` item 7 (Accepted):** where `ADR-0007` item 7 requires tenant owner/admin JIT approval (`PLT-019`) before staff access to tenant data, `S08` (engine Administrator) and store-root/`S06` break-glass under this ADR is permitted only under strict conditions: (a) it is **limited to platform-incident repair with zero tenant-data read** unless `PLT-019` tenant approval has been obtained wherever the tenant/admin path is reachable; (b) it requires both founders (until a third trusted person exists), hardware-key MFA, a written reason, and a ≤ 1-hour time box; (c) it is logged off-box, alerts both founders, and notifies every affected tenant; (d) **any credential checked out under break-glass is rotated automatically by an automated forced-rotation job on session end or T+60m expiry** (alerting at T+65m if unrotated), and when shared DB server `S06` is used, every co-hosted tenant audit/notification rule applies. Cross-border staff access remains gated on `Q-14` (`ADR-0007` item 7). Agents never break-glass (`ALP-044`) and never read C4 (`ALP-016`).
7. **Rotation by schedule, by event and on expiry**, with dual-slot/overlap cutover so nothing breaks mid-rotation: token signing keys (`S02`) 90d with overlapping JWKS; service certificates (`S03`) ≤ 24h; tenant DB creds (`S05`) and pool cache/queue creds (`S07`) 90d via **dual-slot / dual-user (`slot_a`/`slot_b`) rotation** coordinated with worker reload before revoking the old slot; `S06` 30d + automated after every break-glass; `S18` **requires OIDC federation (`INF-003`) for production deploys** (fail closed on static deploy keys unless a time-boxed `GOV-017` exception is recorded); ZATCA CSIDs alerted at 60/30/14/7/1 days and expired/revoked CSIDs block issuing fail closed. Every staff departure or suspected leak rotates every reachable secret.
8. **Secrets never leave through side channels.**
   - `SecretValue` redacts itself in string, repr, JSON, pickle and exceptions.
   - Logs pass a structured scrubber (key deny-list + value patterns) before export; hits alert.
   - Errors map via `PLT-024`; core dumps/crash reporters scrubbed or disabled.
   - **Argv / disk / backups:** No secret on host `argv` or inside images/build args; replace the current `scripts/provision_tenant_site.py` container-shell password `argv` flags with fd/stdin/file/post-create SQL before production (`SEC2-T36` tests inside-container `/proc/*/cmdline`). While `INF-001` memory-backed `site_config.json` rendering is pending, exclude `site_config.json` and private site configs from every tenant backup and scan backup archives in `SEC2-T08`.
   - **Repo & CI:** `scripts/scan_secrets.py` + GitHub secret scanning stay required (`ADR-0021`).
   - **The model gateway never receives a secret:** Tool API excludes C4; the gateway checks prompts, tool results, and outputs against secret patterns and an in-memory set of **keyed HMAC fingerprints** keyed by `S23` (with secondary overlap key during rotation, synchronous invalidation on `secret.created`/`rotated`, bounded staleness SLA, fail-closed both at startup and on mid-run feed outage/staleness, and uniform generic blocks/scoped checks so Tenant B cannot probe Tenant A secrets). Chat **never prompts for an OTP** (OTPs are accepted only in the dedicated form), and pastes matching PEM/token/secret shapes are blocked before calling any model.
9. **Decided now:** inventory (`S01`–`S23`, `Z1`–`Z5`), key hierarchy (`S10a`/`S10b`), `SecretStore`/`Signer` interfaces, path scheme, workload-identity boundary, break-glass refinement of `ADR-0007` item 7 + forced auto-rotation, dual-slot rotation, ZATCA pilot fallback exception (`ADR-0042`), gateway fingerprint rules, and tests `SEC2-T01`–`T39`. **Deferred until INF-001 and Q-129 close:** concrete store product / KMS / HSM (`OpenBao` MPL-2.0 licence check under `LEG-004` UNVERIFIED), region, hardware-backed availability (`UNVERIFIED`), memory-backed `site_config.json` rendering, and OIDC cloud deploy wiring (`INF-003`). Selection criteria are in detail section 3.

## Alternatives rejected
- **Secrets persisted to disk in the engine's site config and copied into backups (status quo of the dev bench).** Readable by anyone with host or backup access, no rotation; fails data-classification C4 rules.
- **Self-hosted Vault or OpenBao as the only store, including production ZATCA keys.** Their transit engines lack `secp256k1`, making `Z1` exportable into process memory; acceptable only for the **first-pilot-only** fallback in item 3 (replaced before G3) or as the KV layer beside a non-exportable KMS/HSM. Vault's BUSL licence (`UNVERIFIED` for SaaS) needs `LEG-004`; OpenBao (`MPL-2.0`, `UNVERIFIED` under `LEG-004` until recorded) avoids BUSL.
- **One shared platform key for all tenants' ZATCA signing, or one shared fallback signer batch process holding multiple tenants' keys.** Impossible/unsafe by design (`Z1` per unit, and one process memory read compromises all tenants).
- **Let support staff read secrets to debug.** Rotation covers every support need; reading creates a standing exfiltration path (T53).
- **Store the raw OTP to retry onboarding later.** Single-use and short-lived; persist only the HMAC replay marker for `SEC2-T10` and ask the owner for a new OTP on genuine retry.

## Consequences
- Easier: one interface for every caller; hosting choice becomes a backend swap; one complete C4 inventory (`S01`–`S23`, `Z1`–`Z5`).
- Harder: signer service and fingerprint feed availability become live dependencies (fail closed); dual-slot rotation and ephemeral provisioning init add setup complexity.
- **Residual risks, stated plainly:** (1) Engine workers in one bench pool share OS/process access to that pool's `site_config.json` (`S05`, `S21`) and pool Redis/queue (`S07` unless per-tenant Redis ACL users are enabled), so a worker compromise exposes co-hosted sites in that pool — store policy only enforces pool identity (`SEC2-018` is an application guard). Tracked in `SEC-004` isolation tests and mitigated by `ERP-002` pool caps. (2) Until `ERP-003`'s inside-container `argv` flags are replaced before production, container-namespace `/proc` could observe creation args. (3) Break-glass using `S06` touches a multi-tenant DB server and triggers multi-tenant audit/rotation rules.
- Must be done: `SEC2` requirements map to rows in the detail doc. `ADR-0039` (`ERP-008`), `ADR-0040` (`PLT-003`), and `ADR-0042` (`CMP-033`/`CMP-004`) rely on this ADR. `CMP-004` tests non-exportable KMS/HSM `Z1` signing; `CMP-007` implements onboarding/renewal; `SEC-011` implements `S10a`/`S10b` envelope encryption and crypto-shredding; `INF-001` applies section 3 criteria; `Q-14` governs cross-border staff break-glass.

## Supersedes
None. Refines [ADR-0007](ADR-0007-identity.md) item 7 for platform-incident break-glass (`S08`/`S06`) with zero tenant-data read and `PLT-019` approval wherever reachable.
