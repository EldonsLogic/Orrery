# ADR-0038: Secrets management: one store interface, keys that sign stay in the KMS, nothing secret reaches a log, the repo or a model

Status: Proposed
Owner: partner
Approved by: pending (cross-model review, then both founders; security review required by RULES 42)

Plan ID: SEC-002. Design only; no code until this is reviewed and accepted. Detail (inventory, access matrix, rotation table, requirements SEC2-001 to SEC2-046, test cases SEC2-T01 to SEC2-T32) is in [../security/secrets-management.md](../security/secrets-management.md).

## Context
- Every C4 item in [data-classification.md](../security/data-classification.md) needs a home, an access rule, a rotation rule and a guarantee that it never leaks. The threat model lists the gaps: T4 (connector credentials), T10 (ZATCA signing keys), T53 (control plane holds engine admin credentials for every tenant), T60 (coding agents leaking secrets) ([threat-model.md](../security/threat-model.md)). Security baseline control 6 ("secret manager only; rotation runbook") is due at G1.
- Today secrets exist only on the dev bench: `scripts/provision_tenant_site.py` (ERP-003) generates the database and Administrator passwords and forwards them through the container environment, never on host argv; the engine writes the site database password into the site's config file (standard engine behaviour, UNVERIFIED for every version we pin). Nothing is persisted in a secret store yet.
- The ZATCA keys are the critical case. ZATCA e-invoicing requires an ECDSA key on the secp256k1 curve per e-invoice generation unit, a CSR, a compliance CSID and then a production CSID obtained with a one-time password from the Fatoora portal (third-party guides, for example https://www.wafeq.com/en-sa/tax-and-reporting/zatca-phase-2-integration:-5-steps-to-avoid-onboarding-errors and https://learn.microsoft.com/en-us/dynamics365/finance/localizations/e-invoicing-sa-onboarding, accessed 2026-11-18; the curve, the 60-minute OTP window and the roughly one-year certificate validity are UNVERIFIED until checked against ZATCA's own Developer Portal Manual, https://zatca.gov.sa/en/E-Invoicing/Introduction/Guidelines/Documents/DEVELOPER-PORTAL-MANUAL.pdf, under CMP-004).
- Hosting is not chosen (INF-001, open question Q-129). Where the store physically runs, which KMS exists in-country and whether it offers hardware-backed keys all depend on that choice.

## Decision
1. **Everything in the inventory is C4 and lives in one logical secret store per environment and region**, reached only through two internal interfaces: `SecretStore` (get, put, rotate, destroy, list metadata; values typed `SecretValue`) and `Signer` (sign a digest with a named key; the key is never returned). Concrete products sit behind these interfaces, so the hosting choice changes a backend, not callers. Production tenant secrets sit in the tenant's region (data-classification section 3); dev, staging and preview have their own stores and never hold a production secret (ADR-0018).
2. **Keys that sign stay inside the KMS or HSM wherever the backend supports the algorithm**: identity token signing keys, internal service CA, compiled-artifact integrity key (engine-adapter open question 16.8), audit-chain export key (SEC-008) and the ZATCA keys. Callers send a digest; the KMS returns a signature.
3. **ZATCA signing: target is a non-exportable secp256k1 key held by the KMS or HSM, behind a separate signer service.** AWS KMS offers `ECC_SECG_P256K1` for signing (https://docs.aws.amazon.com/kms/latest/developerguide/symm-asymm-choose-key-spec.html, accessed 2026-11-18); HashiCorp Vault and OpenBao transit list only P-256, P-384, P-521 and Ed25519 (https://developer.hashicorp.com/vault/api-docs/secret/transit, accessed 2026-11-18), so they cannot hold this key non-exportably. Whether the ZATCA signature flow (XAdES signed properties, invoice hash, QR stamp) can be completed from a remote digest-only signature, and whether the ERPGulf app can call an external signer instead of reading the key itself, is UNVERIFIED; CMP-004 must prove it against the ZATCA sandbox. **Fallback, if either fails:** the key is generated in an isolated signer process, stored only in the secret store encrypted under a KMS key, loaded into that process's memory per signing batch, never written to the engine database, a file or a log, and never handed to an engine web worker. The engine never holds the ZATCA private key in a database field in clear in either path; if the ERPGulf app requires that, it is adapted (a documented import change with PROVENANCE) or replaced, not accepted.
4. **One key and one CSID per e-invoice generation unit per tenant; no key is shared between units, tenants or environments.** Renewal always generates a new key pair (no CSR re-use with an old key). The OTP is entered by an owner or admin in a dedicated form, used in one call and never stored, logged, shown again or passed through the chat or a model.
5. **Least privilege by workload identity.** Each service authenticates to the store with its own workload identity, never a shared static credential. Policies are path-scoped: `{env}/platform/{service}/{name}` and `{env}/tenant/{tenantId}/{kind}/{name}`. A tenant-scoped read requires the tenant from the platform-stamped context, never from a request body. Key administrators can rotate, disable and schedule destruction but cannot use or read a key; key users cannot change policy.
6. **No human reads a C4 value in production.** Support can trigger a rotation, never view (data-classification section 3). Break-glass to the store's root or KMS administration needs both founders (until a third trusted person exists), hardware-key MFA, a written reason, a time box; it is logged, alerts both founders, and the affected tenant is notified when a tenant secret is touched. Agents never use break-glass (ALP-044) and never read C4 (ALP-016).
7. **Rotation by schedule, by event and on expiry**, with overlap so nothing breaks mid-rotation. Cadences are in the detail doc; key ones: model-provider keys 90 days, token signing keys 90 days with overlapping published keys, service certificates at most 24 hours, tenant database credentials 90 days, ZATCA production CSIDs renewed from 60 days before expiry (alerts at 60, 30, 14, 7, 1 days; expiry blocks invoice issue fail closed rather than issuing unsigned). Every staff departure or suspected leak rotates every secret that person or system could reach.
8. **Secrets never leave through side channels.**
   - `SecretValue` redacts itself in string, repr, JSON and exceptions.
   - Logs pass a structured scrubber (key deny-list plus value patterns) and an alert fires on any hit.
   - Errors are mapped to our error model before leaving a service (PLT-024).
   - No secrets on argv, in container images, in core dumps or in crash reports.
   - In the repo, `scripts/scan_secrets.py` runs in pre-commit and CI, with GitHub secret scanning on top (ADR-0021).
   - **The model gateway never receives a secret.** The Tool API generator excludes C4-classed fields from every schema and result. Tools never return C4. The gateway runs an outbound filter on every prompt and tool result: secret patterns plus fingerprints of live secrets. A hit blocks the call and raises `agent.output_flagged`. Pasted keys or OTPs in chat are caught before the model call.
9. **Decided now:** the inventory, classes, interfaces, path scheme, access model, break-glass rule, rotation cadences, redaction and model-gateway rules, and the test cases. **Deferred until INF-001 and Q-129 close:** the store product and KMS or HSM, its region, whether hardware-backed keys are available in-country, how the engine's site config file gets its database password (rendered at start into memory-backed storage is the target), backup key custody, and the CI deploy credential (target: OIDC federation, no long-lived cloud keys in CI). The selection criteria are in the detail doc section 3.

## Alternatives rejected
- **Secrets in the engine's site config and database (status quo of the dev bench).** Readable by anyone with host or database access, copied into every backup, no rotation; fails data-classification C4 rules.
- **Self-hosted Vault or OpenBao as the only store, including ZATCA keys.** Good secret manager, but its transit engine has no secp256k1, so the ZATCA key would be exportable and in process; acceptable only as the fallback in item 3 or as the KV layer beside a KMS that signs. Vault's licence (Business Source since 2023, UNVERIFIED for our SaaS use) also needs a LEG-004 check; OpenBao (MPL) avoids that.
- **One shared platform key for all tenants' ZATCA signing.** Impossible by design (each unit has its own CSID) and one leak would hit every tenant.
- **Let support staff read secrets to debug.** Rotation covers every support need; reading creates a standing exfiltration path (T53).
- **Store the OTP to retry onboarding later.** It is single-use and short-lived; a retry asks the owner for a new one.

## Consequences
- Easier: one interface for every caller; the hosting choice becomes a backend swap; an auditor gets one inventory and one rotation table.
- Harder: a signer service and its availability become a dependency of invoice issue (CMP-004); store outages fail closed, so the store needs its own uptime target and runbook (PLT-015).
- Residual risk, stated plainly: engine workers in one bench pool serve several sites and can read every site config on that pool, so a worker compromise exposes those sites' database credentials. Mitigations are per-pool limits (ERP-002), short-lived credentials where the engine allows, and SEC-004 isolation tests; it is not eliminated.
- Must be done: SEC2 requirements are mapped to rows in the detail doc. ADR-0039 (ERP-008) and ADR-0040 (PLT-003) rely on this ADR; PLT-003 creates per-tenant secrets only through `SecretStore`. CMP-004 must answer the remote-signer question in item 3; CMP-007 implements ZATCA onboarding and renewal on this design; SEC-011 implements envelope encryption and crypto-shredding; INF-001 must apply the selection criteria. A plan row for the secret store implementation should be added once hosting is chosen (founder decision; not added here).
