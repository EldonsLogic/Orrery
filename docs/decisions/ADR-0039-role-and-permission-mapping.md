# ADR-0039: Blueprint roles map to adapter-owned engine roles, field levels and record scopes by a fixed table; anything unmapped or unresolved is denied

Status: Proposed
Owner: partner
Approved by: pending (cross-model review, then both founders; security review required by RULES 42 because this touches authorisation)

Plan ID: ERP-008. Design only; no code until this is reviewed and accepted. Detail (mapping tables, permission-level algorithm, drift fingerprint, the 48 denied-case tests DENY-01 to DENY-48) is in [../architecture/role-and-permission-mapping.md](../architecture/role-and-permission-mapping.md). Cross-references ADR-0038 (SEC-002, open PR #128) and ADR-0040 (PLT-003, open PR #144) in plain text until those ADRs land on `main`.

## Context
- A Blueprint role (contracts/blueprint.schema.json `role`) has `function`, one `scope` (company, branch, warehouse, department, own_records, assigned_records), `permissions` per entity (actions read, create, update, delete, submit, cancel, approve, export, with `hiddenFields` and `readOnlyFields`), `canUseChatActions` and `isAdmin`.
- The engine expresses access as roles, permission rules per document type and permission level, field permission levels, record-level user permissions, and role profiles (https://docs.frappe.io/framework/user/en/basics/users-and-permissions, accessed 2026-11-18; behaviour on our pinned version UNVERIFIED until the bench tests in the detail doc pass).
- Rules already settled:
  - Roles never come from the caller (CE-SEC-001).
  - Role lookup fails closed and never falls back to System Manager (CE-SEC-002).
  - Human shadow engine users carry the member's Blueprint roles, and drift is a security bug ([ADR-0007](ADR-0007-identity.md) items 4, 9, 11; see item 7 below for our refinement of item 9's store location).
  - Roles map to adapter-owned roles, never built-in engine roles (contracts/engine-mapping.md).
  - The adapter never authorises on `onBehalfOf.roleIds` and accepts no role from `input` (contracts/engine-adapter.md 4.2, ADP-C-002, ADP-C-012).
  - `role.upsert` and `role.disable` are `unsupported` until ERP-008 (contract section 13).
  - Agents are their own principals and never use a human's session or human shadow engine user ([agent-least-privilege.md](../security/agent-least-privilege.md) ALP-001).
- The gateway (OPR-004) is the first check on every tool call. For human users, the engine-side mapping is a second, independent check so chat never exceeds what the user could do in the engine's own UI (Tool API section 4). For agents, the engine layer bounds the agent's grant only; the on-behalf-of human permission intersection is enforced by the gateway (see item 10).

## Decision
1. **One managed engine role per Blueprint role**, named deterministically from the role id with a reserved prefix and marked as adapter-managed. The adapter creates, changes and disables only managed roles. It never grants, edits or assigns a built-in engine role (System Manager, Administrator, or any other shipped role). Automatic and built-in roles attached to engine users (`All`, `Guest`, `Desk User`, `Website Manager`) hold zero permissions on mapped document types **and** on unmapped business, audit, system, file and ledger document types (including `Version`, `Comment`, `Communication`, `Activity Log`, `Notification Log`, `File`, `ToDo`, `User`, `Prepared Report`, `Data Import`, `GL Entry`, `Stock Ledger Entry`), except an explicit reviewed minimal allowlist. The site is verified for this before it is marked ready and on every drift check.
2. **Actions map by a fixed table** (detail section 2): read gives read; create gives create; update gives write; delete gives delete; submit gives submit; cancel gives cancel; export gives export. `approve` is never a document permission: it becomes the role's right to the matching workflow transitions. Report and print stay off until `DENY-21`, `DENY-22` and `DENY-23` pass on the bench; create, write, report and print on entities with field masking are gated on `DENY-23` (child-table permlevel enforcement) passing on the bench. Share, import, set-user-permissions and email are never granted. Amend is granted only with both create and cancel.
3. **Fields: hidden and read-only become permission levels, computed deterministically.** For each entity, fields are grouped by their signature (per role: writable, read-only or hidden). Fields treated uniformly by every read-capable role—every role `w`, or `r` only where a role lacks `update`, or `r` for all roles because the field is Blueprint `readOnly` or computed (marked `read_only=1` on the DocField)—stay at level 0 so read-only/computed fields do not waste the 9 extra permlevels. Every other signature gets its own level 1 to 9. Level numbers are kept for signatures that already have one, and new signatures take the lowest free level, so the layout depends only on the previous layout and the target Blueprint. More signatures than levels rejects the plan (`limit_exceeded`). Bench tests must verify `insert`/REST `PUT` enforcement for `readOnlyFields`, `hiddenFields`, mandatory (`reqd`) hidden fields, and child tables (`DENY-23`, `DENY-38`).
4. **Record scope (strictly no mixed scopes on shared entities):**
   - `company` adds no restriction.
   - `branch`, `warehouse` and `department` become record-level user permissions on each holder's shadow user, pointing to mapped location records and restricted to the document types that role grants.
   - The plan rejects any role with `branch`, `warehouse` or `department` scope if it grants an entity whose engine mapping lacks a link field for that location type, unless the entity is a reviewed non-scoped baseline reference type (`DENY-35`).
   - `own_records` becomes the owner-only flag (`if_owner`) on that role's rules.
   - `assigned_records` has no engine equivalent we have verified, so a role with it is rejected at plan (`unsupported_value_type`). The gateway still enforces it for chat; the engine side denies, it does not widen.
   - Because the engine unions permissions across roles with OR semantics, assigning one member roles with conflicting scopes on the same entity (such as `own_records` plus `branch`, or `branch-A` plus `branch-B`) would fail open. Therefore mixed scopes across multiple roles on any shared entity are forbidden and rejected at the assignment store and in `sync_members` (`scope_conflict`; resolves detail section 7 D-4). Multiple roles on one member are permitted only when scopes on every shared entity are identical or their granted entities are disjoint.
5. **Role profiles are not used for enforcement.** Engine roles are assigned to each shadow user directly by `sync_members`. Whether profile changes propagate to users differs between sources and versions (UNVERIFIED), and a bundle that may lag is a drift path.
6. **`isAdmin` and `canUseChatActions` are platform rights, not engine rights.** `isAdmin` maps to nothing in the engine and never to a system or administrator role (`DENY-41`). `canUseChatActions: false` is enforced by the gateway only.
7. **Single external assignment store and fail-closed defaults** (requirement list in detail section 5):
   - Authoritative member-to-role and agent-grant assignments live outside the engine site in one platform store (regional provisioning assignment store, versioned by monotonic `syncVersion`). This proposes superseding only ADR-0007 item 9's location wording; accepted ADR-0007 remains authoritative until both founders approve that supersession. Q-292 records the conflict and blocks implementation of the external-store move; drift checks must never compare the engine with itself.
   - No role, scope or user from any request body, model output, artifact or event.
   - An unmapped entity, field, action, location, location link or scope rejects the role step at plan. Nothing is mapped to the "nearest" permission.
   - Any engine permission on a managed or automatic role—or any non-managed role or unmanaged enabled engine user—that the mapping does not produce is drift, and extra access is removed first.
   - An unknown role in an assignment gives `unknown_role` and changes no member.
   - A failed lookup at any stage (assignment store, mapping, engine read) denies. There is no default role, no cached role set past its maximum age, and no fallback to any administrator, system or guest-with-rights role.
   - A member with no active role has a disabled shadow user.
   - A permission change that cannot be compensated leaves the site `recovery_required`, and the gateway refuses every tenant call except reads of platform status until a human resolves it.
8. **Blueprint change, idempotency, and apply-sync ordering.**
   - Role ops arrive as `role.upsert` and `role.disable` (contract 9.3). Re-enabling a previously disabled `roleId` via `role.upsert` reuses the preserved managed role record and restores rules cleanly rather than failing with `subject_exists`. The adapter applies all role steps of one artifact as one permission reconciliation per affected entity, journaling the before-layout for compensation.
   - Hold a tenant permission-reconciliation fence across apply, sync and verification; block tenant business calls throughout. On failure keep the fence until compensation is verified or recovery is completed. Initial provisioning uses this same boundary. Contract changes for this orchestration must be accepted before implementation.
   - Removing a role still assigned is refused (`subject_in_use`). A disabled role keeps its record for audit with all rules removed.
   - For any `apply` that touches roles, `apply` verifies role/level/transition/auto-role state, clears the engine's permission cache for affected users, requests a full assignment snapshot from the authoritative store with a newly allocated monotonic `syncVersion` (the adapter never invents or reuses a version), invokes `sync_members`, and passes the full drift fingerprint post-condition **before** reporting `applied`. If `sync_members` or the post-condition fails (for example leaving wider stale assignments after narrowing a scope), the adapter compensates back to the pre-apply layout (or marks the site `recovery_required` if compensation fails; `DENY-43`).
9. **Drift detection and baseline grants.** A canonical fingerprint covers: every role on every engine user (managed and built-in/automatic); the set of enabled engine users; managed roles and their rules; custom permission rules on mapped types and on automatic/built-in roles across mapped and unmapped audit/system/file/ledger types; the level of every mapped field; workflow transition roles; user permissions; and reviewed baseline grants. Reviewed reference-data baseline grants must pass structural validation: strictly `read`-only, zero C3/C4 fields, and never attached to `All` or `Guest` (`DENY-45`). On mismatch the adapter alerts, removes non-managed role assignments / disables unmanaged users / strips extra grants first, then restores the approved Blueprint layout and re-checks. Restoring an already-approved Blueprint layout during drift reconciliation is restoration of prior human-approved state rather than a new grant under [ADR-0027](ADR-0027-human-floor-action-policy-and-agent-authority.md); a second mismatch moves the site to `recovery_required`. A new event `engine.permission_drift` is proposed; it is not in force until the events contract ADR adds it.
10. **Agents get their own draft-only engine principal and grant-scoped role.**
    - Per [agent-least-privilege.md](../security/agent-least-privilege.md) section 3.1 (amended in this PR alongside ALP-001 and OQ-2 for Eldon's review), each agent gets a separate draft-only agent engine user in its own namespace (never a human's shadow user, no password, no API key, no email, never able to sign in).
    - It carries one managed role per agent grant (`agent-eligible Blueprint role ∩ grant`, resolving ALP OQ-2).
    - **Draft-only writes:** Agents receive `create` and `write` **only** on `docstatus == 0` drafts of entities whose reviewed mapping of engine draft capability and Blueprint `workflows[].transitions[].kind` ([ADR-0037](ADR-0037-manifest-risk-class-and-transition-kind.md)) explicitly permits drafts. Submit, cancel, amend, approve, delete, export, and direct `create` or `write` on non-submittable master or settings entities (such as Supplier bank details, Customer, Item, price lists, and settings) are always stripped; any agent update to a non-submittable entity must use a pending-change record requiring human approval (`DENY-36`).
    - **Honest enforcement boundary:** For agents, the engine layer bounds only the agent's grant (`AG-*`). Because the agent engine user does not dynamically intersect with the calling human's per-call scope (`TC-13` and human branch scope), the intersection with the on-behalf-of user's current permissions is enforced by the gateway (`ALP-005`, `ALP-006`) and is explicitly named here as a residual engine-layer dependency (future optional defence: pre-check permission as the on-behalf-of human shadow user without ever acting as them).
    - **Synchronous revoke/kill and adapter fail-closed:** Grant revocation, expiry, owner suspension, or kill-switch engagement synchronously disables the agent's engine user durably before revocation/kill reports complete (`ALP-022`). Both the gateway and the adapter re-check grant state/version (`ALP-023`) and the kill-switch flag (`ALP-036`), failing closed when the kill flag store is unreachable (`DENY-42`).
    - **Contract follow-ups (`sync_principals` & `S09`):** `contracts/engine-adapter/sync-members.schema.json` currently validates only `m_*` members (`additionalProperties: false`). Delivering grant-intersected agent roles (`ag_*`) and expiring JIT support principals (`PLT-019`, `S17`) requires a follow-up contract ADR (Eldon's lane) extending `sync_members` or adding `sync_principals` with principal `kind` (`member` | `agent` | `support`), grant intersection payloads, and expiry. Additionally, per ADR-0038 (open PR #128), `S09` gateway impersonation credentials must be distinct and bound by principal kind (`human` vs `agent`) so a gateway defect cannot impersonate a human shadow user on an agent path. Support principals follow the same grant pattern (`PLT-019`), read-only by default and auto-disabled on grant expiry (`S17`).

## Alternatives rejected
- **Map Blueprint roles onto built-in engine roles** (for example a finance role onto the engine's accounts roles): their permissions change with engine upgrades and are wider than the Blueprint says; contradicts contracts/engine-mapping.md.
- **One role profile per member role combination:** propagation is uncertain, and it multiplies objects without adding control.
- **Rely on engine OR union semantics for conflicting multi-role scopes (`RM-015` v1):** fails open when combining `own_records` with `branch`, or `branch-A` with `branch-B`, on the same entity.
- **Fail open with a warning when a mapping is missing** (the prototype behaviour CE-SEC-002 removed): turns every gap into silent over-permission.
- **Enforce only at the gateway:** a gateway bug, or any engine path the gateway does not cover, would expose everything. Defence in depth is the point of the shadow user.
- **Run agent calls as the on-behalf-of human's shadow user:** gives the agent everything the human can do in the engine and contradicts ALP-001.
- **Widen implicitly so documents work** (auto-granting read on linked entities): convenient but invisible. The validator should instead flag a link target the role cannot read (BPL-003 lint follow-up), and the result is a deny until the Blueprint grants it. Reference data every document needs (currency, units, the company record) comes only from reviewed per-component baseline grants listed in the mapping. These are read-only and never on C3, C4 or ledger writes.

## Consequences
- Easier: one deterministic table both sides can test; OPR-004, WEB-010 and WEB-011 build on fixed semantics; drift is measurable across all engine users and unmapped DocTypes.
- Harder: field-level masking is limited to 9 extra signatures per entity (though uniformly `readOnly`/computed fields stay on level 0). `assigned_records` is blocked in the engine until a reviewed mechanism exists. Mixed-scope roles on shared entities are disallowed at assignment time. Report, print, masked create/write, REST insert/PUT and child-table behaviour must pass on the bench (`DENY-21..23`, `DENY-38`) before enablement.
- Must be done:
  - Eldon's lane / shared follow-up ADRs: (1) confirm `docs/security/agent-least-privilege.md` §3.1, `ALP-001` and `OQ-2` edits included in this PR; (2) contract ADR extending `sync_members` / adding `sync_principals` for `agent` and `support` principals + expiry (`S17`) and adding `engine.permission_drift`; (3) note the [ADR-0007](ADR-0007-identity.md) item 9 assignment-store location refinement in the next identity/Tool API ADR; (4) `contracts/engine-mapping.md` fields for permlevels and baseline grants.
  - ADR-0038 (open PR #128) tracks separate `S09` binding per principal kind (`human` vs `agent`).
  - Gateway error mapping (`PLT-024`) must strip any managed engine role names so engine identifiers never leak to callers (`ADR-0016`, `DENY-46`).
  - ERP-008 implementation ships `DENY-01` to `DENY-48` against the fake and the real adapter. PLT-003 (ADR-0040, open PR #144) runs the first `sync_members` and stores the drift baseline.
