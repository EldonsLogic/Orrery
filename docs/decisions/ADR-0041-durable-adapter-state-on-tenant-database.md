# ADR-0041: Durable adapter state lives in the tenant database

Status: Proposed
Owner: partner
Approved by: pending (Eldon review)

## Context
The engine adapter ([contracts/engine-adapter.md](../../contracts/engine-adapter.md) 5.6 and the idempotency rules) promises that a key replays its stored result for at least 30 days, that the step journal proves no step ran twice, and that audit records survive. Until ERP-026 the adapter state sat in a SQLite store whose default is `:memory:`, so a restart or a restore could forget a key and let an apply run a second time. ADR-0028 requires durable checkpoints at every recovery boundary.

## Decision
- **Where:** all adapter state is stored in the tenant's own MariaDB database, beside the tenant data. One schema per tenant database; every table still carries `tenant_id` (`adapter_events` too) and a store can be bound to one tenant at construction (`tenant_id=`): it then refuses every other tenant (the platform id excepted), and events, audit and journal reads return only that tenant's rows, so a misrouted connection can neither read nor write across tenants. The adapter answers a misrouted call `tenant_not_found` and writes no foreign tenant id. An unbound store (dev, tests, the conformance harness) serves any tenant.
- **Tables:** `adapter_sites` (state, applied ids, history, lock), `adapter_idempotency` (PK tenant, operation, key; input hash; stored outcome; `created_at`), `adapter_plan_tokens`, `adapter_plan_evidence`, `adapter_prepare_intents`, `adapter_execution_journal`, `adapter_audit_log` (unique audit id), `adapter_events`, `adapter_members`. Schema is created idempotently (`CREATE TABLE IF NOT EXISTS`, InnoDB, utf8mb4).
- **Reserve before the effect (multi-worker):** `acquire` binds the idempotency key and takes the site lock in one committed database transaction before any effect: an `in_progress` row in `adapter_idempotency` (unique key `(tenant, operation, key)`, input hash, operation id, lease expiry) plus a compare-and-set on `adapter_sites.lock_id`. A second worker (any process, any connection) gets the stored `in_progress` outcome, or the final outcome after completion, or `idempotency_conflict` for other input, or `concurrent_change` for another key while the lock is held; it never runs the effect. No in-process cache or counter takes part: sites are read from the database, audit and operation ids are random, event ids are ULIDs. `provision_site` and `sync_members` reserve their key the same way; for them a concurrent retry gets `concurrent_change` (the contract defines the `in_progress` outcome for apply and rollback only). The bound input hash is never rewritten (`idem_put` raises on other input); `sync_version` moves only by compare and set.
- **Transactions and crash recovery:** `finalize` commits the outcome (compare and set on the reservation), the site row and the event in one `store.transaction()`; a failure between them leaves the acquire state, never a half-write. `MariaDBAdapterStore.transaction()` nests as savepoints (an inner failure the caller catches undoes only the inner work), refuses DDL inside it (DDL commits implicitly), and requires a connection with autocommit off. A worker that dies mid-operation leaves an `in_progress` row and a lock; when its lease (`lease_seconds`, default 3900, above the contract's one-hour deadline) expires, any worker closes it exactly once: apply and rollback end as `recovery_required` (site blocked and unlocked for a human, ADR-0028, never a second blind run) and the same key replays that outcome; other operations are released to retry. Recovery runs at adapter construction and lazily when a lock or lease is found stale. A worker that lost its lease cannot finalize (its writes roll back) and gets the stored `recovery_required` outcome as `ok: true` (contract 5.6.1: the operation record exists). Ownership (an unexpired lease and the site lock) is re-checked before every journal entry, engine step and DDL statement, so a worker whose lease ran out stops at once and runs nothing more. Whether a run puts the site back to `ready` is decided by the acquire itself (it reports whether it moved the site out of `ready`), never by an earlier read, so a worker that finishes between another worker's read and acquire cannot leave the site stuck in `applying`. An unexpected error inside a run closes it in process: `failed_clean` when no step ran, otherwise `recovery_required`, lock released, instead of waiting out the lease. `provision_site` and `sync_members` check the result of the key completion inside their transaction and roll back when the reservation was lost (`concurrent_change`, retryable); `sync_members` holds a row lock on the tenant's site until its commit, so two syncs of one tenant run one after the other and a later call cannot overwrite what an earlier one committed. The runbook for clearing `recovery_required` is [adapter-recovery-required](../runbooks/adapter-recovery-required.md). Effects the adapter cannot put on the tenant connection (DDL, external sends) rely on the journal and these recovery rules.
- **Retention:** idempotency keys at least 30 days (the contract's `idempotencyRetentionSeconds`); the purge job is a follow-up and deletes by `created_at`, never earlier. Journal and audit records are not purged by the adapter; the audit retention period belongs to the compliance docs and is UNVERIFIED here.
- **Restore:** because keys, journal and the data they describe live in one database, a dump or point-in-time restore returns them together as of one moment. A key issued after the restore point is unknown after the restore, and its effect was rolled back with it, so a retry is a correct first run. Tested with a real dump and restore.
- **Production guard:** the adapter takes an `AdapterStore`. Production is `environment="production"`, or `CHANGE_ENGINE_ENV` set to anything other than `dev`, `development` or `test`, or, when neither is set, hooks switched off. An explicit `environment` argument, even empty, is never replaced by the variable; empty and unknown values are production. In production the adapter refuses at construction: test hooks (`test_hooks` defaults to off), a volatile store, and any store that is not production-grade (`production_grade`: MariaDB only). A SQLite file is durable but outside the tenant database backup boundary, so it is dev and test only. `reset()` needs test hooks like the other hooks.

## Alternatives rejected
- A central state store (one database for all tenants): a second place to back up and restore, so keys and effects can disagree after a restore of either side; a shared failure and cross-tenant exposure point; breaks per-tenant export and deletion.
- Redis or another cache for keys: not durable by default and not covered by the tenant backup.
- Keep SQLite files per tenant: not covered by the tenant database backup and a second durability story to operate.

## Consequences
- Follow-ups (not in ERP-026): wire the engine's effects onto the tenant connection (`FrappeRuntimeBackend`, ERP-003) so engine writes join `store.transaction()`; heartbeat to shorten the lease; the 30-day purge job (`created_at` is indexed); a restore drill on the real bench (CE-SEC-005); an audited admin operation to clear `recovery_required` instead of the manual runbook SQL (needs a contract change); a migration for any adapter state created before `adapter_events.tenant_id` existed (none is deployed). Behaviour with `provision_site` crashing after the engine provisioned but before the site row exists is UNVERIFIED (a retry re-runs provisioning).
- Tests: conformance for both stores, restart replay, restore (including a real apply after the dump and a correct first run after restore), guard table, two-connection and two-thread races, crash injection between the state write and the key write, lost lease; MariaDB tests need a server and are skipped without one locally; CI runs them on a MariaDB 11.4 service with `REQUIRE_ERP026_MARIADB=1`, which turns a missing server, driver or container into a failure, so they cannot skip silently. Added after the cross-model review of PR 126: the two-worker race that left a site in `applying`, a key lost to lease recovery in `provision_site` and `sync_members`, concurrent `sync_members`, an expired lease before a step or DDL, unexpected errors before and after a step, and tenant binding.
