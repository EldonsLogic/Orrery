## Context
CMP-004 (G1) needs a ZATCA Phase 2 invoice that passes the ZATCA sandbox: signing, hash chain, clearance and reporting. CMP-002 evaluated the only MIT-licensed Frappe/ERPNext option, the ERPGulf ZATCA app ([zatca-erpgulf-evaluation.md](../compliance/zatca-erpgulf-evaluation.md)). The AGPL Lavaloon app is forbidden (RULES 34, ADR-0002). The evaluation proposed "adopt with wrapper or vendor core logic" and required an ADR before any build. That is this record (CMP-033).

What the evaluation found, and what this ADR re-checked:
- **Licence.** MIT, `Copyright (c) 2024 ERPGulf` ([LICENSE](https://github.com/ERPGulf/zatca_erpgulf/blob/main/LICENSE), accessed 2026-11-18); the GitHub API reports `spdx_id: MIT` ([repos/ERPGulf/zatca_erpgulf](https://api.github.com/repos/ERPGulf/zatca_erpgulf), accessed 2026-11-18). Root `license.txt` still holds the unfilled MIT template. Direct and runtime dependencies are permissive (pikepdf MPL-2.0); the transitive tree is UNVERIFIED. Recorded in the [licence register](../legal/licence-register.md) (LEG-004).
- **Upstream state.** Tag `v3.0.1` is commit `d906ba7` ([release](https://github.com/ERPGulf/zatca_erpgulf/releases/tag/v3.0.1), accessed 2026-11-14). `main` head at this writing is `015eaf80b7d2a910c73a2eca553bbafa1410dbfa` (2026-11-16, [commits/main](https://github.com/ERPGulf/zatca_erpgulf/commits/main), accessed 2026-11-18). The function and line references below are from that commit.
- **No tests.** All four `test_*.py` files are `pass` stubs; the CI workflow targets another app (evaluation 4.2).
- **Non-transactional chain.** `sign_invoice.py` writes the previous-invoice hash straight onto the Company or settings record (`company_doc.custom_pih = encoded_hash` at `409, 415, 421, 500, 506, 516` in `reporting_api` and `714, 721, 728, 786, 793, 803` in `clearance_api`) without a row lock, so concurrent submissions can read the same PIH and fork the chain (evaluation 3.2).
- **ICV is not a counter.** `createxml.get_icv_code` (line 18) strips the non-digits out of the invoice name and uses the rest as the ICV. It is not an allocated sequence.
- **Desk coupling.** `frappe.publish_realtime("show_gif" / "hide_gif")` in `sign_invoice_first.py` (lines 368, 380, 1365, 1366, 1377) and `sign_invoice.py` (lines 268-269, 279, 602-603, 655), Desk assets, workspace and custom pages in `hooks.py`, and `custom_*` fields on `Company`, `Customer`, `Address` and `Sales Invoice` (evaluation 4.2). That conflicts with ADR-0016 (engine invisible, headless).
- **Keys in records.** `create_private_keys` (line 118) writes the private key as unencrypted PEM (`NoEncryption()`) into a document field; `digital_signature` (line 558) reads it back from the Company or settings record. That conflicts with key custody in the threat model (T10, SEC-002, SEC-011).

So the stateful half of the app (chain, counter, queue, hooks, keys) is the half we cannot use. The stateless half (key and CSR generation, XML, canonicalisation, hashing, signing, QR TLV helpers) holds real ZATCA know-how we should not rewrite blind.

## Decision
**Hybrid. Vendor the app's pure-Python XML/crypto structure (stripped of all arithmetic, `frappe.*` calls, and unsafe defaults); rebuild everything that touches state.**

### 2. Rebuild ourselves
- **EGS invoicing unit resolution & genesis PIH.** On submit, resolve the branch/company invoice to an onboarded ZATCA EGS invoicing unit (multi-branch / multi-device aware); **fail closed** if no unit is mapped, or if the unit has no active CSID (expired, revoked, or onboarding incomplete). For a brand-new unit (`ICV = 1`), the genesis PIH is Base64 of the SHA-256 lowercase hex digest of `"0"` (`NWZlY2ViNjZmZmM4NmYzOGQ5NTI3ODZjNmQ2OTZjNzljMmRiYzIzOWRkNGU5MWI0NjcyOWQ3M2EyN2ZiNTdlOQ==`, [Electronic Invoice XML Implementation Standard](https://zatca.gov.sa/ar/E-Invoicing/SystemsDevelopers/Documents/20230519_ZATCA_Electronic_Invoice_XML_Implementation_Standard_%20vF.pdf) v1.2, p. 54, and [Electronic Invoice Data Dictionary](https://zatca.gov.sa/ar/E-Invoicing/SystemsDevelopers/Documents/20230519_EInvoice_Data_Dictionary%20vF.xlsx), field `KSA-13`, both published on [ZATCA E-Invoice specifications](https://zatca.gov.sa/en/E-Invoicing/SystemsDevelopers/Pages/E-Invoice-specifications.aspx), accessed `2026-11-19`).
- **Hash chain and invoice counter allocator (Option B: short DB lock + outside-lock KMS signing).** One chain per EGS invoicing unit, in its own table (`apps/engine/change_engine/change_engine/compliance/`), not custom fields on core records. Because ZATCA's `invoice_hash` is the SHA-256 of the C14N 1.1 invoice XML *after stripping `UBLExtensions`, `QR`, and `Signature`* (XML Implementation Standard v1.2, p. 54), `invoice_hash` — and therefore the next invoice's `PIH` — is fully deterministic before calling KMS `Signer`. Allocation and signing therefore split cleanly into two phases:
  1. **Inside the short DB lock (final step of `on_submit`, zero network or KMS I/O):** After ERPNext GL and Stock Ledger validation/posting succeed, take `SELECT ... FOR UPDATE` on that unit's chain head, assign the next monotonic `ICV`, read the prior link's `invoice_hash` as `PIH` (or genesis PIH for `ICV = 1`), generate `UUID`, normalize XML timestamp inputs (`IssueDate`, `IssueTime`, UTC `generated_at`), build the canonical unsigned invoice XML, compute `invoice_hash` locally, advance the chain head to `(ICV, invoice_hash)`, insert the immutable `ZATCA Submission` row with status **`PENDING_SIGN`** (persisting `uuid`, `icv`, `pih`, `invoice_hash`, canonical unsigned XML, and `generated_at`), and commit atomically with `on_submit`, releasing the DB lock immediately. If `on_submit` rolls back before commit, the chain head and `PENDING_SIGN` row roll back atomically. **Zero network, KMS, or ZATCA HTTP calls** happen inside the DB lock or `on_submit` transaction.
  2. **Outside the DB lock (signing worker & gapless KMS-failure retry):** Outside any DB lock, the signing/outbox worker claims `PENDING_SIGN` rows, calls `ADR-0038`'s `Signer` (non-exportable KMS/HSM — a network call), injects the cryptographic stamp (`UBLExtensions`, `Signature`, `QR` Tags 1–9) to produce immutable `signed_xml`, persists `signed_xml` and `SigningTime`, and transitions the row to `READY_TO_SUBMIT` (outbox) in one transaction. **KMS / `Signer` failure rule:** if `Signer` fails (timeout, KMS outage, throttling), the row **stays in `PENDING_SIGN`** with its exact allocated `ICV`, `UUID`, `PIH`, and `invoice_hash` — never skipping, deleting, or reusing that `ICV`. The worker retries signing for that exact `PENDING_SIGN` row with backoff (emitting an operator alert on repeated failure) until signing succeeds, preserving both **zero network I/O inside the DB lock** and a **strictly gapless `1..N` chain**.
- **Runtime key custody & G1 vs G3 gate separation.** `SEC-002` (G1, `ADR-0038` in PR `#128`, Proposed — **explicit precondition before `ADR-0042` moves from `Proposed` to `Accepted`**) governs G1 sandbox keys and key-custody interfaces before any sandbox CSID/key is created (`CMP-004` depends on `SEC-002`); `SEC-011` (G3) is a hard gate before any **production tenant** key or CSID is issued. At runtime, the EGS unit record in the engine holds only opaque key/CSID references (never PEM private keys, OTPs, or CSID API secrets in Frappe DocType fields or logs). Signing calls `ADR-0038`'s `Signer` (target: non-exportable `secp256k1` KMS/HSM; see dated note for the proposed pilot-only exception awaiting dual-founder sign-off) and `SecretStore` only for the duration of `sign()`, strictly outside any DB lock.
- **`Sales Invoice` vs immutable `ZATCA Submission` state machine (B2B vs B2C recovery).** Separate the posted accounting `Sales Invoice` from immutable `ZATCA Submission` attempts (each recording `uuid`, `icv`, `pih`, `invoice_hash`, unsigned canonical XML, `signed_xml`, `generated_at`, `status` (`PENDING_SIGN` -> `READY_TO_SUBMIT` -> `cleared` / `reported` / `rejected`), `zatca_warnings`):
  - **Rejected / failed-attempt chain rule:** a ZATCA `400` rejection **stays in the chain** (its `ICV`, `UUID`, and `invoice_hash` are never reused, edited, or rolled back, and the next submission's `PIH` references that rejected `invoice_hash`), and a transient KMS failure stays in `PENDING_SIGN` and retries for that exact `ICV` so no chain gap ever forms.
  - **Standard (B2B):** buyer delivery is blocked until a `ZATCA Submission` reaches `cleared` (or `reported` under HTTP `303`). On `400`, the invoice cannot be delivered; recovery creates a new rectified `ZATCA Submission` attempt (new `UUID`, `ICV`, `PIH`, `SigningTime`; and a Credit/Debit Note per accounting rules if posted monetary/tax amounts must change) without mutating the prior chain link.
  - **Simplified (B2C):** the buyer receipt with Phase 2 cryptographic QR is deliverable once signing completes (`READY_TO_SUBMIT`, `signed_xml` persisted, before ZATCA 24h reporting completes). On `400` reporting failure, the GL/stock posting and buyer receipt remain untouched, and recovery issues a new rectified `ZATCA Submission` row referencing the prior failed submission's hash as `PIH`.
- **Clearance and reporting outbox.** Once a `PENDING_SIGN` row is signed and transitions to `READY_TO_SUBMIT`, the outbox worker transmits the **exact stored `signed_xml` bytes** on every `timeout` / `429` / `5xx` retry — never re-signing an outbox item (which would change `SigningTime` and signature). Handling by status: HTTP `200` (`cleared` / `reported`); HTTP `202` (**Accepted with warnings**) is terminal accepted (persist warnings for operator review, never resubmit); HTTP `303` (**Clearance switched off**) routes the Standard invoice to the Reporting API per [E-invoicing Detailed Technical Guideline](https://zatca.gov.sa/en/E-Invoicing/Introduction/Guidelines/Documents/E-invoicing-Detailed-Technical-Guideline.pdf), p. 78 (accessed `2026-11-19`); HTTP `409` / duplicate-invoice responses trigger explicit state reconciliation rather than blind retry.
- **24-hour reporting clock & alerts.** Anchor the 24-hour Simplified reporting window to explicit UTC `generated_at` recorded at chain allocation. Both `reporting_window_hours` (`24`) and `reporting_alert_lead_hours` come from the country pack (ADR-0015), not hardcoded constants. If 24 hours elapse before acceptance, **never drop the invoice**: continue submitting late reports and emit a compliance breach event (`ERP-009`) plus operator alert.
- **All engine hooks.** Our own hooks in `apps/engine/change_engine/change_engine/compliance/` trigger chain allocation and `PENDING_SIGN` creation at the end of `on_submit` (zero network/KMS calls in the hook), block edits/cancels on issued documents (`Sales Invoice` / `ZATCA Submission`), store `signed_xml` immutably once signed outside the DB lock, and emit platform events (`ERP-009`). Rejections reach users via our domain error model (`OPR-018`, `PLT-024`) in Arabic and English (ADR-0016). Nothing touches Desk.

Reason: the evaluation found stub tests, non-transactional chain writes and Desk coupling. We take none of that.

Until both pass, say "implemented, not yet verified", never "compliant" or "certified".

### 5. Tracking upstream security and correctness fixes
- `PROVENANCE.md` and the component manifest record the pinned SHA. Vendored files are never edited in place without a line in `PROVENANCE.md` "Changed".
- The partner watches the upstream repository's releases and security advisories. At each upstream release, and at least at every gate exit while this component is live, the partner diffs the kept upstream functions between our pin and the new commit and records the result in a session log: no relevant change, take the fix, or not applicable.

## Alternatives rejected
- **Fork the whole app:** inherits Desk coupling, custom fields on core records, the non-transactional chain, keys in records and the maintenance of a large codebase with no tests.
- **Rebuild from scratch:** wastes parts that already encode ZATCA's canonicalisation, signing envelope and QR rules, and re-learns their quirks the slow way.
- **Run the upstream app as-is behind a wrapper** (the evaluation's other option): the chain and Desk problems sit inside the app and a wrapper cannot fix them.

## Consequences
- Easier: CMP-004 starts from working crypto and XML structure; state, concurrency and error handling are ours and testable.
- Harder: we own the adapted code and its divergence from upstream; upstream fixes need a manual diff each time.
- Must be done:
  - **Precondition before `ADR-0042` moves from `Proposed` to `Accepted`:** `ADR-0038` (PR `#128`, Proposed) must be merged (or its `Signer` / `SecretStore` / fallback-signer contract finalised so `ADR-0042` does not depend on an unmerged spec), Open Questions 1, 3, 4 and 5 answered, and both founders complete Tier 3 line-by-line review/sign-off.
  - Then: the vendoring import PR (partner, under CMP-004 or a new plan row if the founder prefers), then CMP-004; `SEC-002` key custody before any sandbox key and `SEC-011` (G3) before any live tenant key; engine event emitter (ERP-009). R-018 mitigation moves from "proposed" to this plan once accepted.
- CMP-033 stays `doing` until `ADR-0038` (PR `#128`) is merged and both founders accept this ADR.

## Reviewer notes
Written by the drafting agent (Claude Opus 5.5), refined after cross-model review (`2026-11-18`) and Eldon's review (`2026-11-19`). These do not change the decision above; the founder decides.

1. **The "pure core" is not pure.** At `015eaf8`, `sign_invoice_first.py` has 182 lines naming `frappe` and the XML builders take an engine `Sales Invoice` document. `digital_signature`, `certificate_hash`, `tag8_publickey` and the CSR functions look keys and certificates up from engine records by company abbreviation. "Vendor" will in practice mean "extract and adapt". The PROVENANCE "Changed" list will be long, and the Tier 3 review must cover the adapted code as if it were new.
2. **The XML builders compute tax.** `xml_tax_data.py` recomputes VAT (`net_amount * (tax_percent / 100)`, line 95; `taxable_amount * rate / 100`, lines 202, 225; and `tax_data_with_template` `545-588, 691-695, 813-856`), `create_xml_final_part.py` recomputes VAT and totals in `item_data` (`679-736`) and `item_data_with_template` (`1144-1168`), and `custom_round` (`1090-1112`) uses `ROUND_DOWN` on a third decimal of 5. All arithmetic is stripped and replaced with pre-computed engine figures checked fail-closed.
3. **The TLV encoder has a length defect for Arabic text.** `generate_tlv_xml` (`1115-1117`) pre-encodes Tag 1 (`encode("utf-8")`), so Tag 1 enters `get_tlv_for_value`'s (`954-973`) `else` branch where `bytes([len(tag_value)])` raises `ValueError` above 255 UTF-8 bytes, while any unencoded `str` tag hits character-count vs UTF-8 byte length mismatch and non-standard `0xFF` handling. Extending our UTF-8 byte-length Phase 1 encoder (`components/compliance/zatca_sa/phase1.py:371-405`, CMP-003) to Tags 6-9 avoids this completely.
4. **Key generation is fine; key storage is not.** Keep the `SECP256K1` generation and the CSR OID encoding inside `Signer`; drop the PEM-in-a-record storage (finding above) and drop `csr_configuration.py`'s `TST` defaults and `random.getrandbits(32)`.
5. **Facts confirmed vs remaining UNVERIFIED from primary ZATCA publications (Principle 10, verified `2026-11-19`):**
   - **VERIFIED** against [E-invoicing Detailed Technical Guideline](https://zatca.gov.sa/en/E-Invoicing/Introduction/Guidelines/Documents/E-invoicing-Detailed-Technical-Guideline.pdf) (accessed `2026-11-19`): Simplified (B2C) 24-hour Reporting (section 4.3.1, p. 49); rejected invoice hash remaining in the PIH chain and resubmission requiring a new unique hash, UUID, ICV and timestamp, plus non-cleared Standard (B2B) invoices not being valid tax invoices until cleared (pp. 71, 78); `secp256k1` key/CSR generation and one-time CSID onboarding (pp. 57, 79); HTTP `202` accepted-with-warnings non-resubmission (p. 79); and HTTP `303` Reporting fallback when clearance is disabled (p. 78).
