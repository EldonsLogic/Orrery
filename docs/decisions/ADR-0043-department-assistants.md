# ADR-0043: Department-scoped assistants in the Blueprint

Status: Proposed
Owner: eldon
Approved by: pending

## Context
OPR-017 and [app-screens.md](../product/app-screens.md) (department assistants) ask for one chat assistant per department with its own instructions, allowed tools, limits and memory scope, configured in the Blueprint and never exceeding the signed-in user's role and scope. The Blueprint (0.2.0, [ADR-0037](ADR-0037-manifest-risk-class-and-transition-kind.md)) has no place for this, and the contracts README requires an ADR for any contract change. Constraints: [ADR-0027](ADR-0027-human-floor-action-policy-and-agent-authority.md) (human floor), [agent-least-privilege.md](../security/agent-least-privilege.md) (SEC-020), [prompt-injection-defence.md](../security/prompt-injection-defence.md) (SEC-003) and [tool-api.md](../../contracts/tool-api.md) sections 1.1, 4 and 11.

## Decision
1. **Blueprint 0.3.0** adds an optional top-level `assistants[]` (at most 32). Each assistant has `id`, `department` (a role function: sales, purchasing, warehouse, finance, accounting, hr, operations, support), `labels`, `roles` (who may invoke it), `instructionsKey`, `tools[]` (`{tool, confirm}`), `limits` (`perCall.maxToolCalls`, `perCall.maxRows`, `perDay.maxToolCalls`, `perDay.maxWrites`, per user), `memory` (`scope`: `none`, `session` or `department`, optional `retentionDays` for department only) and `provenance`. `additionalProperties: false` everywhere; ids and tool names have patterns. Every 0.2.0 Blueprint stays valid; `meta.schemaVersion` stays `0.1.0` (Q-141).
2. **No authority of its own.** An assistant is configuration of the one chat, not an agent principal: no identity, role, scope, grant, owner or service account, and the schema has no field for one. Every call runs with the invoking user's permissions and is an **agent-class call** (Tool API section 4, 0.3.1): tool and per-transition `agent_creatable` and `approval.agent_required` apply, and approve and reject moves are refused even when the user could make them in person: `effective = user's current permissions and scope ∩ assistant tools ∩ chat mode list ∩ taint downgrade ∩ action-policy row`. Being listed in `roles` grants nothing. Scheduled or event-triggered work stays an SEC-020 agent with a grant, not an assistant.
3. **Tools.** Each tool must be in the tenant's generated tool set, `agent_creatable: true`, at most R2, and callable by at least one listed role; a tool is listed once. An R2 tool needs `confirm: true` (the user confirms over the rendered payload). An `<entity>.transition` tool must carry a `transitions` allowlist (Blueprint 0.4.0); each listed move must be agent-creatable, at most R2, callable by a listed role, and never an approve, reject or reversal move or one with its own approval rule. Never allowed: R3, R4, approve, reject, submit, cancel, amend and delete verbs, writes other than create, update and export on ledger- or stock-class entities, `approval.decide`, `blueprint.*`, the protected `update_bank_details`, `update_contact_details` and `update_access` tools, and `memory.*` tools when `memory.scope` is `none`. The verb, entity-class and transition-name refusals run even without a tool set. Tool-API rules still apply on top (ledger, tax and export calls park for human approval).
4. **Instructions are an i18n key, never inline prose.** The key (`assistants.<name>.<part>`) resolves to the platform catalog (L0) or to `i18n.labelOverrides` (tenant text, L1, 200 characters per locale). L1 text fills only the tone and terminology slot: it cannot add tools, raise limits, name roles or change approvals, because those are typed fields enforced by code (PI-RULE-1, PI-RULE-3). Draft Blueprints, and so draft instruction text, are L3 until published (AP-BPL-01).
5. **Limits** only restrict. The schema maxima are the platform caps; a plan cap may be lower; `perCall.maxToolCalls` and `perDay.maxWrites` may not exceed `perDay.maxToolCalls`. Values are placeholders (Q-156).
6. **Memory** is always keyed by tenant and never crosses tenants. `session` is the user's current thread. `department` notes are shared within one tenant and department, stored with the author's scope, filtered by the reader's scope, read back as L3, and follow section 6 of the injection design (preferences and terminology only, quarantined when written from a tainted thread).
7. **An assistant can never** change its own tools, instructions, limits or memory scope (only a published Blueprint revision can, and bpdiff classifies any `assistants` change as `access`), approve, submit an R3 or R4 action, post to the ledger, or touch bank, contact or access details.
8. **Enforcement.** Validator rule 14 (`BP-AST-001` to `BP-AST-016`, `services/blueprint/validator/rules_assistants.py`) refuses the cases above; without a supplied tool set or instruction catalog the static refusals still run and it warns that the generated-risk, agent-flag and caller checks did not. Instruction text in `i18n.labelOverrides` under `assistants.*` is classed `access` by bpdiff, like the assistant itself. The gateway re-checks every call at run time; the validator is not the guarantee.

## Alternatives rejected
- Give each assistant its own role or service account: an assistant would become broader than some of its users (ADR-0027 rejects an agent inheriting or holding wider authority); the user's own permissions are the only ceiling.
- Inline instruction prose in the Blueprint: unbounded tenant text inside the prompt with no slot limit; a key keeps it typed, translated, reviewable and short.
- Allow R3 tools with confirmation: R3 rows need human submission and step-up; a chat confirm card is not that control.
- Tenant-wide or cross-department memory: leaks records across scopes and widens the poisoning surface (T48).
- Model each assistant as an SEC-020 agent with a grant: grants, owners and expiry fit autonomous runs, not a user's interactive turn; scheduled work keeps that path.
- Reference departments as `locations` of kind `department`: most Blueprints have none, while every Blueprint has role functions, which the department views already follow.

## Consequences
Blueprint drafting can propose assistants per department; the review gate sees them as `access` changes. Callers that validate before publish must pass the generated tool set (`ValidationContext.tool_set`) so membership, risk and caller checks run (Q-157). Runtime work: the chat runtime and gateway apply the tool list, confirm flag, limits and memory scope (OPR-004, OPR-014); the platform instruction catalog is still to be written. Contract change touches auth-adjacent behaviour, so it needs both founders and a different-model security review (RULES 42). Code: `contracts/blueprint.schema.json`, `services/blueprint/validator/rules_assistants.py`, `services/blueprint/diff/bpdiff`, tests `services/blueprint/tests/test_assistants.py`.
