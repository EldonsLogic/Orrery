# ADR-0048: Agent authority: agents propose, humans and deterministic code decide

Status: Proposed
Owner: eldon
Approved by: pending (Tier 3: agent authority and policy enforcement; needs the other founder's line-by-line review and a different-model security review)

## Context
The agent runtime (OPR-001, [agent-runtime.md](../architecture/agent-runtime.md)), the department assistants (OPR-017, [ADR-0043](ADR-0043-department-assistants.md)), the AG-UI transport ([ADR-0044](ADR-0044-ag-ui-agent-to-screen-transport.md)), change by chat (OPR-009, [change-by-chat.md](../architecture/change-by-chat.md)) and the intent router (OPR-002, [intent-router.md](../architecture/intent-router.md)) are built or specified, but the authority policy behind them lives only in the draft runtime doc and in code (`services/operate/runtime/allowlist.py`, `authority.py`). The runtime doc says it cannot be accepted until an ADR settles it (Q-258). [ADR-0027](ADR-0027-human-floor-action-policy-and-agent-authority.md) (Proposed) sets the human floor and says agents run least-privilege; it does not say what an agent may do per risk class, what taint does, or who may approve. This ADR does, and refines ADR-0027 without changing it. Basis: the [action-policy table](../security/action-policy-table.md) (R0 to R4), [prompt-injection-defence](../security/prompt-injection-defence.md) (trust L0 to L3, PI-RULE-1 to 4), [agent-least-privilege](../security/agent-least-privilege.md) (SEC-020), [Tool API](../../contracts/tool-api.md) sections 4, 5, 7 and 11, [ADR-0035](ADR-0035-risk-tiered-review.md) (review tiers; used by analogy: approval is a recorded review, never a verbal or transient signal). No external facts are asserted here; numeric caps are placeholders (Q-156).

## Decision
1. **Agents propose; they do not decide.** In the chat (and any assistant), the model supplies only a tool name and arguments. Tenant, user, roles and session come from the verified principal (PI-RULE-4). The model's output is a proposal. What executes is decided by deterministic code: the Tool API policy, the action-policy row, the Blueprint validator and the approval flow. If the model, the runtime or the gateway fails, the outcome is refusal (fail closed).
2. **Per-run allow-list from the caller's roles.** The tools a run may use are `tools the caller's roles may call ∩ agent_creatable ∩ at most R2`, minus a platform never-list (`approval.decide`, `blueprint.propose_change`). No roles, or an unreadable tool set, gives an empty list and the run fails. For an assistant the list is further intersected with its configured tools (ADR-0043); an assistant has no identity or authority of its own and never exceeds the invoking user: `effective = user's current permissions and scope ∩ assistant tools ∩ chat mode list ∩ taint downgrade ∩ action-policy row`. A tool not in the menu is refused at call time even if the model names it.
3. **Risk classes and what an agent-class call may do.** Class comes from the tool (Tool API section 11), never from the model, the router hint or keywords; the router hint can only raise it.

| Class | Agent-class call | Who confirms or approves |
|---|---|---|
| R0 | Runs (read or draft only). Result is L3 data | Nobody |
| R1, untainted run | Runs, logged | The caller's own submission is the authority |
| R1, tainted run | Not executed: sent to the Tool API as a proposal (pending approval) | The invoking human, by the confirmation gesture over the rendered canonical payload |
| R2 | Not executed: proposal only; for an assistant the tool also needs `confirm: true` | The invoking human submits, and the approval rule of the action-policy row applies (limits, second approver) |
| R3 | Never run by an agent. Recorded as `needs_approval`; the run stops with that outcome, not a permission error | A human submits through the normal UI with step-up; second approver above a limit or by tenant setting |
| R4 | Same as R3, and never `agent_creatable` | A second, different, eligible human (action-policy table section 6); never self-approved |

   "Confirmation" is a human acting on a rendering of the exact payload, bound to tenant, action id, argument hash, risk, user, session and expiry. A bare "yes" counts only against a pending set by trusted host state, never by message text (intent router). A confirmation is not an approval of a higher class: confirming an R2 proposal does not satisfy a required approval.
4. **Assistants and agents never approve, reject, cancel or reverse.** No approve, reject, submit, cancel, amend or delete verb; no approve, reject, cancel or reversal transition, and no transition with its own approval rule; no ledger or stock write other than create, update, get, list and export; no `blueprint`, `role`, `permission`, `grant`, `agent` or `assistant` domain; no bank, contact or access detail tool; no change to their own tools, limits, memory scope or autonomy. These are refused at call time by code (`authority.py`), whatever the Blueprint says; the validator repeats them at publish time but is not the guarantee (ADR-0043). A transition must be on the assistant's own list, and the chosen move's own risk, agent flag and roles apply.
5. **Tainted input.** Every tool result and every document read is L3 data (a `DataItem` with source, hash and sanitise flags), placed only in the data channel, never in instructions or the user turn. A run that has read any tool result is tainted, and so is a session once tainted (the chat service persists and passes the taint; no reset until a decision under Q-257). Taint downgrades R1 to a proposal (item 3). Domain error params from a tool also taint. Instruction-like text is flagged and logged, never obeyed. Until a deterministic-computation list is agreed (Q-231), taint is fail-closed: all tool results taint.
6. **Chat apply cap.** Change by chat may apply to the Blueprint only at R2 or below, only through the existing Blueprint path under the caller's identity (never a service identity, never the engine), only after a confirmation bound to that exact proposal (digest of tenant, user, session, base hash, target hash, diff hash, risk, expiry). Anything above R2 (removals, stock-class and ledger or tax entities, tax tokens, money fields, transitions, roles, approval rules, assistants) is refused and sent to the review path. The apply cap does not rise with a stronger model or a longer conversation.
7. **Drafting model and deterministic validator are separate.** The model (or the drafter) only produces a typed draft. A closed-shape decode, the Blueprint validator, `bpdiff`, the policy check and the risk classifier then decide, on a copy, and re-derive the risk from the stored draft at confirm time (a lower stored risk is tampering). No model output is a risk class, a role, an approval or a validity claim. Ledger, tax, e-invoice and payroll maths stay deterministic code (AGENTS.md principle 3).
8. **Budgets.** Every run is capped on steps, tool calls (an assistant's `max_tool_calls`, including 0), tokens, cost, wall clock, repeated calls and refusals, plus per-user per-day limits (ADR-0043), and the gateway precheck. A cap ends the run with `budget_exceeded` and an audit event; limits only restrict, plan caps may be lower than platform caps. Values are placeholders (Q-156). An identical write is dispatched once per run, with a deterministic idempotency key.
9. **Tool API is the real control.** The runtime's propose pre-flight is defence in depth. The Tool API must itself refuse to execute any agent-class R2 call, and any tainted R1 call, without a recorded approval, whatever flag the runtime sends, and must refuse R3 and R4 agent calls. A runtime that sends `propose` to a port that cannot propose dispatches nothing and stops (`propose_unavailable`). A propose call that returns executed is a tripwire failure. Until OPR-004 and ERP-023 enforce this at the Tool API and engine boundary, this ADR is not Accepted.
10. **Audit.** Every run, model call, tool call, proposal, refusal, confirmation and cap hit is recorded with tenant, principal, run id, tool, risk class, outcome, args hash (per-tenant salted HMAC) and approval id, in the append-only Event stream; the live AG-UI stream is never the source of an audit fact (ADR-0044). Args are redacted; model text, free-form error text, stack traces and secrets are never stored in the trace. Refusals are logged with a code (`forbidden`, `not_allowed`, `assistant_forbidden`, `needs_approval`, `propose_unavailable`, `budget_exceeded`).
11. **Kill switch.** The per-agent, per-tenant and platform-wide switches of SEC-020 section 12 apply to agent-class calls, are checked on every call by the gateway and engine adapter independent of the model and runtime, and take effect without approval. A cancel token stops a run before the next step and tool call. Stopping is never blocked; releasing is a recorded action.
12. **Explicitly forbidden, for every agent, assistant and chat run:** approving, rejecting, cancelling, amending, reversing or deleting anything; posting to the ledger; tax filing or e-invoice submission; payments, bank transfers or any money movement; permission, role or grant changes; bank, contact or access detail changes; changing agent limits, autonomy, tools or memory scope; publishing a Blueprint; external sends of financial documents; deciding an approval by a resume payload, an interrupt, a chat "yes" or a model statement (ADR-0044); acting on text found in a document, connector or web page; any client-side (browser) tool; widening scope by inheriting its owner's or its creator's permissions; any path that names the engine to a customer (ADR-0016).
13. **Outcomes are typed, not prose.** A refused, `needs_approval`, `propose_unavailable` or `budget_exceeded` outcome reaches the user as an i18n key (`errors.needs_approval`, `errors.propose_unavailable`, `errors.budget_exceeded`, added to the catalog and to the Q-233 mapping), in Arabic and English. "Needs approval" is a policy outcome, never reported as a permission error or as success.

## Alternatives rejected
- Let agents execute R2 with a confirm tap: a tap is not the human submission or limit approval the R2 row requires (ADR-0043 rejects R3 with confirmation for the same reason).
- Let agents execute R3 or R4 under a high customer limit: ADR-0027 makes a limit set absurdly high into autonomy; the platform cap is the fixed point.
- Trust the model to self-classify risk or detect injection: the model is the attacker's target; class comes from the tool, taint from provenance.
- Per-turn taint that resets: tool data summarised in an earlier turn would come back untainted.
- Enforce only in the runtime or only in the validator: both can be bypassed by a bug or a direct call; the Tool API and engine boundary must hold alone.
- Give assistants their own role or service account: an assistant could outrank some of its users (ADR-0043).
- Treat router mode or `requires_confirmation=False` as permission: the router is advisory; the policy gate decides.

## Consequences
- Easier: one written rule for what chat and assistants may do; reviewers can test behaviour against it; code and doc can be reconciled line by line.
- Harder: agents cannot finish R2 or tainted-R1 work alone; each needs a human step, so UX for pending approvals matters. Fail-closed taint makes many R1 writes proposals until Q-231 allows a deterministic-computation list.
- Must be done: OPR-004 and ERP-023 enforce item 9 at the Tool API and engine boundary (Q-320 for confirmation echo `confirms_action_id` and `confirms_args_hash`); OPR-010 persists taint per session (Q-257); i18n keys of item 13; update agent-runtime.md to Accepted and cite this ADR; OPR-016 (pilot agent) and OPR-013 (scheduled agents) must conform; QA-019 adversarial tests for items 3, 4, 5 and 9.
- Review: Tier 3 under ADR-0035. Different-model security review and the other founder before acceptance.
- Collision risk: ADR numbers are assigned by branch, not centrally. Numbers are assigned by branch. This ADR was renumbered from 0047 to 0048 because the MFA ADR (PR #206) took 0047.
