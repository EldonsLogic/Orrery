# ADR-0051: Adapter-owned engine roles and workflow states carry a reserved prefix; a name the engine already holds under another spelling is refused; role.upsert writes the mapped grants

Status: Proposed
Owner: partner
Approved by: pending (security review by a different model, then Eldon line by line; RULES 42 because this touches authorisation)

Plan IDs: SEC-022 (namespacing and collision refusal), BPL-032 (mapped permission rules). Refines [ADR-0039](ADR-0039-role-and-permission-mapping.md) (Proposed) items 1 to 3 for the first implementation; detail in [../architecture/role-and-permission-mapping.md](../architecture/role-and-permission-mapping.md). Internal document: it names the engine (ADR-0016).

## Context
- The BPL-027 bench run of the trading fixture on the real adapter found two security gaps (bench test_04b and test_06, both `expectedFailure` tripwires):
  - **Name collision.** The adapter wrote roles and workflow states under the raw Blueprint id. The engine stores names in MariaDB with a case-insensitive collation (`utf8mb4_unicode_ci`, which also ignores trailing spaces), so Blueprint role `auditor` resolved to the built-in `Auditor` and state `approved` to the built-in `Approved`. Ids such as `administrator`, `all`, `guest` or `system_manager` would land on built-in roles too. Holders of the Blueprint role would then hold a built-in role with permissions the Blueprint never granted: privilege escalation, and a breach of the mapping-contract rule that roles map to adapter-owned roles, never built-in ones (contracts/engine-mapping.md).
  - **No grants.** `role.upsert` created the role only. Of 161 mapped action grants in the fixture, 160 were missing and one matched only through a built-in role; hidden and read-only fields were not applied. Blueprint permissions were not enforced in the engine at all.
- `sync_members` also created any role id it was given that did not exist yet, so an assignment could invent a role.
- ADR-0039 item 1 already asks for "one managed engine role per Blueprint role, named deterministically from the role id with a reserved prefix"; it does not fix the prefix, the collision rule or what happens before its bench gates pass.

## Decision
1. **Names.** The managed engine name of a Blueprint role or workflow state is `bp-` followed by the Blueprint id (`auditor` gives `bp-auditor`, `approved` gives `bp-approved`). Only a value matching the Blueprint id grammar `^[a-z][a-z0-9_]{1,63}$` (contracts/blueprint.schema.json) is named; anything else refuses the step with `unsupported_value_type`. The `-` is outside that grammar, so no raw Blueprint id can equal a managed name, and no shipped engine role or state starts with `bp-` (UNVERIFIED for every installable app; the collision rule below covers it either way). The prefix is reserved for the adapter: a record under it that the adapter did not write is drift (ADR-0039 item 9). The prefix is the adapter-managed mark for now; a registry of managed names in the durable adapter state (ADR-0041) is a follow-up.
2. **Collision rule (fail closed, before any write).** The adapter looks a managed name up through the engine's own name comparison. If the engine returns a record whose stored name is not exactly the managed name (another case, a trailing space, any collation fold), that record is not the adapter's and the step is refused with `protected_subject`, side-effect free. A failed lookup raises; it is never read as "no collision". This applies to:
   - `role.upsert` and `role.disable` (the role itself);
   - `workflow.upsert`: every state, every transition endpoint, and every `allowedRoles` entry, all checked before the document type, action labels or states are written; a transition with no `allowedRoles` (the Blueprint requires at least one) is refused (`unsupported_value_type`), never given to a default role; the workflow deployment engine refuses a colliding state again before its lock and journal (`WORKFLOW_STATE_NAME_COLLISION`), as defence in depth, and a failed or missing state lookup there raises;
   - `report.upsert`: every `visibleToRoles` entry, checked before the document type is created; an empty or missing `visibleToRoles` is refused (`unsupported_value_type`), never shown to `All`;
   - `sync_members`: every role id must be an enabled role held under exactly its managed name, else `unknown_role` and no member changes (contract 5.9). `sync_members` never creates a role.
   - `role.upsert`: the step's subject id, the last pointer segment (`/roles/<id>`) and the definition's `id` must be the same, else `definition_conflict`; the gated subject is the role that is written.
3. **Grants (BPL-032).** `role.upsert` reconciles the managed role's custom permission rules (`Custom DocPerm`) through the engine API the adapter already uses, by ADR-0039 section 2, narrowed until the ADR-0039 bench gates pass. Every narrowing withholds; nothing is widened or mapped to a "nearest" permission.
   - **Actions.** `read` is required, else nothing is granted on that entity. `create`, `update` (engine `write`), `delete` and `export` as listed. `submit` only on a submittable document type and only with `write`; `cancel` only with `submit`; `amend` only with `create` and `cancel`. `approve` is no document flag (it is the role on workflow transitions). `report`, `print`, `share`, `import`, `email` and `set_user_permissions` are always 0 (RM-017, RM-018).
   - **Masked entities.** A grant with `hiddenFields` or `readOnlyFields` gets no `create` or `write` (RM-018, until DENY-23 and DENY-38 pass). Read-only fields therefore need no level of their own.
   - **Scopes.** `company`: no restriction. `own_records`: the owner-only flag (`if_owner`) on every rule of the role. `branch`, `warehouse`, `department`: the role is created with no rules until record-level user permissions on holders exist (ADR-0039 item 4); holders get nothing from it, never everything. `assigned_records`: refused (`unsupported_value_type`).
   - **Grant targets are an allowlist (review round 1, updated round 2 and follow-ups).** A grant may target only (a) an entity in the adapter's reviewed mapping (`ENTITY_TO_DOCTYPE`, which includes `delivery_note` / `delivery_note_line` from `contracts/examples/engine-mapping-golden-path.json`; the read-route allowlist `route_guard.RESOURCE_ALLOWLIST` keeps its own explicit reviewed subset `Customer`, `Item`, `Sales Order` and `Sales Invoice` so adding grant entities does not open new read routes) that is not protected, or (b) a document type the adapter created itself for an unmapped Blueprint entity: custom (`custom=1`), in the adapter's module (`Custom`), stored under exactly the derived name. Everything else is refused with `protected_subject`, in the plan stage (the entity must be in the reviewed mapping, or be an unmapped entity of this Blueprint whose derived document type is checked by `can_grant_own_doctype`, which requires an existing record to have `custom=1`, module `Custom` and exactly the derived name (a name no record holds yet is allowed only when no table exists for it either, `frappe_backend.py` `can_grant_own_doctype`; a name held by a built-in, any other record or an existing table is refused), and defaults to `False` when an engine backend lacks that checker; the in-memory adapter has no engine and allows an own entity of the same Blueprint that the other checks let through). Accepted residual of the in-memory adapter: it cannot see engine built-ins, so an own entity whose derived name is a built-in document type that is neither protected nor in the reviewed mapping (for example `server_script`, `has_role`, `payment_entry`) plans `gated` there, where the engine path refuses it (`protected_subject`). No engine is present, every engine path (the backend plan check and the apply stage) checks again, and production never builds an adapter without a backend; the in-memory adapter is a test double. The protected-entity check is case-insensitive (`gl_entry` derives `Gl Entry`, which is `GL Entry`; it is protected, as is `docperm` for `DocPerm`); that fix blocks none of those three names, since `Server Script`, `Has Role` and `Payment Entry` are not in the locked set; the engine path refuses them at plan time, because the document type is not the adapter's own (b), and again at apply on the engine, where the document type record must match (b). The protected check compares a normalised key (stripped, runs of whitespace and underscores collapsed, case folded) and reuses the shared Tier 0 locked-DocType helper `safety_guardrails.is_locked_doctype` (which applies NFKC normalisation, drops Unicode format `Cf` characters, fails closed on non-strings, any Unicode control character `Cc`, and any remaining non-ASCII letter or combining mark, and compares whitespace-collapsed, casefolded names; also used by `safety_guardrails.py`, `workflow_engine.py` and `report_engine.py` on the direct apply path, follow-up 4; live MariaDB `utf8mb4_unicode_ci` collation behaviour for Unicode variants remains UNVERIFIED); the plan stage refuses an entity id outside the Blueprint id grammar `^[a-z][a-z0-9_]{1,63}$` (`unsupported_value_type`) or a protected entity (`protected_subject`) on both adapters before any write across: `/entities/<id>` pointer segments (entity/field/relation steps whose pointer is not under `/entities/<id>` are refused with `unsupported_value_type`), `entity.add` subject ids (which must also equal the pointer segment, else `definition_conflict`) and inline `definition.fields[]` / `definition.relations[]` targets, `field.*` and `relation.*` element steps (exact `/entities/<id>/fields/<fid>` or `/entities/<id>/relations/<rid>` pointer, exactly one parent is required with extra parents refused as `unsupported_value_type`, `subject.parents[0].id` must equal the entity pointer segment, `subject.id` must equal the last pointer segment, and on `field.add` / `relation.add`, `params.definition.id` must equal both, else `definition_conflict`), `field.reorder` (exempt from the last-segment rule because it uses the collection pointer `/entities/<id>/fields`; requires exact `/entities/<id>/fields` pointer with `bpdiff`'s entity subject `kind="entity"`, `id=<id>`, `parents=[]`, validating entity/parent grammar and protection first, else `definition_conflict`; `relation.reorder` does not exist in the contract), `definition.target` on link `field.add` and `relation.*` steps, `/target` on `field.set_property` / `relation.set_property` (adapter config only; the Frappe backend does not map `/target`), `/options` on `relation.set_property` (always refused) and on `field.set_property` (refused unless the field exists in site config with a known non-link Blueprint type and has no `/type` change recorded in the current artifact or any earlier applied artifact; `protected_subject` when the offered value names a protected/locked target, else `unsupported_value_type`; because `frappe_backend.py` ignores `/type`, any recorded `/type` change permanently disqualifies the field from the non-link proof, while unchanged non-link fields such as `select` may still set `/options`), `workflow.upsert` and `report.upsert` `definition.entity` (required on workflows, optional on reports per the Blueprint schema), and `role.upsert` grant targets (follow-ups 3 and 4). Direct-path caveat: on the direct apply path (`safety_guardrails.validate_mutation_safety` for `add_custom_fields` and `property_setter_engine.execute_property_setter_deployment` for `options` on Link, Table, or unknown-type fields), the shared helper `safety_guardrails.is_restricted_link_doctype` blocks only the three ledger/audit DocTypes (`GL Entry`, `Payment Ledger Entry`, `Change Engine Audit Log`) using the same NFKC/`Cf`/`Cc`/non-ASCII/whitespace/casefold rules; by founder decision on PR #262 (2026-11-22), it stays intentionally scoped to those three types rather than the broader `ZONE_2_LOCKED_DOCTYPES` set (so ordinary links such as `User` keep working while the plan path stays stricter), and does not enforce Blueprint id grammar or an allowlist unless `allowed_link_doctypes` is passed. This covers every engine document type outside the mapping: for example Server Script, User Permission, Property Setter, Custom Field, Role Profile, Has Role, Webhook, File, Data Import, Payment Entry. It also covers the engine's own business document types that are not reviewed yet: on a real site the trading fixture's Supplier, Price List, Purchase Order, Purchase Receipt and Purchase Invoice grants are refused at plan time, so its roles do not apply until those are added to the reviewed mapping (`BPL-034`, Eldon's lane). A custom document type made by hand in the `Custom` module is taken as the adapter's, the same accepted residual as a hand-made `bp-` role, until the managed-name registry exists.
   - **Refusals before any write.** A protected entity (ledger, tax, audit, security, identity) or one outside the allowlist gives `protected_subject`; a reviewed entity with no engine table gives `subject_missing`; two grants on one document type give `definition_conflict`.
   - **Unresolved hidden field.** If a hidden field is not on the engine document type under the adapter's field name, the whole grant on that entity is withheld (the field cannot be hidden, so the entity is not opened). ADR-0039 DENY-07 asks for a plan-time rejection; that needs the mapping at plan and is a follow-up.
   - **Field levels.** On each document type, hidden fields are grouped by the set of managed reading roles that hide them. A group keeps the level its fields already hold, else takes the lowest free level from 1 to 9. A level used by any rule of a role the adapter does not own, or by a field the adapter did not place, is never used or granted. A field the adapter placed is a `custom_` field it moved with a `permlevel` property setter; any other field found on a level the adapter owns (added there by hand or by an app) is never adopted or moved: grant and upsert paths refuse with `protected_subject` before any write (drift; review round 1), while `role.disable` revocation still clears the role's own rules and disables the role without touching the foreign field (review round 2). A `custom_` field moved by hand with a `permlevel` property setter is taken as placed, an accepted residual until the managed-name registry exists. More groups than levels gives `limit_exceeded` (`limit: permission_levels`) before any write. Each managed reading role gets a rule on each used level: `read` unless it hides that group, `write` only if it has `write` at level 0, and its `if_owner`. Other managed roles' visibility is read back from their rules, so the layout does not depend on the order roles are applied in.
   - **Built-in rules kept.** When the first custom rule is written on a document type the engine stops reading its standard rules, so the adapter first copies them to custom rules with the engine's own `setup_custom_perms`. Built-in roles keep exactly what they had; the adapter never edits their rules (RM-004).
   - **Idempotent and reversible.** A second `role.upsert` with the same definition writes nothing. A grant the new definition drops is zeroed (the row is kept, not deleted). `role.disable` zeroes every rule of the role and keeps the record (RM-008); a later `role.upsert` re-enables and restores it. The document type cache is cleared after each change.
4. **Out of scope here, still required by ADR-0039:** the drift fingerprint (item 9), user-permission scoping (item 4), per-user permission cache clearing and the apply, sync and verify fence (item 8), journaled compensation of rule changes (rollback relies on the inverse artifact's `role.upsert`), agent principals (item 10). `role.upsert` and `role.disable` stay `gated` (every plan that holds one needs gate approval). Pre-existing behaviour kept and flagged: a workflow state with no outgoing transition (a final state) is editable only by the built-in `System Manager` (`allow_edit`); it grants a Blueprint role nothing and is listed for the ADR-0039 implementation. The earlier fallbacks of a transition without `allowedRoles` to `System Manager` and of a report without `visibleToRoles` to `All` are removed: both are refused (review round 1).

6. **Existing sites (migration).** No tenant site exists outside throwaway bench and dev sites (no pilot, no production). Nothing is migrated: a site provisioned before this change keeps raw-named roles and workflow states, an old `role.disable` of a raw id is not undone, and `sync_members` returns `unknown_role` until the role is upserted again. Such a site is re-provisioned, not upgraded. A migration step is required before the first site that must survive an adapter upgrade exists.
7. **Step pointers name a known root (review follow-up 5).** `_judge` refuses at plan time, with `unsupported_value_type`, any step whose pointer has no segments (`""`, `/`), has an empty segment (`//`, `/locations/`), or whose first segment is not one of `ALLOWED_POINTER_ROOTS` (`adapter/engine.py`): the sections `components`, `locations`, `entities`, `roles`, `workflows`, `approvals`, `reports` (the values of `SECTION_OF`, the sections the step kinds write) and the settings roots `company`, `compliance`, `i18n`. Every other root is refused, including any root starting with `_` (so the adapter's own `_typeChangedPointers` record in `site.config` is never a step target, with or without a recorded `/type` change), `settings`, and the Blueprint sections no step kind writes (`branding`, `integrations`, `assistants`, `meta`). `_judge` also refuses, with the same reason code and independent of schema validation (the contract pattern is not enforced when `jsonschema` is missing), any pointer that does not start with `/`, and any pointer with fewer segments than its kind needs (`min_pointer_segments`): `settings.set` 1 (`/company`, `/compliance`, `/i18n`, nested paths longer); `field.reorder` 3 (`/entities/<id>/fields`); `option.reorder` 5 (`/entities/<id>/fields/<id>/options`); `option.add` and `option.quarantine` 6; `field.*` and `relation.*` elements 4; every other kind 2 (`/<section>/<id>`), so `location.upsert /locations`, `location.upsert /company`, `entity.quarantine /entities` and `role.disable /roles` are refused at plan time. `field.*` and `relation.*` steps keep their existing exact-length check, which answers `definition_conflict` (and `unsupported_value_type` below `/entities/<id>`). The segment counts are minimums for the shape of the pointer; element existence stays with the later checks. The root must also be the root its kind belongs to (review follow-up 6, `KIND_ROOTS` in `adapter/engine.py`, derived from `STEP_KINDS`, `SECTION_OF` and `SETTINGS`): `settings.set` only `/company`, `/compliance` or `/i18n`; `component.*` only `/components`; `location.*` only `/locations`; `entity.*`, `field.*`, `relation.*` and `option.*` only `/entities`; `role.*` only `/roles`; `workflow.*` only `/workflows`; `approval.*` only `/approvals`; `report.*` only `/reports`. A mismatch (`location.upsert /roles/x`, `location.upsert /company/x`, `settings.set /entities`) is refused with `unsupported_value_type`. A kind with no entry, as for the unsupported `binding.*` kinds, has no root and is refused before this check is reached. Tests: `tests/test_sec_022_review_followups_6.py`. The refusal runs before any lookup or write on both the in-memory and the engine-backed adapter, so nothing is written and the site never enters `recovery_required` for it. Tests: `tests/test_sec_022_review_followups_5.py`.
8. **`entity.*` steps address the entity, and a field's type changes only through `/type` (review follow-up 7, Eldon's review of #274, Medium 1).** Review found that `entity.set_property` could change a field's type in the config without the change entering the `/type` history (`_typeChangedPointers`, item 3), so the `/options` link-target proof for a later `field.set_property` could be defeated: with pointer `/entities/customer/fields/ref_link` and property `/type` (a gated step the history missed), or with pointer `/entities/customer` and property `/fields` (planned `auto_approved`, no gate). `entity.add`, `entity.set_property` and `entity.quarantine` also accepted a pointer below the entity, so `entity.quarantine` on a field pointer removed the field and (by reading `_exec`, not run) `entity.add` below `/entities/<id>/fields` would append an element to a field list. `_judge` (`adapter/engine.py`) now refuses at plan time, with `unsupported_value_type`, before any lookup or write and on both adapters:
   - an `entity.*` step whose pointer is not exactly `/entities/<id>` (two segments);
   - an `entity.set_property` whose `params.property` is not a well-formed pointer (not a string, no leading `/`, or an empty segment), or whose first segment is `id`, `fields` or `relations` (`ENTITY_STRUCTURAL_PROPERTIES`), so it also refuses `/fields/ref_link/type`. Entity-level properties such as `/labels`, `/pluralLabels`, `/kind`, `/numbering`, `/workflow`, `/components` and their nested paths still plan; a deny list, not an allow list, so no property that planned before and does not touch the element lists is newly refused;
   - a step of a kind that carries `params.property` (`settings.set`, `component.configure`, `entity.set_property`, `field.set_property`, `relation.set_property`; `PROPERTY_KINDS`) whose property is not a well-formed pointer: not a string, no leading `/`, or an empty segment. `_segs` drops any text before the first `/`, so without this, and with schema validation skipped, `x/type` wrote `type` on the field with no gate and no history entry, and `x/options` and `x/target` skipped their exact-spelling checks (found by the cross-model review of #280);
   - a `field.set_property` that reaches `type`, `options` or `target`, or a `relation.set_property` that reaches `options` or `target`, by any spelling other than exactly `/type`, `/options` or `/target` (`/type/x`, `/options/0`, `/target/x`; `EXACT_ELEMENT_PROPERTIES`). Exactly `/type` is still `gated` (`storage_not_additive`) and still recorded in `_typeChangedPointers` on apply, and exactly `/options` and `/target` keep their target checks.
   With these, `field.set_property /type` is the only step that can change a field's type in the config: `field.add` and `relation.add` at an existing element are `subject_exists`, a retained definition is only restored when equal, and `entity.add`, `entity.quarantine` and `entity.set_property` can no longer reach a field. The contract schema already refuses a malformed `property` (pattern `^(/[^/]+)+$`) and a non-string; `_judge` checks it independently, because schema validation is skipped when `jsonschema` is missing (Eldon's Low 3, still open), and a non-string `property` no longer raises on the semantic-property lookup. Residual, not done here: where an engine backend exists, the field type for the `/options` check is still read from the site config; Eldon suggests reading it from the engine. ## Alternatives rejected
- **Keep raw ids and only refuse collisions:** a Blueprint could never have an `auditor` or `approved`, and every future built-in name would break existing Blueprints.
- **A prefix inside the id grammar (`bp_`) or a title-case rename:** a raw Blueprint id could then equal a managed name, or a built-in.
- **A hash or opaque name:** not readable by support staff in the engine desk and not reversible to the Blueprint id.
- **A tenant-specific prefix:** one site per tenant (ADR-0006) already separates tenants; it adds nothing.
- **Grant the full ADR-0039 table now:** report, print, masked create and write, and location scopes would widen access before the bench denied cases prove the engine enforces them.

## Consequences
- Easier: test_04b and test_06 assert managed names and the exact grant set; a Blueprint can use any id; built-in roles and states are never reused or edited.
- Harder: location-scoped roles grant nothing in the engine until user-permission scoping lands; masked entities are read-only in the engine; customer-facing errors must keep stripping managed names (RM-022, DENY-46).
- Accepted residual (child rows through read routes): a single-record `GET /api/resource/<DocType>/<name>` on an allowlisted parent DocType (such as `Sales Order` or `Sales Invoice`, or `Delivery Note` if ever added to the read routes) returns the parent record together with its embedded child-table rows (such as line items and tax rows), even though child DocTypes themselves are excluded from direct `/api/resource/<Child DocType>` queries. List routes can also return child rows through `fields=[...]` query parameters, which the guard does not filter. UNVERIFIED on the pinned bench whether list routes return child rows that way.
- Done: the live BPL-027 bench run of the trading fixture class (test_04b, test_05, test_06), recorded in `docs/log/2026-11-21-partner-antigravity-sec-022-review-followups.md` (PR #252).
- Must be done: security review by a different model and Eldon's line-by-line review (Tier 3); the follow-ups in item 4.
