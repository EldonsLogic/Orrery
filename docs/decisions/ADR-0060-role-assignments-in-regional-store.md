## Decision
1. **Location.** The authoritative record of which member holds which Blueprint role in a tenant lives in a regional assignment store outside the tenant's engine site, run by the platform in the tenant's region (customer data stays in-country, ADR-0006). The engine site holds only the copy that `sync_members` writes onto shadow users.
2. **Unchanged from item 9.** The Blueprint defines roles. Assignments are written only by the membership screens or an approved chat action by a role with invite permission. The gateway reads assignments per request from this store. The shadow engine user is re-synced on every assignment change, not only on apply. A failed lookup denies (ADR-0007 item 2, ADR-0039 item 7).
3. **Tool API reading.** Tool API section 4 step 2 ("Load the caller's roles for that tenant from identity", `contracts/tool-api.md` line 100) is read as "from the regional assignment store". This ADR does not edit the contract; the wording is fixed in the next Tool API ADR, as item 9 already required; plan row GOV-065 tracks it.
4. **PR #129 items confirmed.** The ALP section 3.1, ALP-001 and OQ-2 text in point 4 of Context, and the apply/sync boundary in ADR-0039 item 8, are confirmed as the founders' position. Contract changes they need (`sync_members` / `sync_principals`, `engine.permission_drift`) still need their own contract ADRs before implementation (ADR-0039 line 56 and line 71). This item records a confirmed position only; it accepts no part of ADR-0039, which stays Proposed.
5. **Not decided here.** The store's technology, schema and deployment; how it relates to the central identity store across four markets (Q-14 stays open); whether ADR-0039 and ADR-0040 are accepted (they stay Proposed and follow their own review).

### Security conditions (GOV-066)
From [adr-0060-security-review.md](../security/adr-0060-security-review.md). They bind the store's design ADR and every implementation. Where an item is stricter than item 2, the item here wins.

6. **Writers (H1, L3).** One assignment-write service is the only principal that can change the store. It accepts a change only as the execution of an approved `AP-PERM-01` request ([action-policy-table.md](../security/action-policy-table.md)): Owner initiates, a second different Owner or admin approves, never self-targeted, payload bound by hash. "A role with invite permission" in item 2 is not enough on its own. Agent and model principals are refused as actor; member, role and tenant come from the approved payload, never from model output at execution time. One named exception: provisioning writes the first owner assignment of a new tenant, once, from the verified signup identity, audited. The provisioning workflow, staff tooling and database credentials used for other control-plane data (`S22`) give no write access to assignments. The store rejects a role id that is not active in the tenant's applied Blueprint revision and any `scope_conflict` (ADR-0039 item 4) before it stores anything.
7. **Per-tenant keying and isolation (H2).** Every record is keyed by the platform-generated `tenantId`. Every read takes the tenant only from the verified token (ADR-0007 item 3), never from a URL, body or header. The store itself enforces the tenant boundary (per-tenant partition or row-level policy bound to the caller's tenant context), not application code alone. Records are encrypted under the tenant's own envelope key ([hosting-rules.md](../security/hosting-rules.md)). Cache and idempotency keys include the tenant. Cross-tenant read and write tests join SEC-004. This is how "authorisation stays in the tenant" (ADR-0007 item 2) is read from now on: per-tenant data in a shared store, isolated by the store.
8. **`syncVersion` integrity (H3).** The store allocates the version, per tenant, in the same transaction as the write it describes. A version is never reused and never chosen by a caller. Each snapshot handed to `sync_members` is bound to its `tenantId`, `syncVersion` and content hash by a signature or MAC that the receiving side verifies; a snapshot for another tenant or with a failed check is refused and nothing changes. After a restore of the store from backup, the tenant's assignments are not authoritative: its calls are denied until a human-reviewed reconciliation finishes and versions resume above the highest ever issued. After a restore of a tenant site, the site is fenced until a full sync at a fresh version and the full drift check pass.
9. **Deny on outage (M1).** Unreachable, timed out, partial, malformed, or failing the tenant or integrity check: each one denies the call. An empty role set also denies. There is no fallback to the engine copy, to a cached set or to a default role, and no switch that enables one. Revoking access must not depend on the store: membership removal, suspension and the session-version bump in identity (ADR-0007 items 10 and 13) keep working while the store is down. The store has its own uptime target and runbook before it serves a live tenant.
10. **No stale reads (M2).** The gateway reads the store on every request, and again when an approved action executes. No role set is cached until a later ADR sets a maximum age (ADR-0039 open decision D-2); until then the maximum age is 0. A read that may lag a committed write (for example an asynchronous replica) counts as a cache and is not allowed for authorisation reads.
11. **Drift: the store wins (M3).** The engine copy is never used to change or repair the store. A narrowing change (role removed, member disabled) takes effect at the gateway as soon as it commits, and the sync to the engine starts immediately (ADR-0007 item 9 wording restored). If that sync fails, the affected principal stays denied at the gateway and the mismatch is drift: alert, remove the extra engine access first, and fence the tenant if it cannot be removed (ADR-0039 items 7 and 9 once accepted). A widening change is not usable until its sync is verified.
12. **Audit (M4).** Every assignment write, refused write and restore reconciliation writes an append-only, tenant-visible audit record in the tenant's country: actor, approver, target member reference, roles and scopes before and after, payload hash, `syncVersion`, time. If the audit write fails, the assignment write fails. The store keeps history so the assignment set at any issued `syncVersion` can be rebuilt. Audit integrity follows T56 (hash-chained, exported off-box).
13. **Staff and break-glass (M5).** No staff, support or break-glass path writes assignments. Support access is a separate expiring grant (ADR-0007 item 7, PLT-019), never a member role row. Any direct change to the store's data outside the write service must be detectable (history hash chain checked by the drift check) and is treated as a security incident with tenant notification.
14. **Residency and lifecycle (M6, M7).** "Regional" in item 1 means in the tenant's country, with the same placement as the tenant site, including backups, replicas and logs (ADR-0006). A market with no in-country location for the store is not served until a founder decision and counsel's advice are recorded; the legal position per market is UNVERIFIED. The store holds opaque per-tenant member references, not global person ids, emails or phone numbers. Records of different countries are never replicated or joined across countries. Removing a member deletes that member's assignment records; deleting a tenant deletes all of them (to be added to the deprovisioning steps with ADR-0040); only the audit trail stays, under [data-retention.md](../security/data-retention.md).
15. **Scope and order (L1, L2, L4).** This ADR moves member-to-role assignments only. Agent grants and support principals may be kept in the same store only under these same conditions and their own writer rules (agent-least-privilege.md, PLT-019). No code reads roles from, or writes assignments to, the store before the Tool API ADR (GOV-065) and the store's design ADR are accepted, and that design ADR has its own security review showing how items 6 to 14 are met. Until the store exists no real assignment is stored anywhere.

## Alternatives rejected
- **Keep assignments in the tenant site (ADR-0007 item 9 as written).** The drift check would compare the engine with data in the same site, so a compromise or bug in the site could rewrite both sides (ADR-0039 item 7).
- **Keep them in the central identity store.** ADR-0007 item 1 keeps that store free of tenant authorisation data, and its location across markets is still open (Q-14).

## Consequences
- Easier: drift baselines are independent of the engine site; ERP-008 and PLT-003 can implement the external store once their ADRs are accepted and reviewed.
- Harder: one more regional service on the authorisation path; its outage must deny, not fall back (item 9). The store is a shared, high-value target for every tenant in a country; items 6 to 13 narrow that risk and do not remove it.
- Done: the security review by a different model (GOV-066, RULES 42), recorded in [adr-0060-security-review.md](../security/adr-0060-security-review.md); Q-292 is marked applied.
- Must be done: the store's design ADR with its own security review against items 6 to 14, before any implementation; the Tool API ADR fixing section 4 step 2 wording (GOV-065); contract ADRs for the `sync_members` extension (including the snapshot binding in item 8); the deprovisioning step for assignment records (item 14).
- No contract file changes in this ADR.

## Supersedes
[ADR-0007](ADR-0007-identity.md) item 9 only (line 26), "Where the person-to-role assignment lives": the location "in the tenant's site" is replaced by the regional assignment store above. Items 1 to 8 and 10 to 13 of ADR-0007 stand unchanged. Effective now that this ADR is Accepted.
