# ADR-0068: A signed, single-use DDL-gate grant lets the guarded field path add a unique or index constraint to an adapter-owned custom field on an allow-listed built-in engine type

Status: Proposed
Owner: partner
Approved by: pending (security review by a different model, then Eldon line by line; RULES 42 because this touches authorisation and the audit trail)

Plan ID: BPL-040 (design only; no code until this ADR is Accepted and reviewed). Answers Q-603 as the partner decided it. Internal document: it names the engine (ADR-0016). Paths below shorten `apps/engine/change_engine/change_engine/` to `CE/`. Line numbers were checked again for revision 3 at commit 9160d33. Revisions 2 and 3 answer the security reviews listed under Review history.

## Context
- A Blueprint with a unique or indexed field that `entity.add` must add to a built-in engine type (`customer_code` on Customer, `supplier_code` on Supplier) cannot apply. The backend refuses it with `unique_or_index` before any write (`CE/adapter/frappe_backend.py:896-903`). The plan marks it `gated` (`CE/adapter/engine.py:1362-1363`; `CE/adapter/frappe_backend.py:565-567`), and apply then requires `approvals.gateApproved` (`CE/adapter/engine.py:1771-1779`). That approval is only a ULID whose presence and format the adapter checks; its truth is the control plane's (`contracts/engine-adapter.md:116`, 15.3). Nothing reaches the backend.
- The same refusal covers an existing field that lacks the constraint (`frappe_backend.py:888-894`), a quarantined field restored without it (`:1017-1021`) and `field.set_property` on `/unique` or `/indexed` (`:643-652`). Tests pin this: `CE/tests/test_bpl_031_entity_add_existing_doctype.py:252-271`, `:497-575`.
- The DDL gate approves exactly one `ADD COLUMN custom_*` statement (`CE/guarded_apply/ddl_plan_gate.py:55-60`) and rejects `ADD UNIQUE` and `ADD INDEX` (`:381-408`). For a new unique column the engine's diff yields the column with inline `unique`, then `ADD UNIQUE INDEX IF NOT EXISTS` (`:235-236`, `:345-352`); an indexed column yields `ADD INDEX <field>_index` (`:354-357`). A rejected plan falls back to a controlled admin deployment queue that does not exist yet (`CE/api/endpoints.py:428-429`).
- The guarded six-stage path runs lock, inspect and gate, durable audit intent, engine operation, reconcile, finalize (`CE/guarded_apply/schema_reconciler.py:80-245`). Each engine statement is checked against the approved plan before it runs (`endpoints.py:1080-1090`). A target with unresolved `RECOVERY_REQUIRED` or `PREPARED` is blocked (`schema_reconciler.py:118-124`, `endpoints.py:652-670`). Today any index change at reconcile is `RECOVERY_REQUIRED` (`ddl_plan_gate.py:751-757`).
- Weaknesses in today's path that this design must not inherit (found in review, verified): deployment ids come from a per-process counter that restarts at 1 (`frappe_backend.py:180-184`); the Stage 3 intent is an upsert that can overwrite an older row (`endpoints.py:984-994`); the baseline schema and the approved and executed statements live only in instance dicts (`endpoints.py:528-533`); the idempotency and recovery lookups return "none" on a database error (`endpoints.py:652-687`); the lock-timeout setter swallows errors (`endpoints.py:620-626`); `_ensure_doctype_exists` inserts a whole custom type with `unique` and `search_index` taken from the Blueprint, outside the gate (`frappe_backend.py:986-1002`, `:588-589`).
- Rules this must meet: approvals bound to tenant, exact action, data revision, approver and expiry (ADR-0027; RULES 23); identity and roles only from the authenticated session, fail closed (RULES 41); `onBehalfOf.roleIds` never authorise a configuration operation (ADP-C-012); apply is journaled and recoverable, not universally reversible (ADR-0028); signing keys stay in the KMS (ADR-0038 item 2); the engine stays invisible (ADR-0016); a row depends on the other founder's row only in an earlier gate (ADR-0025).

## Decision

### 1. The grant
1. **Wire format, one strict parse.** Token = `ddlg1.` + base64url without padding of the payload + `.` + base64url without padding of the signature. The payload is canonical JSON (contract 5.8 rules: UTF-8, sorted keys, no whitespace), at most 2048 bytes; the whole token at most 3072 bytes. The parser rejects: duplicate keys (never last-wins), unknown or missing keys, padding or non-base64url characters, numbers with a fraction or exponent, integers outside 0 to 2^53-1, strings that miss their contract pattern (ULIDs, `art_` plus 32 lowercase hex, and every hash as `sha256:` plus 64 lowercase hex, the contract's `sha256` type, `contracts/engine-adapter/common.schema.json:9`, produced by `CE/adapter/contracts_support.py:71-74`), and a payload that does not re-canonicalise to the exact received bytes. `iat`, `exp` and `approver.authTime` are integer Unix seconds. `nonce` is 16 random bytes (22 base64url characters). The signature is 64 bytes of ed25519 over the exact payload bytes. `scope` holds exactly one entry in v1 (item 8); a second or duplicate entry refuses.
2. **Claims:** `v` (1); `typ` (`ddl_constraint_grant`); `kid`; `aud` (the adapter environment's configured audience); `tenantId`; `siteId` (item 3); `siteClass` (`sandbox`, `test`, `production`); `operation` (`apply` only); `idempotencyKey` (of the apply call); `artifactId`; `contentHash`; `baseConfigHash` (`sha256:` hash of the site export at plan time, the value the plan token binds, `CE/adapter/engine.py:1378-1388`); `gateApprovedId`; `policyVersion` (the action-policy table version the issuer evaluated); `scope` = `[{stepSeq, kind, subject, doctype, fieldname, fieldtype, constraint}]` with `constraint` `unique` or `index`; `approver` (`kind` = `user`, `id`, `authTime`, `mfa` = true); `iat`; `exp`; `nonce`.
3. **Site incarnation.** Tenant plus site class does not identify a site: the resolver maps a tenant to a site name only (`frappe_backend.py:129-141`). The build adds an opaque 128-bit `siteId`, minted at provisioning and stored twice: in the regional store's tenant-to-site binding and in a one-row adapter table inside the site database. Every remap, clone and restore, in place or to a new site, runs only through trusted provisioning, which marks the site unavailable, mints a new id, writes it to both copies, and only then makes the site available again. The issuer reads `siteId` from the binding. The verifier requires the grant's `siteId` to equal both the binding for `tenantId` and the value read from the opened site, and `aud` to equal its own configured audience; while the two copies differ (an unfinished or bypassed rotation, an untracked clone) every grant refuses. So a grant issued before any rotation, including an in-place restore, fails afterwards.
4. **Issuer, and how revocation is honoured.** Only the control-plane approval service issues grants, and only at the approval's `approved` to `executing` transition in the action-policy state machine (`docs/security/action-policy-table.md:100-112`). At that moment, from its own source of truth and not from a cache, it: recomputes the change hash; refuses a cancelled, voided or expired request; re-evaluates the current gate policy row (recording its version as `policyVersion`) and the approver's and requester's current eligibility (ADR-0027, ADR-0049, ADR-0050); and binds the grant to the apply call's `idempotencyKey`. `approver` comes from the authenticated session's identity token, never a body; agents, support grants and service callers are refused. Revocation is honoured by refusal to issue: cancellation and voiding are allowed only while the request is pending or approved (`action-policy-table.md:106-107`), so anything revoked before execution starts never gets a grant, and after the transition the table forbids cancellation. **Policy floor (tightening after issue).** Publishing a new action-policy table version first commits that version as the floor in the regional store (a global row, plus a tenant row for a tenant-scoped change; the effective floor is the larger), and only then may the issuer evaluate under it. A floor only rises. The verifier refuses a grant whose `policyVersion` is below the effective floor at 11.2, and again inside the reservation transaction (item 12), which reads the floor rows under a shared row lock: a publication that commits after the 11.2 check is seen there, and one that starts later waits for the reservation to commit. A policy so takes effect at its floor commit; a grant reserved before that commit was valid under the policy then in force. A missing or unreadable floor row refuses (`engine_unavailable`). Withdrawing a `kid` (11.2) stays the emergency stop. Chosen over accepting a 330 s window because the reservation transaction already runs in that store: the floor costs one row and one locked read. A grant not consumed before `exp` dies; the approval then follows the table's failure rules.
5. **Key:** a new KMS ed25519 key, inventory entry "DDL-constraint grant signing key" (proposed `S24`), used through ADR-0038's `Signer`; only the approval service's workload identity may sign. The adapter holds public keys by `kid` from its environment's secret store. No private key is ever in the repo; production, staging and dev keys are separate (ADR-0018). Test vectors use a throwaway key whose private half is discarded after generation; its `kid` is refused outside tests.
6. **Why a signature, not an HMAC:** with an HMAC the verifier holds the minting secret, so a compromised adapter or engine worker could mint approvals. With a signature it can check a grant but not create one.
7. **Lifetime:** `exp - iat` at most 300 seconds, enforced by the verifier; clock skew 30 seconds. Expiry is checked again inside the reservation transaction (item 12) against the store's clock, right before consumption.

### 2. The one audited code path
8. **v1 scope (narrowed).** A grant is valid only for an artifact with **exactly one step** that adds **exactly one constraint** to **exactly one new field**: a `field.add` or `relation.add`, or an `entity.add` of a contract-mapped entity whose definition holds that one field only. The field has no column and no metadata yet, is adapter-owned (`custom_` prefix), is Blueprint `string` or `link` (engine Data or Link), carries no `default`, and sits on a doctype in the **constraint allow-list** (a versioned data file; starts with Customer and Supplier; never a protected entity, `CE/adapter/mapping.py:250`). Why:
   - One step keeps `baseConfigHash` true from plan to effect, because no earlier step of the operation changes the export; grant, reservation, scope entry and deployment are one-to-one, so no per-field state can go stale; rollback has one inverse step. Multi-field and multi-step artifacts are refused (item 26), never partly run.
   - **No compiler split.** The constrained field must be the only change in its Blueprint revision as authored. The compiler never splits a larger change; it refuses, at compile and before any approval, a revision that adds a constrained field next to anything else (new neutral code `constraint_change_not_isolated`). A Blueprint that wants a new unique field is applied as two separately approved revisions: first everything else, then the one-field constraint revision, whose `blueprint.base` must equal the first's target (`CE/adapter/engine.py:1073-1075`). Each apply advances the applied revision on its own (`engine.py:1918-1922`) and each is complete and valid alone. Why this is safe: until the second applies, the field is absent from the applied revision, the export, the metadata and the table, so no state has the field without its constraint. If the second fails clean, expires or loses approval, the site stays on the first revision and the constraint revision is approved again or dropped (a `RECOVERY_REQUIRED` outcome blocks the target per item 16). Anything that references the field (form, report, permission, postcondition) cannot be in the first revision and comes in a later one. Studio shows the constraint revision as its own pending change after the others; its review screen shows the one field, the constraint, the type, the row count and the collation note (item 19).
   - Data or Link without a default only: the gate's column definer adds `not null default 0` for Int and Check and for Currency, Float and Percent, and a quoted default whenever one is given (`ddl_plan_gate.py:222-233`), then appends `unique` (`:235-236`). Such a column fills existing rows with one value, so the unique index cannot build, and later inserts collide. Data and Link without a default get no default clause, so the column is nullable and existing rows hold NULL (MariaDB behaviour on the pinned version UNVERIFIED; bench item 24).
   - No existing-column case: `field.set_property` false to true, restoring a quarantined field that lacks the constraint, and adding a constraint to an existing native or custom field need a duplicate scan, collation-aware comparison and an existing-column reconcile predicate. v1 refuses them all (item 26).
9. All constraint DDL goes through **one function in `CE/guarded_apply/`**: a constraint mode of the six-stage deployment reusing `execute_single_field_deployment`'s stages and gate. No other caller may pass a grant; the backend receives it as an explicit argument, never from module or request state.
10. **Every other entry point refuses constraint creation.** Checked in `CE/adapter/frappe_backend.py`, `execute_step` (from `:597`) and its callees:
    - `_apply_or_restore_custom_field` (`:1005-1060`), reached from `field.add`, `relation.add` (`:618-628`) and mapped `entity.add` (`:908-913`): the only route into the constraint mode.
    - `_ensure_doctype_exists` (`:986-1002`) inserts a custom type whose field definitions carry `unique` and `search_index` (`:588-589`), outside the gate. It receives Blueprint fields only from the unmapped `entity.add` branch (`:868-873`); the calls at `:627`, `:1196` and `:1296` pass `{}` and create a plain title field. The planner marks such an entity `gated` (`engine.py:1362-1363`), so today a present `gateApproved` reaches this insert. The build makes the unmapped branch refuse any field with `unique` or `indexed` before any write, with or without a grant, and makes `_ensure_doctype_exists` itself refuse a definition with either flag. Constraint creation through custom-type insertion is out of v1.
    - The restore branch (`:1017-1021`), the present-field branch (`:888-894`) and `field.set_property` on `/unique` or `/indexed` (`:643-652`) keep refusing.
    - Property setters map no constraint property (`:71-81`). `field.set_property` on `/default` for a field that carries an adapter-added unique constraint is refused, because a default would make repeated inserts collide.
    - The decimal six-stage branch (`:1031-1050`) runs only without `unique` or `indexed`. Rollback inverse steps run through the same `execute_step` and meet the same refusals.
11. **Checks before the effect, in this order** (any failure refuses with a neutral code, fail closed, audited per item 14):
    1. Caller and tenant first, nothing read from the grant: the caller is an allow-listed service in the gateway-stamped context, and a per-tenant attempt rate on `context.tenantId` holds (configured; absent means refuse); excess refuses `rate_limited`.
    2. Strict parse and ed25519 signature (item 1) with an allow-listed, not withdrawn `kid`; `typ`, `v`, `aud` match. `iat ≤ now + skew`, `now ≤ exp`, lifetime at most 300 s; `policyVersion` at or above the effective policy floor (item 4).
    3. `tenantId` equals the authenticated `context.tenantId` and the tenant the resolver opened (`frappe_backend.py:129-141`, `:208-211`); `siteId` matches per item 3; `siteClass` equals the site's class. Only now is the attempt charged to the grant: at most 3 per (authenticated tenant, grant hash); excess refuses `rate_limited`. A refusal before this point counts only against the caller's own tenant rate, so a caller holding another tenant's grant cannot spend that tenant's budget.
    4. `artifactId`, `contentHash`, `gateApprovedId` and `idempotencyKey` equal the apply input. `baseConfigHash` equals the current export hash, checked at admission before any step (next to `engine.py:1771-1779`) and again under the lock just before the reservation.
    5. Scope equality: the backend derives the one entry from the artifact and the mapping, never from the grant, and it must equal `scope` exactly.
    6. v1 shape (item 8) holds, from live metadata.
    7. The advisory lock is held (`schema_reconciler.py:98`). The durable recovery and idempotency lookups (item 13) succeed and find no `RECOVERY_REQUIRED` or `PREPARED` row for the target.
    8. The live DDL plan is exactly: `ADD COLUMN` of this field with no `not null` and no `default`, plus `ADD UNIQUE INDEX IF NOT EXISTS` or `ADD INDEX` on this column only, on this table only. No `MODIFY`, no `DROP`, no other column. `endpoints.py:1080-1090` enforces the same list per statement.
    9. Row count, bounded: `SELECT COUNT(*) FROM (SELECT 1 FROM <table> LIMIT ceiling + 1)`. No configured ceiling refuses; above it refuses with `table_too_large`. v1 needs no duplicate scan (new column only).
    10. The constraint mode sets the session `lock_wait_timeout` with a setter that raises (today's swallows errors, `endpoints.py:620-626`), then reads `@@SESSION.lock_wait_timeout` back; any other value refuses.
12. **Reservation: consumption bound to the operation.** One committed transaction in the adapter's regional store inserts a reservation with unique keys on `(tenantId, nonce)` and `(tenantId, idempotencyKey)`, holding the grant hash, the operation binding, the single scope entry with state `reserved`, and the deployment id. The same transaction rechecks `exp` against the store's clock and re-reads the policy floor under a shared row lock (item 4). From that commit the grant is spent whatever the outcome; refusals at item 11 do not spend it; those after 11.3 count against its attempt budget. The scope entry then moves `reserved`, `dispatched`, and `applied`, `failed_clean` or `recovery_required`, each once.
13. **Durable evidence before any effect.** The deployment id is `dep_` plus the first 32 hex characters of sha256(`tenantId|nonce|stepSeq|constraint`), so it never repeats after a restart. The Stage 3 intent is a plain `INSERT`, never an upsert: on a duplicate key it reads the existing row and continues only if grant hash, idempotency key and payload hash all match (a resume of the same reservation); otherwise it refuses `idempotency_conflict` with no effect. The committed intent holds the complete before-schema fingerprint (every key in `SCHEMA_KEYS`, `ddl_plan_gate.py:524-528`), the approved statements, the expected delta (column definition and index descriptor), the reservation id and the grant hash. A dispatch journal row is committed immediately before each statement is sent and updated when it returns. Prerequisites the build row adds to `guarded_apply` for this mode: (a) baseline and approved plan in the intent row; (b) the dispatch journal; (c) idempotency and recovery lookups that raise on a database error, which blocks (`engine_unavailable`); (d) reconcile reading only durable evidence; (e) derived deployment ids and the strict intent insert. If any write fails, nothing runs.
14. **Audit record** (internal only, `contracts/engine-adapter.md:200`): auditId, requestId, correlationId, tenant, siteId, siteClass, aud, caller service, `onBehalfOf` (recorded, not trusted), `kid`, nonce, sha256 of the grant (never the grant), approver id, `authTime`, `iat`, `exp`, `policyVersion`, `gateApprovedId`, idempotencyKey, artifactId, contentHash, reservation id, deployment id, scope entry, row count, lock timeout read back, approved statements, dispatch journal, before and after fingerprints, outcome and stage timings. Every refusal writes a refusal record (grant hash, code, stage), capped per authenticated tenant and, after 11.3, per grant hash.
15. **Replay.** The same idempotency key and grant hash returns the stored outcome without a new effect. The same key with another grant refuses `idempotency_conflict`. A failed lookup blocks; it never counts as "no earlier attempt".

### 3. Failure and rollback
16. **A failed statement does not prove `failed_clean`.** After any failure, and on restart, the outcome comes only from the durable baseline and a fresh complete schema read: `failed_clean` only if the live schema equals the baseline on every fingerprint key and no engine metadata row exists for the field; `applied` only per item 17; anything else, including an incomplete or failed read, is `RECOVERY_REQUIRED` under the existing rows (`schema_reconciler.py:254-320`). Whether a failed or interrupted `ALTER TABLE` leaves the table unchanged on the pinned MariaDB version is UNVERIFIED; bench item 24.
17. **New-column predicate only.** `assess_applied_ddl` (`ddl_plan_gate.py:693-762`) gains a constraint variant that accepts exactly: the baseline plus the approved column at the end of the column order (approved type, nullable, default NULL, the table's default charset and collation), plus exactly one index matching the full approved descriptor (name, uniqueness, the single column, no prefix length, BTREE), with every other column, index, constraint, check, trigger and table attribute unchanged, and engine metadata matching the approved definition. No existing-column predicate exists because v1 has no existing-column case (item 8).
18. **Crash between DDL and finalize.** Reservation, intent, baseline and dispatch journal are already durable. On restart the deployment is `PREPARED`, the target stays blocked, and reconcile classifies it per items 16 and 17. A missing or unreadable piece of evidence gives `RECOVERY_REQUIRED`, never `applied`. Recovery never re-runs DDL; the reservation is spent.
19. **Rollback keeps the constraint.** The inverse of the add is quarantine, which hides the field and keeps column and index (`frappe_backend.py:1126-1129`; contract line 142). Later inserts must write NULL, not `''`, into the hidden column, and so must blank inserts while the field is live; both UNVERIFIED, bench item 24. If the bench shows `''`, `unique` stays off (an index-only constraint never blocks inserts). Uniqueness follows the column collation, expected to be case-insensitive (`ABC` equals `abc`; UNVERIFIED); the review screen tells the approver. Re-applying restores through the restore branch, which needs no DDL because the index still exists. Dropping a constraint stays refused. The integration row depends on BPL-041 moving `unique_or_index` into `check_ready`, so a rollback that would need constraint DDL is refused before any step runs.

### 4. What stays refused
20. Everything outside item 8 keeps `unique_or_index`: any step without a valid grant or with a mismatched scope; artifacts with more than one step or more than one constrained field; a revision that adds a constrained field next to any other change; existing columns (native such as `item_code`, earlier custom, quarantined restore, `set_property` in either direction); types other than Data and Link; fields with a default; constraint fields in a new custom type; doctypes off the allow-list; composite or prefix indexes; tables above the ceiling; and every rollback that would drop a constraint.

## Alternatives rejected
- A controlled admin deployment only: no binding to the approved change, a second unaudited path, does not scale. It stays the fallback above the ceiling.
- Adding the column without the constraint: rejected in the BPL-031 review (the Blueprint would apply without enforcing uniqueness).
- An HMAC grant: the verifier could mint (item 6).
- The adapter fetching the approval record by ULID at run time: a new runtime dependency and trust channel into the engine side. Issuing at the executing transition gets the same freshness offline.
- A grant valid for a whole multi-field, multi-step artifact with per-field scope entries and intermediate-state checks: closes R1 too, but needs a schema prediction per step and per-field recovery. Rejected for v1 as more complex for the same outcome; revisit with evidence of need.
- A compiler split into an ordinary and a constraint artifact with an intermediate revision and a recovery protocol: two authored, separately approved revisions reach the same outcome with no half state (item 8).
- Accepting a bounded window for policy tightening: the floor costs one row and one locked read (item 4).
- Existing-column cases in v1: need duplicate scans, collation handling and a second reconcile predicate. Deferred (item 8).
- Trusting `approvals.gateApproved` as it stands: an unsigned id with no scope, approver or expiry.

## Consequences
- Easier: Blueprints with unique customer or supplier codes apply on built-in types, with an approval that is bound, single-use, revocation-aware and audited.
- Harder: a KMS key, a contract field, an issuer, a site incarnation id and durable evidence in `guarded_apply` must exist first. The compiler refuses a constrained field that is not alone in its revision, so the owner approves it as a separate change after the rest; provisioning must rotate `siteId` on every remap, clone and restore. The reconciler learns to accept exactly one approved index.
- Open for founders: the initial allow-list (Customer and Supplier proposed); the row ceiling and attempt budgets (set after a bench measurement); whether the approver must differ from the requester for this gate; MFA step-up for production grants (ADR-0047); who owns the compiler isolation check, Studio's display of the separate change, and the `siteId` rotation in remap, clone and restore tooling; whether the approval returns to `approved` when a grant expires unconsumed; a separate row for today's path defects (counter ids, upsert intent, swallowed lookups and lock-timeout errors, in-memory baseline), which this ADR avoids only in the constraint mode.
