## Context
- PLT-024 built the customer-facing API edge core in `services/gateway/edge/` (`gateway.py`, `paths.py`, `projection.py`, `headers.py`, `errors.py`, `markers.py`; summary in [services/gateway/README.md](../../services/gateway/README.md)). It is pure in-process logic tested with fake upstreams: deny-by-default `/v1/` routes, allow-list projection of engine JSON, header and cookie filtering, engine-error mapping, and an audit sink that is required.
- Its audit is process memory: an `intent` record before a mutating handler, an `outcome` after every request, a 1000-record deque for outcome records that failed after a possible effect, reservation at 900 to return `503 audit_unavailable`, and `audit_drop_count`. Process memory is not crash durable.
- Facts in today's core that this design changes: a route is matched by path for any allowed method (`gateway.py:167`), and "mutating" is decided by the HTTP verb alone (`gateway.py:29`, `gateway.py:175`); a handler returns a complete body in `UpstreamResponse` (`gateway.py:60`) that `projection.py:119` parses whole; an expired engine `sid` makes the gateway clear the platform cookie (`gateway.py:237`, `headers.py:70`, cookie `SameSite=Lax` at `headers.py:27`); the raw path is recorded up to 256 characters (`gateway.py:269`).
- The README and the PLT-024 logs (2026-11-18 and 2026-11-20) set three hard preconditions before any HTTP binding or live route: (1) a durable spool with recovery, retry and observable drop and backlog health; (2) tenant, user and session from verified identity bound to every audit record (Tool API section 8); (3) request-body, Idempotency-Key and upstream-body caps with regression tests (PR #123 review item 5). Q-302 asks Eldon to add `unauthenticated` and to ratify `audit_unavailable`.
- Identity exists as a core (PLT-005, Eldon's lane): `verify_customer_token(token, tenant_id)` returns `AccessClaims` (issuer, audience, subject, tenant, realm, session_version, mfa_satisfied, auth_time, token_id, times; no roles) after checking the membership and its session version. Roles come from a `RoleResolver` port; ADR-0060 item 15 forbids reading real roles from the regional store before SEC-024 (store design ADR with its own security review) and GOV-065 (Tool API wording) are accepted.
- The engine adapter contract covers the configuration path only (`capabilities`, `provision_site`, `plan`, `apply`, `rollback`, `sync_members`...); `execute` and `query` (Tool API runtime) are out of scope ([contracts/engine-adapter.md](../../contracts/engine-adapter.md) section 1, line 11). So ADR-0041's 30-day idempotency covers configuration operations, not business writes. The adapter context already requires a `correlationId` (engine-adapter.md line 38; `contracts_support.py:180`) and writes it to `adapter_audit_log` (engine-adapter.md line 200; `storage.py:232`, `mariadb_store.py:43`), with no index on it.
- The store of record for audit is SEC-008 (append-only, hash-chained, exported off-box; Eldon's lane, G2, todo; threat T56). Its location is not decided, and this ADR does not decide it.

## Decision

### 1. Shape of the binding
1.1 **(P)** The binding is a thin HTTP adapter around `Gateway.handle`: it builds a `GatewayRequest` carrying the verified principal and serialises the `GatewayResponse`. Route policy, audit and caps that need route knowledge stay in the edge core, testable without a socket.
1.2 **(P) Two layers of HTTP control.** WSGI (PEP 3333) runs after the server has parsed the request, so the application cannot see or refuse framing ambiguities, enforce header-read deadlines or replace parser-generated errors. Therefore:
- **At the production listener and at every HTTP hop in front of it** (proxy, if INF-001 chooses one): refuse a request with duplicate or non-numeric `Content-Length`, with both `Content-Length` and `Transfer-Encoding`, with any request `Transfer-Encoding`, with obsolete line folding, with more than one `Host` or a `Host` that disagrees with an absolute-form target (RFC 9112 sections 6.3 and 3.2), and close the connection after any framing error; enforce the header-read and body-read deadlines and header caps of section 4; send no `Server` header and our own error body for every parser-generated refusal. The production listener is a separate choice with a licence record in PLT-029; `wsgiref` and `http.server` are for tests only.
- **In the WSGI application:** repeat every check it can see (defence in depth) and every route-dependent cap. A configuration in which the listener does not provide the first layer is not deployable.
1.3 **(Inherited, ADR-0016)** The engine runs on an internal network; the public listener reaches it only through route handlers over the engine adapter.
1.4 **(P)** Health, readiness and metrics are served on a second listener bound to the internal network only, never on the public listener and never under `/v1/`.

### 2. Durable audit spool
2.1 **(P) What it is.** Each gateway instance owns one local, append-only spool: a SQLite database (standard library `sqlite3`) in WAL mode with `synchronous=FULL`, on a persistent, encrypted volume in the same country and placement as the instance (ADR-0006). That this gives crash durability on the production volume type is UNVERIFIED until tested there (PLT-028). It is a **delivery buffer, not a store of record**: it serves no reads except to its own forwarder and recovery, holds a record only until the store of record has committed it, is never backed up or restored as a source of truth, and is never shared between instances or over a network file system. It is not a second regional store and does not touch the control-plane regional database (ADR-0040) or the regional role store (ADR-0060).
2.2 **Why SQLite here does not contradict ADR-0041.** ADR-0041 keeps adapter state out of SQLite because idempotency keys and their effects must restore together with the tenant database. The spool holds no state that must agree with tenant data after a restore; it only survives a process crash until a record reaches SEC-008.
2.3 **(P) Single writer.** An instance takes an exclusive lock on its spool at start (an advisory file lock plus a row holding `instance_id` and a fencing counter). A second process that finds the lock held refuses to serve.
2.4 **(P) Two tables, independent lifetimes.** `records` is the append-only log that the forwarder delivers and prunes. `open_intents` holds one row per admitted mutating request (`audit_id`, intent `seq`, reserved bytes, partition, tenant) and is **never touched by the forwarder**. The intent record and its `open_intents` row are inserted in one transaction; the outcome record and the deletion of that row are committed in one transaction. So an intent that the store of record has already acknowledged and pruned still has its open row while the handler runs, and restart always finds it.
- Mutating request: intent and open row commit **before** the handler runs. If the commit fails or admission (2.7) refuses: `503 audit_unavailable`, handler not called.
- Read, denial or validation failure: the outcome record commits before the response is sent, else `503 audit_unavailable` (P: today this path returns 500 `internal_error`).
- After a possible mutating effect: if the outcome commit fails, the real result is returned (an error would invite a duplicate); the outcome is retried in process, and the open row keeps the reservation; if the process dies first, recovery (2.9) closes it.
2.5 **(P) Integrity inside the spool.** Each record carries `instance_id`, a per-instance monotonic `seq` (the ordering authority; wall-clock time can move backwards), `key_id` and `chain = HMAC(key[key_id], prev_chain || canonical_record)`. Keys are versioned secrets registered under ADR-0038 by PLT-028 (no id allocated here). Rotation writes a `key_rotation` record under the old key that names the new `key_id`; the next record chains under the new key; the old verification key stays available until every record under it is committed in the store of record. The tenant-wide chain and off-box export remain SEC-008's (T56).
2.6 **(P) Checkpoints held outside the spool.** A valid HMAC prefix proves nothing about a deleted suffix or a restored older file, so the store of record keeps, per instance, the **committed watermark** (`seq`, `chain`, `key_id` of the highest contiguous committed record) and the **last reported head** (`seq`, `chain`), which the forwarder reports with every batch and at least every 5 s. The forwarder writes to the store with a per-instance credential (ADR-0038; registered by PLT-028), and the store accepts records and checkpoints for an `instance_id` only from that credential. At start, and before every batch:
- the local spool must contain the store's committed watermark (or the local pruned-through checkpoint must equal it): a local position behind the store means a rolled-back file, so the instance fails closed;
- the local chain must reach at least the store's last reported head with the same `chain` at that `seq`: a missing or different record below the reported head means truncation or rewrite, so the instance fails closed;
- the batch to send is re-verified from the watermark to its last record, so tampering while the process runs stops forwarding, stops admitting mutations and pages.
Residual: records committed after the last head report (at most 5 s) can be removed undetected by someone with write access to the volume.
2.7 **(P) Capacity, partitions and admission.** Capacity is counted in records and bytes. Bytes are the measured database and WAL file sizes plus `reserved_bytes` (4 KiB per open row, times an overhead factor of 2 for SQLite pages and WAL; the factor and the sizes are UNVERIFIED until measured in PLT-028). Capacity: 100,000 records or 512 MiB. Admission check and the open-row insert run in one `BEGIN IMMEDIATE` transaction, so reservations are atomic across threads and processes and survive a restart. Partitions, each with its own record and byte budget:
- `preauth` (10%): records without a verified identity or with a token for another tenant (5.4). When it is full, those requests get `429 rate_limited` and one aggregate record per minute per reason (count, keyed source digests) in a slot reserved for it; tenant traffic is unaffected.
- `tenant` (90%): verified requests; one tenant may hold at most 20% of it, so one noisy tenant cannot block the others.
Within a partition, new mutations are refused at 90% of its budget; reads and denials at 100%. Mutations are also refused while `oldest_unforwarded_age_s` exceeds 300 s (P), which bounds the window of records a volume loss can take (2.11); reads continue. `audit_drop_count` stays a counter that must be zero; any increase pages.
2.8 **(P) Forwarder and receipts.** The forwarder (same process, or a separate one under the same lock family) delivers records in `seq` order in batches (at most 500 records or 1 MiB) to the `AuditStore` port (Q-614). The store processes a batch in `seq` order and answers per record with `committed`, `duplicate` (same `(audit_id, phase)` and same hash), `conflict` (same key, other hash) or `rejected` (schema), plus the new contiguous committed watermark. For `conflict` and `rejected` the store writes a placeholder at that `seq` (record hash, `chain`, reason; for a conflict it also keeps the second payload as evidence beside the first, neither overwritten), so the chain and the watermark stay contiguous; the full local record moves to a `quarantine` table with its `seq` and `chain`, counts against capacity, pages, and leaves only by an audited operator action. The forwarder prunes local `records` only up to the returned watermark, in one transaction that also stores the pruned-through checkpoint. A crash between the store's commit and the local prune re-sends the batch; the store answers `duplicate` and the same watermark. Failures back off from 1 s doubling to 60 s with jitter, forever; nothing is dropped. Until SEC-008 provides the store the port has a test double only and **no live route may be registered** (section 8).
2.9 **(P) Restart and recovery.** An instance is not ready until it has: taken the lock; verified the spool against the store's checkpoints (2.6; if the store is unreachable, it starts without serving mutations until the check passes); and closed every row of `open_intents` by appending an `outcome` with `status: null`, `reason: "unknown_after_restart"` and deleting the row, one transaction per row. Recovery is idempotent: a crash during recovery leaves the unclosed rows for the next start, and a closed row cannot be closed twice. Only then does it start the forwarder and report ready.
2.10 **(P) Reconciliation of unknown outcomes.** The adapter already accepts and stores `correlationId` (Context). The gateway sends its request `audit_id` as `correlationId` on every adapter call; each adapter call keeps its own `requestId` and `auditId`, so a request that makes several calls stays traceable call by call. An unknown outcome is reconciled only against a **terminal** adapter outcome (`adapter_idempotency` status done with its stored outcome, or the operation record's final status): an audit row for a refused or still-running operation proves nothing about an effect. The contract has no read by `correlationId` today and the column has no index, so automatic reconciliation waits on Q-611; until then each unknown outcome is a human-visible alert. For business writes outside the adapter contract the same rule applies to whichever component owns their deduplication (2.12).
2.11 **(P) Instance loss.** The spool survives a process crash and restart on the same volume (UNVERIFIED on the production volume type). Loss of the volume loses unforwarded records: the accepted residual, bounded by the 300 s cutoff in 2.7. Mitigations: replicated in-country block storage if INF-001 provides it (UNVERIFIED); a decommissioned instance's volume is attached to a forwarder-only recovery process and drained to zero before deletion; for configuration mutations the adapter's audit in the tenant database is a second trail. GLB-T29 tests only that the age alert and the cutoff fire; it does not and cannot prove the loss away.
2.12 **(P) Replay and deduplication.** "Replay" here means re-delivery of spooled records; the gateway never re-sends a request to the engine. A mutating route may be registered only if it declares a **durable deduplication provider for that exact operation**, keyed by tenant, operation and `Idempotency-Key` and bound to the input hash: the adapter's tenant-database store (ADR-0041) for configuration operations, or the Tool API store that Tool API section 6 requires for business writes (owner and location: Q-613). A mutating route without one is refused at startup. Every request, a replay included, passes authentication and the route permission check (section 3) before the deduplication lookup, so a stored result is never returned to a caller who has since lost access. The edge itself adds no idempotency store.
2.13 **(P) Observability.** Metrics on the internal listener: `audit_spool_records`, `audit_spool_bytes` (per partition), `audit_reserved`, `audit_oldest_unforwarded_age_s`, `audit_forward_failures_total`, `audit_quarantine_records`, `audit_unknown_outcomes_total`, `audit_admission_refusals_total`, `audit_preauth_aggregated_total`, `audit_drop_count`. Alerts: drop count above zero, quarantine above zero, checkpoint or chain failure, oldest unforwarded age above 60 s, admission refusals above zero for 1 minute.

### 3. Identity, tenant binding and caller permissions
3.1 **(Inherited, ADR-0007 items 3 and 10)** The tenant comes from the request host only, after canonical hostname validation (PLT-003, SEC-021). The customer token from the `__Host-session` cookie is verified with `verify_customer_token(token, host_tenant)`: issuer, audience naming that tenant, tenant claim equal to the host tenant, realm `customer`, active membership and current session version. Any failure is `403 permission_denied` (401 maps to `permission_denied` until Q-302 is answered). The tenant is never read from a path, query, body or header.
3.2 **(P) Order of checks.** Cheap checks run before expensive ones and before any audit write: listener framing and caps (1.2, 4), host validation, route and method match (3.3), per-source and global pre-authentication rate limits (SEC-009 port; a local token bucket until it exists), `preauth` admission, then token verification and role resolution.
3.3 **(P) Declared methods and effects.** A `Route` declares its allowed methods and one effect, `read` or `write`. A `write` route may use only POST, PUT, PATCH or DELETE; registration refuses a `write` route on GET or HEAD, and a `read` route's handler receives only a read-only upstream client. Any undeclared method on a registered path returns the same our-404 as an unknown path. Intent records, the Origin check (3.7) and the `Idempotency-Key` requirement follow the declared effect, not the verb, replacing `MUTATING_METHODS` (`gateway.py:29`) as the trigger.
3.4 **(Inherited)** Staff tokens are a separate realm and are refused on customer routes (ADR-0007 item 7). **(P)** The edge accepts no agent token: agent and department-assistant calls go through the Tool API path (ADR-0043, agent-least-privilege).
3.5 **(P) Route permission, read authoritatively.** A `Route` declares one required permission id. On every request the gateway resolves the caller's permissions through the `RoleResolver` port and denies on any failure, timeout, malformed or empty result. **(Inherited, ADR-0060 items 8 to 11)** The read is authoritative (never an asynchronous replica, maximum age 0); the result must name the claims' tenant and pass the store's integrity check; a tenant fenced after a restore denies; a widening change is not usable until its sync is verified. This is a coarse gate: scope, field rules, approvals (including the re-check when an approved action executes, ADR-0060 item 10) stay with the Tool API (contract section 4, OPR-004), and the engine evaluates the call as the caller's shadow user (ADR-0007 item 11). The real store is read only after SEC-024 is accepted with its own security review (ADR-0060 item 15); until then a fake only.
3.6 **(P) Step-up for admin routes.** A route may declare `admin: true`; it then requires `mfa_satisfied` true **and** `auth_time` within the route's `max_auth_age_s` (ADR-0007 item 6, the identity step-up).
3.7 **(P) Session cookie and cross-site writes.** Session-cookie issuance and clearing belong to identity, not to the upstream: PLT-030 removes the mapping of an expired engine `sid` to clearing our cookie (`gateway.py:237`); an engine session cookie in any response is dropped and raises an internal alert, and nothing an upstream returns can change the browser session. Identity sets the cookie `HttpOnly; Secure; Path=/; SameSite=Strict` (today's clear directive uses `Lax`, `headers.py:27`). A request must carry at most one `__Host-session` cookie (duplicates are refused). No CORS headers are ever sent. A `write` request must carry exactly one `Origin` equal to the tenant's canonical origin, checked before the intent record.
3.8 **(P) Handler input.** `UpstreamRequest` gains `audit_id`, `tenant_id` and `subject` from the verified claims, and an upstream client with the caps of section 4; the handler selects the tenant site and shadow user from these fields only.

### 4. Size caps and time limits (all values (P); listener = enforced at the listener and every hop, app = in the application)
| Item | Cap | Where | When exceeded |
|---|---|---|---|
| Raw request target | 2,048 bytes | listener, app | 400 `invalid_arguments`, `details.limit = "path"` |
| Request headers | 64 fields, 8 KiB per field, 16 KiB total | listener, app | 400 `invalid_arguments`, `limit = "headers"` |
| Framing | 1.2 rules; a body needs one valid `Content-Length`; any `Expect` refused | listener, app | 400, connection closed |
| Query string | refused unless the route declares parameters; then 2,048 bytes, declared names only | app | 400 `invalid_arguments`, `limit = "query"` |
| Request body | route default 256 KiB, declared up to 4 MiB; file uploads out of scope | listener (ceiling), app (route cap, counting reader stops at cap + 1) | 400 `invalid_arguments`, `limit = "request_body"` |
| `Idempotency-Key` | required on `write` routes; exactly a ULID or a UUID | app | 400 `invalid_arguments`, before the intent |
| Client header read / body read / response write | 10 s / 30 s / 30 s | listener | connection closed; outcome recorded once the request line was read |
| Upstream response headers | 100 fields, 32 KiB | upstream client | 500 `internal_error`, reason `upstream_too_large` |
| Upstream body | JSON route 2 MiB default, declared up to 16 MiB; `own_content_type` route declared, at most 25 MiB | upstream client (counting read, connection closed at cap + 1), core re-checks | same |
| Upstream JSON | depth 32, 200,000 values | linear pre-scan of the bytes before `json.loads` | 500 `internal_error`, reason `upstream_unparseable` |
| Upstream bytes in flight | 256 MiB per instance, reserved before the read | upstream client | 503 `engine_error` retryable |
| Upstream connect / total | 2 s / 30 s | upstream client | read: 503 `engine_error` retryable; write: 4.2 |
| In-flight requests | 256 per instance | app | 429 `rate_limited` with our `Retry-After`, before the intent |

4.1 **(P)** Caps are checked before the intent record wherever possible. Error bodies never echo the oversize value. A dedicated `payload_too_large` code is Q-612; until then `invalid_arguments`. Because `UpstreamResponse` holds a complete body (`gateway.py:60`), caps applied only in the core would come after the memory is spent; the gateway therefore hands handlers a capped upstream client (3.8) and the core check is a second line.
4.2 **(P) Write timeout.** If the upstream deadline passes after a write was sent, the outcome is unknown: the gateway records `reason: "upstream_timeout_unknown"` and answers `503 engine_error` retryable. A retry with the same `Idempotency-Key` reaches the route's deduplication provider (2.12), which returns the stored or in-progress outcome: one effect even when the upstream committed before the client timed out. Long-running operations (apply, up to the adapter's one-hour deadline) are never held on a synchronous request; their routes return the operation reference.

### 5. Audit record (identity-bound)
5.1 **(P) Fields of every record**, intent and outcome: `audit_id`, `phase` (`intent`, `outcome`, `reconcile`, `key_rotation`, `aggregate`), `instance_id`, `seq`, `key_id`, `chain`, `ts` (UTC, milliseconds), `partition`, `route` (our registered template, never the engine path), `method`, `param_count`, `path_normalisation`, `identity` (`verified` or `none`), and when verified: `tenant_id`, `user_id` (token subject), `realm`, `session_version`, `token_id`, `mfa_satisfied`, `auth_time`; `role_ids` and the role store's version as read for the decision (once the store exists); `idempotency_key` (random by grammar, so stored as is); `request_bytes`; on outcome also `status`, `reason`, `error_code`, `latency_ms`, `upstream_correlation` (the `correlationId` sent).
5.2 **(P) Redaction.** A raw path can carry pasted credentials or personal data, so the raw path is no longer recorded (it is today, `gateway.py:269`). A matched request records the route template and a keyed digest of its parameters; a refused path records its length, a keyed digest and `path_normalisation`. The body is recorded only as `request_digest = HMAC(digest_key, body)` with a versioned key separate from the chain key: a plain hash of a low-entropy body (an amount, a yes or no) could be guessed offline, while a keyed digest still lets an investigator who holds the key confirm a disputed body. Source address appears only as a keyed digest for throttling. Never recorded: tokens, cookies, `Authorization` values, bodies, query values, engine headers, engine field names or engine text. Redacted arguments belong to the Tool API's `tool.called` record (Q-610).
5.3 **(Inherited, contract section 8)** Tool API section 8 lists `session_id`. `token_id` changes on every refresh rotation and `session_version` only tracks revocation, so neither links one session's records. **(P)** Record both now; **no live route until Q-609 is answered and a stable verified session id (or the accepted alternative) is in the claims**, with a test that a refresh keeps the linkage (GLB-T40).
5.4 **(P) Unauthenticated and cross-tenant attempts** (`identity: none`, or a token for another tenant) go to the `preauth` partition (2.7) and to a platform security stream, with the host tenant marked unverified; they never enter a tenant's own audit view.
5.5 **(P) Deprovisioning.** A closed tenant's records may sit in `records`, `open_intents`, `quarantine` or a detached recovery volume. ADR-0040's deprovisioning verification (step 8) must probe all four on every instance and every retained volume and find none for the tenant before certifying; quarantined records of that tenant are resolved or destroyed under the deprovisioning approvals. The workflow change belongs to the ADR-0040 owner (partner); it is not made here.

### 6. Engine invisibility at the binding
6.1 **(Inherited, ADR-0016)** Everything a caller can observe is ours: paths, headers, cookies, error shapes, `audit_id` format.
6.2 **(P)** No `Server` or `X-Powered-By` header; every parser-generated refusal at the listener and at each hop uses our JSON error body (1.2). Internal listeners, metric names and logs may name the engine; the public listener may not.
6.3 **(P) Internal pre-public probe (ADR-0040 step 10, `PROV-T32`).** The first route is bound on an internal-only hostname that no public DNS name points to, with synthetic tenant data. The QA-016 crawler runs against that hostname: paths, headers, cookies, error bodies, and malformed-HTTP responses from the listener and each hop. Only a pass allows the public hostname to be bound to the same configuration; any later listener, proxy or route change repeats the probe.
6.4 Timing and size side channels against the engine are not addressed (UNVERIFIED whether they reveal the engine).

### 7. Failure summary
| Situation | Write | Read |
|---|---|---|
| Spool commit fails before handler | 503 `audit_unavailable`, handler not called | 503 `audit_unavailable` |
| Partition above admission level, or oldest unforwarded above 300 s | 503 `audit_unavailable` | served until the partition is full |
| `preauth` partition full | n/a (no write without identity) | 429, aggregate record |
| Outcome commit fails after effect | real result, outcome retried, open row kept; else `unknown_after_restart` | 503 `audit_unavailable` |
| Store of record unreachable | served while capacity and the age cutoff allow | served while capacity allows |
| Crash mid-request | open row survives any prune; recovery writes `unknown_after_restart` | outcome may be missing (no effect) |
| Checkpoint or chain check fails | instance stops admitting writes and forwarding; at start, does not serve | same |
| Identity or role store unreachable | 403 `permission_denied`, outcome recorded | same |
| Upstream timeout | 503 retryable, unknown outcome, retry with the same key | 503 retryable |

### 8. Order of work and the live-route gate
PLT-028 (spool) comes before PLT-029 (binding), per the README's spool-before-binding rule and Q-302. No live route is registered until all of these hold: PLT-028 to PLT-030 are merged with their tests; SEC-008 accepts records through the `AuditStore` port with receipts and checkpoints (Q-614); SEC-024 is accepted after its own security review and GOV-065 is accepted, so real roles may be read (ADR-0060 item 15); SEC-009 limits sit in front of the binding; Q-609 (stable session id) and Q-302 are answered and implemented; every `write` route has its deduplication provider (2.12, Q-613); the internal pre-public probe (6.3) has passed; and a security review by a different model has run on the bound gateway. The go-live row is G3, so no partner row in G2 waits on an Eldon row in G2 (ADR-0025).

## Alternatives rejected
- **Keep the in-memory deque and bind HTTP.** Fails README precondition 1.
- **Write audit synchronously into the tenant database (beside `adapter_audit_log`).** The gateway would need database credentials for every tenant, beyond ADR-0007 item 11's per-site impersonation credential; unauthenticated attempts have no tenant database; a tenant database outage would make denials unauditable.
- **Use the control-plane regional database (ADR-0040) or the regional role store (ADR-0060) as the audit store.** Both have their own custody rules (`S22`, ADR-0060 item 6); choosing the audit store of record is SEC-008's decision.
- **Write-through to the store of record on every request.** Every request then fails when the store is briefly unreachable; kept as a possible per-route option.
- **Startup-only chain verification, or an ack of the highest `seq` only.** Cannot detect suffix deletion, file rollback or a partially committed batch (2.6, 2.8).
- **An edge idempotency store.** Duplicates the store that already owns each operation's deduplication (2.12) and adds a restore story.
- **Rely on WSGI or a reverse proxy alone for HTTP safety.** WSGI cannot see framing; a proxy alone can be misconfigured. Both layers are required (1.2).

## Consequences
- Easier: PLT-024's preconditions become concrete, testable rows; gateway, Tool API and adapter records join on one id through the existing `correlationId`; crash, outage, restart and tampering behaviour is specified per case.
- Harder: each instance needs a persistent, encrypted, in-country volume, a lock discipline and a per-instance store credential; scaling down needs a drain; operators own quarantine and unknown-outcome alerts; the production listener needs a licence record; the live route waits on SEC-008, SEC-009, SEC-024 and GOV-065 (all earlier gates than the go-live row) and on Q-609, Q-302 and Q-613.
- Residual risks: a lost volume loses up to the 300 s window of unforwarded records (2.11); records written after the last head report can be removed undetected by someone with volume write access (2.6); unknown outcomes need a human until Q-611; timing side channels are not covered (6.4); all (P) values, the SQLite overhead factor and crash durability on the production volume are UNVERIFIED.
- Must be done: PLT-028 to PLT-031; Q-609 to Q-614 answered by Eldon's lane; the ADR-0040 deprovisioning probe (5.5) by its owner.
