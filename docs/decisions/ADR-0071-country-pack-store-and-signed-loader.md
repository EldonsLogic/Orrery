# ADR-0071: The country pack loader reads signed, published pack versions from the pack store, pinned per tenant, and fails closed

Status: Proposed
Owner: partner
Approved by: pending (security review by a different model, then Eldon line by line; RULES 42 because this touches compliance, keys and the audit trail)

Plan ID: CMP-039 (design only; no code until this ADR is reviewed). Interface partner: CMP-038 (staff pack publishing, Eldon). Items marked **(P)** are proposals Eldon can change; the questions are Q-652 to Q-657. Internal document. Revision 2 (review round 1) is noted at the end.

## Context
- Today the loader reads `<packs_dir>/<country>/<version>/pack.json` from the repo (`components/compliance/country_pack/loader.py`, `load_country_pack`). In production the go-live gate (CMP-034 to CMP-036; [ADR-0063](ADR-0063-country-pack-certification-record.md), [ADR-0067](ADR-0067-country-pack-production-blockers-and-product-choice.md)) checks the certification records in `manifest.json` and `evidence.json`, which `certification.py` reads again from the same directory (`certification_refusals(pack, directory)`).
- ADR-0063 says plainly that these checks "validate recorded approvals; they cannot establish accountant qualifications or authenticate a sign-off or founder identity". Nothing proves that the files the loader reads are the files the two people approved.
- `environment`, `version` and `allow_unpinned` are caller arguments (`resolve_country_pack`; `components/compliance/company_calendar/settings.py` passes them through). `environment` defaults to `"production"`; of about 100 calls in `components/compliance/`, 39 rely on that default and 64 pass `environment`. Without a version, `load_country_pack` picks the highest version in the directory.
- CMP-038 (Eldon, G3) builds the publishing workflow: a draft version with evidence, a diff, two sign-offs (a named accountant plus a founder, never the same person, MFA), publish, scheduled tenant upgrades and an urgent path with a mandatory follow-up review. The platform spec gives the tenant registry the pinned pack version and asks for canary and rollback of pack upgrades ([../specs/05-platform.md](../specs/05-platform.md) item 9 and its tenant registry; [../architecture/country-packs.md](../architecture/country-packs.md) compiler step 5 stores the resolved locale with the compiled artifact).
- Signing keys stay in the KMS behind ADR-0038's `Signer` ([ADR-0038](ADR-0038-secrets-management.md) item 2). ADR-0068 (Proposed, PR #309, not on main) uses the same shape for its DDL grant: ed25519 in the KMS, verifier holds public keys by `kid`, canonical JSON payload. Step-up MFA is an MFA sign-in within 300 s; action-bound step-up (F2) and WebAuthn (F1) are not built, and staff move to WebAuthn before the first real tenant ([ADR-0047](ADR-0047-mfa-design.md), Proposed, items 4 and 8).
- Founder decisions on PR #316 (2026-11-25): (1) SEC-008 owns the audit record format and the `AuditStore` port; (3) platform security events go to a separate in-country platform security stream owned by SEC-008, kept out of the tenant audit.
- Lanes: `components/` is the partner's; `services/control-plane/` (publisher, tenant registry) and `contracts/` are Eldon's (`scripts/lanes.json`). ADR-0025: a row never depends on the other founder's row in the same or a later gate.

## Decision

### 0. Words
- **Pack store**: the versioned store CMP-038 writes and the loader reads. Its product and location are CMP-038's choice; the loader sees it only through a read port.
- **Bundle**: the files of one pack version. **Record**: the signed published pack version record. **Index**: the signed per-country list of published, withdrawn and follow-up states plus the floor. **Pin**: the tenant registry's choice of version for one tenant.
- **Site class**: `sandbox`, `test` or `production` (ADR-0059, ADR-0068). **Key environment**: the deployment the signing key belongs to (`production`, `staging`, `dev`; ADR-0018 keeps them separate). **Deployment key environment**: read from deployment configuration at first use, then fixed for the process, never from a caller; absent or unknown counts as `production` (fail closed).
- **Digest**: every digest field in this ADR is `sha256:` followed by 64 lowercase hex characters; anything else refuses as malformed.

### 1. Interface between CMP-038 (publisher) and CMP-039 (loader)
1.1 **(P) Closed file set.** A bundle is exactly `pack.json`, `manifest.json`, `evidence.json` and, only where the version has one, `strings.json`. No other name, no directories, no symlinks or other non-regular files, each file at most 1 MiB, UTF-8 without a byte order mark. Every file, `strings.json` included, is parsed with `loads_strict` (duplicate keys refuse). The loader refuses a bundle with a missing required file or any extra file (`file_set_invalid`).

1.2 **(P) Content digest over exact bytes, not re-serialised JSON.** For each file, a digest over its exact stored bytes. Then `contentDigest` is the digest of `C`, the canonical JSON of `{"countryCode", "packId", "version", "files": [{"path", "sha256", "size"}]}` with `files` sorted by `path`. Canonical JSON means RFC 8785 JCS: no whitespace between tokens, property names sorted by UTF-16 code units, fixed string escaping, UTF-8 output (https://www.rfc-editor.org/rfc/rfc8785 sections 3.2.1 to 3.2.4, accessed 2026-11-26), restricted further to integers 0 to 2^53-1 and no lone surrogates. The shared vectors (CMP39-T07, T42), with a non-ASCII string and a key-order case, are binding where an implementation disagrees. Hashing exact file bytes avoids any number or Unicode question inside the pack. The loader reads each file once into memory, hashes those bytes and parses those same bytes; every later check, including the existing gate, runs on the in-memory bundle and never reads the store or a disk path again.

1.3 **(P) Published pack version record** (`typ: country_pack_version`). Every field is required unless marked optional; unknown keys refuse.

| Field | Content |
|---|---|
| `v`, `typ`, `kid` | `1`; `country_pack_version`; the signing key id |
| `keyEnv` | `production`, `staging` or `dev`; must equal the key's environment in the trust file and the deployment key environment |
| `publishId`, `publishedAt`, `publishedBy` | The publish record: ULID; RFC 3339 UTC time the publish service signed; staff subject who triggered the publish, which must be one of the two `signerId`s (so a third person cannot publish what two others approved without being recorded) |
| `packId`, `countryCode`, `componentId`, `version` | as in `pack.json`; must match it byte for byte after parse |
| `contentDigest`, `files` | 1.2 |
| `predecessor` | `{version, contentDigest}` of the highest published or withdrawn release with a lower semver than `version`, or `null` for the first; a republish names the same predecessor as the record it replaces |
| `supersedes` | `null`, or on a republish the `publishId` of the record it replaces: same `packId`, `version` and `contentDigest`, two fresh sign-offs, an active key |
| `changeKind` | `scheduled` or `urgent` |
| `followUp` | `{required: true, reviewRef}` when `urgent`; `{required: false}` otherwise |
| `diffDigest` | digest of the diff the signers were shown (CMP-038 defines the diff; the loader only binds it) |
| `evidenceRefs` | at least one `{id, sha256}` naming CMP-038 evidence items; the loader checks shape, never fetches |
| `signOffs` | exactly two entries, item 1.4 |

1.4 **(P) Sign-off entry.** `role` (`market_accountant` or `founder`), `signerId` (stable staff identity subject), `signedAt`, `statementDigest`, `mfa: {assertionRef, method, authTime, boundTo: {signerId, statementDigest}}`; for the accountant also `name`, `market` and `signOffRef`; for the founder also `founderLogin`. `statementDigest` is the digest of the canonical JSON of `{packId, version, contentDigest, diffDigest, changeKind}`: each person signs off this exact content and diff. `assertionRef` points to the step-up event in the identity audit; `boundTo` names the person and statement that step-up was bound to (ADR-0047 F2; until F2 it is the publisher's attestation).

1.5 **(P) Envelope and signature.** Token = `cpr1.` + base64url without padding of the payload + `.` + base64url without padding of the signature. The payload is canonical JSON as in 1.2, at most 64 KiB, parsed strictly: duplicate keys, unknown or missing keys, fractions, exponents, integers outside 0 to 2^53-1 and padding refuse. The ed25519 signature covers the ASCII bytes `country-pack-record-v1\n` followed by the payload bytes, so a signature from another key or record type (for example ADR-0068's grant) cannot verify here. The index (1.6) uses the same envelope with prefix `cpi1.` and domain string `country-pack-index-v1\n`.

1.6 **(P) Country index, floor and withdrawal** (`typ: country_pack_index`, one per key environment and country). Fields: `v`, `typ`, `kid`, `keyEnv`, `countryCode`, `indexSeq` (integer, plus one on every change), `issuedAt`, `published` (list of `{version, contentDigest, publishId}`, one entry per version; a republish replaces that entry's `publishId`), `withdrawn` (list of `{version, contentDigest, reasonRef}`; a withdrawn version never appears in `published` again), `floor` (lowest version any tenant may be pinned to), `followUpOpen` (list of `publishId`), `changeRecords` (list of `{id, kind, sha256}` for every withdrawal, floor raise and follow-up closure). CMP-038 issues a new index on every publish, republish, withdrawal, floor raise and follow-up closure. A withdrawal, a floor raise and a follow-up closure need the same two-person sign-off as a publish, carried in a signed change record the index lists by id (CMP-038 defines its body; the loader checks only the index). **(P) Write order:** CMP-038 writes the new index to the store first, then sets the registry's per-country `minIndexSeq` to its `indexSeq` (3.1), so the registry never names a sequence the store does not yet serve. Rules the loader enforces: `withdrawn` entries never leave the list; `floor` never falls; `indexSeq` is at least the high-water mark, the pin's `indexSeqAtPin` and the registry's `minIndexSeq` (item 2 step 4).

1.7 **(P) Keys and loader trust files.**
- A new KMS ed25519 key, inventory entry "country pack publish signing key"; the SEC-002 owner assigns its `S` number (ADR-0068 proposes `S24` on an unmerged PR, so no number is taken here). Used only through ADR-0038's `Signer`; only CMP-038's publish service workload identity may sign; key administration is a separate identity (SEC2-019). Production, staging and dev keys are separate.
- Verification keys live in a reviewed data file beside the loader, `components/compliance/country_pack/trusted_publish_keys.json` (built by CMP-042), outside every pack version, as ADR-0067 keeps `product_choice_paths.json`. Each entry: `kid`, `keyEnv`, `publicKey`, `status` (`active`, `retired`, `revoked`). Adding a key is a PR with the other founder's review, then a deploy; the store can never add a trusted key. An optional deployment deny-list (configuration, read at start) can only add revocations, so an emergency revocation does not wait for a PR. Where the trust root lives is Q-656.
- Founder signer identities live in a second reviewed file beside the loader, `trusted_signers.json` (CMP-042): entries `{signerId, founderLogin}`, one to one (no `signerId` or login twice), each login in the `scripts/lanes.json` founders map. How it is filled and kept in step with the staff identity system is Q-653.
- A missing, unreadable or malformed trust file or signer file, or a configured deny-list that cannot be read, refuses every store-path load (`trust_config_unavailable` S).
- Rotation: the new `kid` ships as `active` before the publisher switches; the old key becomes `retired`. A record signed by a retired key still verifies if the current index, signed by an active key, lists its exact `contentDigest` and `publishId`; a retired key never verifies an index.
- Revocation: a `revoked` key verifies nothing, record or index. Versions it signed refuse until CMP-038 republishes them (`supersedes`, 1.3) under a new key with two fresh sign-offs.
- Key loss (destroyed or unusable private key, not compromise): loads continue, because the public key is in the trust file; publishing stops until a new key ships.
- Test vectors use a throwaway key whose private half is discarded after generation; its `kid` has `keyEnv: dev` and is refused in any other deployment.

1.8 **What the loader can and cannot prove.** With one publisher key, the two sign-offs, their roles and their MFA are the publisher's signed attestation, and so are the index and every withdrawal, floor raise and follow-up closure behind it: the loader checks no sign-off on those. The loader checks that the attestation is complete and consistent (item 2, step 9) and that the signed content is the content it loads; it cannot prove that two people really signed or that MFA happened. A compromised publish service or key defeats the two-person rule for records and index changes alike (T06). Per-signer signatures the loader can verify, for records and change records, are Q-652. **(P) under Q-652:** in `keyEnv: production` the allowed `mfa.method` set becomes `webauthn` only once ADR-0047 F1 ships, as ADR-0047 item 8 requires for staff before the first real tenant; until then it is `totp` and `webauthn`, a reviewed code constant.

1.9 **Loader-side trust data never comes from the store.** `pack.schema.json`, the component manifest contract, the founders map (`scripts/lanes.json`), `product_choice_paths.json`, the registered component providers for `requires`, and the two trust files of 1.7 come from the deployed code. A published version that needs a provider version the deployment lacks is refused by the existing gate (`go_live_refused`); CMP-038's schedule must only target deployments that carry the provider.

1.10 **(P) Repo-bundled packs** stay for sandbox and test site classes (ADR-0059) and for unit tests. They carry no record.
- **One tenant entry**, `resolve_tenant_country_pack(context, company_overrides)` (CMP-044), serves all tenant work. `PinSource` returns `{siteClass, pin, minIndexSeq}`; `pin` is a store pin (`source: store`, 3.1) or, for sandbox and test only, a repo pin `{source: repo, packId, version}` (shape (P), Q-655). A store pin always uses the store and never falls back to repo packs, whatever the store answers; a repo pin uses the entry's own private repo reader, so it works in any deployment; a repo pin on a production site class refuses `unsigned_repo_pack`; no pin refuses `pin_missing`.
- **Directory functions** (`load_country_pack`, `resolve_country_pack`) keep their signatures, default and gate behaviour, but refuse every call with `unsigned_repo_pack` when the deployment key environment is `production` (or absent), whatever `environment` the caller passes. The test packages set `dev` in their `tests/__init__.py` (CI runs `unittest discover` per package), so the existing calls, including the production-mode gate tests in `test_country_pack_go_live_gate.py`, `test_production_rules.py`, `test_production_review_fixes.py`, `test_pack_*.py` and `test_company_calendar.py`, run unchanged and keep their messages.
- **`company_calendar/settings.py`** gains `resolve_tenant_calendar_settings(context, ...)` on the tenant entry for tenant work; the existing `resolve_calendar_settings(country, packs_dir, ...)` stays as a directory helper under the same deployment guard. An import guard test fixes the allowlist of modules outside the package that may import the directory functions or that helper: `company_calendar/settings.py`, `company_calendar/__init__.py` (re-export) and the two test packages (CMP39-T32). Signing repo packs the same way is rejected below.

### 2. Loader rules (fail closed, in this order)
New refusals raise a `PackStoreRefusal(CountryPackError)` carrying a stable `code`. Existing refusal messages and classes are unchanged (tests pin them); the existing gate's reasons travel inside `go_live_refused`. Codes marked S also emit a platform security event (item 5).

| Step | Check | Code |
|---|---|---|
| 1 | Tenant id from the authenticated context; site class, pin and `minIndexSeq` read through `PinSource`, never from caller arguments; repo and store pins as in 1.10. A caller `environment` that differs from the site class refuses; a caller `version` that differs from the pin refuses; `allow_unpinned` and `allow_test_packs` refuse on the store path | `environment_mismatch`, `pin_missing`, `registry_unavailable`, `version_not_pinned`, `unpinned_refused`, `unsigned_repo_pack` |
| 2 | Read the trust files and the verified state; fetch the country index. Only a store transport failure (no answer, timeout, store error status) may fall back to the verified cache (item 6); fetched bytes that fail any later step refuse with that step's code, never fall back | `trust_config_unavailable` S, `verified_state_unavailable`, `verified_state_unseeded`, `store_unavailable` |
| 3 | Index: strict parse, active non-revoked `kid` of this key environment, signature, `countryCode`; `published` versions unique and none of them in `withdrawn` | `index_malformed`, `key_unknown` S, `key_revoked` S, `key_wrong_environment` S, `signature_invalid` S |
| 4 | Index freshness: `indexSeq` at least max(high-water mark, pin `indexSeqAtPin`, `minIndexSeq`), `floor` not lower, no withdrawal dropped; then raise the high-water mark by compare-and-set (a write never lowers it; if the stored mark is already higher, re-read the state and re-fetch the index once, then apply this step again). | 6 | Fetch record and bundle bytes once; strict parse; digest formats; `kid` rules of 1.7; signature | `record_missing`, `record_malformed`, `key_*` S, `signature_invalid` S |
| 7 | Record `packId`, `countryCode`, `version`, `keyEnv` equal the pin and the deployment; `publishId` equals the index entry; `predecessor` lower and, where the index lists that version, with the same digest; `supersedes` null or another `publishId` | `record_mismatch` S, `predecessor_invalid` |
| 8 | Closed file set; per-file hashes; recomputed `contentDigest` equals the record and the pin | `file_set_invalid` S, `content_digest_mismatch` S |
| 9 | Sign-offs: exactly two; one `market_accountant`, one `founder`; different `signerId`; `publishedBy` is one of them. Founder: `signerId` maps to `founderLogin` in `trusted_signers.json`, the login is in the founders map and maps to `evidence.json` `certification.founder`. Accountant: `signerId` is not a founder `signerId`; `name` after NFKC and casefold is no founder login or founder name in the founders map (those hold logins and `eldon`/`partner` only, so a founder's legal name under another spelling is not caught; the `signerId` check is the control); `name`, `market` and `signOffRef` equal `evidence.json` `certification.accountant`; `market` equals the country. Both: `statementDigest` recomputed and equal; `mfa` present, `method` in the allowed set (1.8), `assertionRef` non-blank and different from the other's, `boundTo` equals the entry's own `signerId` and `statementDigest`, 0 s at most `signedAt - authTime` at most 300 s; every `signedAt` at most `publishedAt`; `publishedAt` not after now plus 30 s | `signoff_count` S, `signoff_same_person` S, `signoff_role` S, `signoff_certification_mismatch` S, `signoff_statement_mismatch` S, `signoff_mfa` S |

Production never selects "latest": the only version it loads is the pin. Every check runs on every load, including cache hits. The loader returns the resolved pack plus provenance `{source: store or cache, publishId, contentDigest, kid, indexSeq, urgent, followUpOpen}`.

### 3. Per-tenant pinning
3.1 **(P) The pin lives in the tenant registry** (control plane, Eldon's lane): `tenantId`, `source` (`store`, or `repo` for sandbox and test, 1.10), `countryCode`, `packId`, `version`, `contentDigest`, `publishId`, `pinSeq` (plus one per change), `indexSeqAtPin` (the index sequence the registry verified when it pinned), `changeKind` (`initial`, `upgrade`, `rollback`, `republish`), `changedBy`, `approvalRef`, `changedAt`. Per country the registry also holds `minIndexSeq`, advanced on every publish, republish, withdrawal, floor raise and follow-up closure in the write order of 1.6; `PinSource` returns it with the pin, so a withdrawal or floor raise after the pin still raises the loader's freshness floor without loader state. Tenants keep the exact version in their compiled artifact as today ([../compliance/country-pack-framework.md](../compliance/country-pack-framework.md) section 5); the registry pin is what the loader trusts. The loader reads the registry through `PinSource` and never writes it. Binding the pin to the digest means a store that serves another record for the same version number refuses (`pin_digest_mismatch`).

3.2 **Pin changes: `check_upgrade(tenant, target)`.** The CMP-038 schedule names a country, a target version and tenant cohorts, canary first; the registry calls `check_upgrade` for each tenant and for every pin change. It runs the full item 2 checks against the target, then the tenant's current company overrides merged against the target (the existing override rules), then the rule for the direction, reading `compatibilityRange` (P) as the versions a release may be upgraded from (the schema and the framework do not define it: UNVERIFIED, settled under Q-655):
- **Upgrade** (target higher): the target's `compatibilityRange` contains the current version, and the target's `migrationRequired` is false (true, required on a major version by the framework, stops the automatic move until a named migration step exists, not in this ADR).
- **Rollback** (target lower): the current version's `migrationRequired` is false and the target is inside the current version's `compatibilityRange`; the target's own policy, signed before the current version existed, is not used. It also needs an approval (who approves is Q-655; (P) one founder with step-up and a written reason).
- **Republish** (same version): same `packId` and `contentDigest`, the target's `supersedes` equals the current `publishId`, a newer `publishId`, an active key.
Only on a pass does the registry move the pin and emit a pin event. A failure leaves the pin, records the reason code and alerts.

3.3 **Rollback and downgrade, defined.** A *rollback* is a registry move to a lower version that is in the index, not withdrawn, at or above the floor, and passes `check_upgrade` (3.2) with its approval. A *downgrade* is anything else that would make a tenant run older content: a pin to a withdrawn or below-floor version, a store serving an older record or index, or a caller asking for a version other than the pin. The loader refuses every downgrade (item 2, steps 1, 4, 5, 7). When an older version must never run again, CMP-038 withdraws it or raises the floor.

3.4 **In-flight periods.** A pin change never applies backwards: the compiler stores the resolved locale with the compiled artifact (country-packs compiler step 5), so a change takes effect at the next compile and apply, and every load event records the version and digest used. The pack schema holds no rates or dated statutory values today: `tax` carries `taxCodesRef`, `filingPeriods` and `roundingRule`; where rates live is outside the pack (UNVERIFIED). Which treatment applies to a supply when a VAT period straddles a rate change (by invoice date, supply date or transitional rule) is a tax fact for each market: UNVERIFIED for Saudi Arabia, the UAE, Egypt and Qatar, routed to the market accountant through CMP-038's evidence. The loader decides none of it. (P) The schedule moves pins only at a boundary the accountant signed off for that change; a law that needs both treatments inside one period needs dated values in the pack, which is a separate schema row (Q-657).

### 4. Urgent changes
The urgent path keeps the full two-person rule: the record says `changeKind: urgent` and `followUp.required: true`, and step 9 applies unchanged. The loader does not refuse an urgent version because its follow-up is open (refusing would block a legal change); every load, upgrade check and pin event carries `urgent: true` and `followUpOpen` from the index. CMP-038 closes the follow-up by a two-person change record that removes the `publishId` from `followUpOpen`; the outcome is either confirmed, or superseded by a new version with a floor raised above the urgent one. Whether an open follow-up stops rollout beyond the canary cohort is Q-657.

### 5. Audit
- Every store-path load, refusal, upgrade check, index advance and verified-state seed is an audit event through an `AuditSink` port; SEC-008 owns the format and the store (decision 1 on #316). Events: `country_pack.loaded`, `country_pack.load_refused`, `country_pack.upgrade_checked`, `country_pack.index_advanced`, `country_pack.state_seeded`; the registry emits `country_pack.pin_changed`. Fields: tenant, site class, caller service, correlation id, pack id, country, version, `contentDigest`, `publishId`, `kid`, `indexSeq`, source, `urgent`, `followUpOpen`, reason code and step. Never pack contents, never the envelope bytes; a refused envelope is recorded by its sha256.
- Codes marked S in item 2 also go to SEC-008's platform security stream (decision 3 on #316), without tenant content.
- **(P)** Store-path events are written through: if the audit write fails, the load refuses `audit_unavailable` (this is a proposal, not a founder decision). Repo-path loads in sandbox and test log best effort.

### 6. Store outage and verified state
**(P) Cached last verified version, bounded.** The loader keeps a verified state (behind a `VerifiedState` port): per country the high-water `indexSeq`, the highest floor and every withdrawal it has seen, plus the last verified index with `lastVerifiedAt` (the loader's clock when it last verified an index fetched from the store) and the bundle bytes and record for pinned versions. Only on a store transport failure (step 2) may it serve the tenant's pinned version from the cache, and only while `lastVerifiedAt` is not in the future and now minus `lastVerifiedAt` is within a configured staleness bound; every item 2 check still runs on the cached bytes against the current trust files, deny-list and the registry's current `minIndexSeq`, so a withdrawal or floor raise published during the outage refuses the cache as soon as the registry carries it. No configured bound means no cache: refuse `store_unavailable`. A registry outage always refuses (`registry_unavailable`), because the pin and `minIndexSeq` are never cached. When the loader runs: at compile and apply (compiler step 1 resolves the pack version) and whenever a component resolves pack values for a tenant, as `company_calendar/settings.py` does. Rationale: a tenant already on a verified version should not stop compiling, applying or resolving its calendar because the store blinked.

**Verified state (P).** Durable, shared by all loader instances of a deployment, never per instance; every update is an atomic compare-and-set that never lowers a high-water mark or floor and never drops a withdrawal. An unreadable state or a failed write refuses (`verified_state_unavailable`). In a `production` deployment an empty state (new deployment, or after loss) never trusts the first index it sees: loads refuse `verified_state_unseeded` until an audited seed (`seed_verified_state(country)`, run by an operator, `country_pack.state_seeded`) fetches and fully verifies an index at or above the registry's `minIndexSeq`. Staging and dev deployments seed that way automatically on first load. The bound, who may run the seed and where the state lives are Q-654.

## Alternatives rejected
- **Digest over re-serialised JSON.** Number and Unicode canonicalisation would need their own rules and tests; hashing the exact stored bytes needs none and the loader parses the bytes it hashed.
- **HMAC instead of a signature.** The loader would hold the minting secret, so a compromised loader host could publish packs (ADR-0068 item 6 makes the same point).
- **Trust keys from the pack store.** Whoever writes the store could then add a key; the trust root must be reviewed outside it.
- **Signing repo packs the same way and allowing them in production.** It adds a second publishing route outside CMP-038's two-person workflow; repo packs stay drafts for sandbox and test.
- **Refuse every load during a store outage.** Safe but it stops invoicing for tenants already on a verified version; kept as the behaviour when no bound is configured.
- **Trust on first use of an empty verified state in production.** A store rolled back while the state was lost would be accepted; the registry's `minIndexSeq` and an audited seed replace it.
- **Refuse urgent versions until the follow-up closes.** It would block the legal change the urgent path exists for.
- **Revocation flags inside `evidence.json`.** ADR-0067's closed key set refuses them, and the pack under review must not decide its own validity; withdrawals live in the signed index.
- **Moving every existing production-mode test to the in-memory gate.** 39 calls rely on the `production` default and many more pass it; the deployment guard (1.10) keeps them unchanged at no loss of protection.

## Consequences
- Production tenants can only run pack content that CMP-038 published with both sign-offs recorded and that has not been withdrawn or fallen below the floor; the repo packs never reach production.
- Harder: the loader gains two trust files, a store port, verified state with a seed step and an audit dependency; every production load needs the registry, and either the store or a fresh cache; CMP-038 must keep the index-then-registry write order.
- Residual, stated plainly: the loader cannot detect a compromised publish service or key, for records or index changes (T06), until Q-652 adds per-signer signatures; it proves records, not accountant qualifications (as ADR-0063 says); a founder's legal name used as an accountant name is caught only through `signerId`; tax transitions are not modelled (3.4, UNVERIFIED).
- A withdrawal, a floor raise or a key revocation refuses every tenant still pinned to the affected version at its next load, store path and cache alike. CMP-038 must move those tenants' pins (upgrade, rollback or `republish`) before or together with that change, and alert on any tenant left behind.
- CMP-038 must produce exactly the formats of item 1 and pass the shared vectors (CMP39-T07, T42); the registry must hold the pin and `minIndexSeq` of 3.1. Tier 3 line-by-line review and a different-model security review are required before Accepted; neither is claimed here.
