## Context
- Today the loader reads `<packs_dir>/<country>/<version>/pack.json` from the repo (`components/compliance/country_pack/loader.py`, `load_country_pack`). In production the go-live gate (CMP-034 to CMP-036; [ADR-0063](ADR-0063-country-pack-certification-record.md), [ADR-0067](ADR-0067-country-pack-production-blockers-and-product-choice.md)) checks the certification records in `manifest.json` and `evidence.json`, which `certification.py` reads again from the same directory (`certification_refusals(pack, directory)`).
- ADR-0063 says plainly that these checks "validate recorded approvals; they cannot establish accountant qualifications or authenticate a sign-off or founder identity". Nothing proves that the files the loader reads are the files the two people approved.
- `environment`, `version` and `allow_unpinned` are caller arguments (`resolve_country_pack`; `components/compliance/company_calendar/settings.py` passes them through). `environment` defaults to `"production"`; of about 100 calls in `components/compliance/`, 39 rely on that default and 64 pass `environment`. Without a version, `load_country_pack` picks the highest version in the directory.
- CMP-038 (Eldon, G3) builds the publishing workflow: a draft version with evidence, a diff, two sign-offs (a named accountant plus a founder, never the same person, MFA), publish, scheduled tenant upgrades and an urgent path with a mandatory follow-up review. The platform spec gives the tenant registry the pinned pack version and asks for canary and rollback of pack upgrades ([../specs/05-platform.md](../specs/05-platform.md) item 9 and its tenant registry; [../architecture/country-packs.md](../architecture/country-packs.md) compiler step 5 stores the resolved locale with the compiled artifact).
- Signing keys stay in the KMS behind ADR-0038's `Signer` ([ADR-0038](ADR-0038-secrets-management.md) item 2). ADR-0068 (Proposed, PR #309, not on main) uses the same shape for its DDL grant: ed25519 in the KMS, verifier holds public keys by `kid`, canonical JSON payload. Step-up MFA is an MFA sign-in within 300 s; action-bound step-up (F2) and WebAuthn (F1) are not built, and staff move to WebAuthn before the first real tenant ([ADR-0047](ADR-0047-mfa-design.md), Proposed, items 4 and 8).
- Founder decisions on PR #316 (2026-11-25): (1) SEC-008 owns the audit record format and the `AuditStore` port; (2) each tenant audit entry records the per-tenant `memberRef` plus `token_id`, no global user id; (3) platform security events go to a separate in-country platform security stream owned by SEC-008, kept out of the tenant audit; (6) one audit id runs end to end, and the engine adapter adds a correlation id per engine call. - Eldon's CMP-038 slice 4 (PR #362, contract 0.3.0) and the change-record code of PR #360 (`services/control-plane/packpublish/workflow.py`) are the publisher side: each index lists only the change it makes (`changeRecords` is `[]` on a publish index), chained to the previous index by `predecessorDigest`, and a withdrawal also drops that version's open follow-up.

## Decision

### 0. Words
- **Pack store**: the versioned store CMP-038 writes and the loader reads. Its product and location are CMP-038's choice; the loader sees it only through a read port.
- **Bundle**: the files of one pack version. **Record**: the signed published pack version record. **Index**: the signed per-country list of published, withdrawn and follow-up states plus the floor. **Pin**: the tenant registry's choice of version for one tenant.
- **Site class**: `sandbox`, `test` or `production` (ADR-0059, ADR-0068). **Key environment**: the deployment the signing key belongs to (`production`, `staging`, `dev`; ADR-0018 keeps them separate). **Deployment key environment**: read from deployment configuration at first use, then fixed for the process, never from a caller; absent or unknown counts as `production` (fail closed). The composition root hands it to the store-path loader at construction; tests of production behaviour construct their own loader with a fake configuration (1.7).
- **Digest**: every digest field in this ADR is `sha256:` followed by 64 lowercase hex characters; anything else refuses as malformed.

### 1. Interface between CMP-038 (publisher) and CMP-039 (loader)
1.1 **Closed file set** (the contract's `files` rule). A bundle is exactly `pack.json`, `manifest.json`, `evidence.json` and, only where the version has one, `strings.json`. No other name, no directories, no symlinks or other non-regular files, each file at most 1 MiB, UTF-8 without a byte order mark. Every file, `strings.json` included, is parsed with `loads_strict` (duplicate keys refuse). The loader refuses a bundle with a missing required file or any extra file (`file_set_invalid`).

1.2 **Content digest over exact bytes, not re-serialised JSON** (as the contract fixes `contentDigest`). For each file, a digest over its exact stored bytes. Then `contentDigest` is the digest of `C`, the canonical JSON of `{"countryCode", "packId", "version", "files": [{"path", "sha256", "size"}]}` with `files` sorted by `path`. Canonical JSON means RFC 8785 JCS: no whitespace between tokens, property names sorted by UTF-16 code units, fixed string escaping, UTF-8 output (https://www.rfc-editor.org/rfc/rfc8785 sections 3.2.1 to 3.2.4, accessed 2026-11-26), restricted further to integers 0 to 2^53-1 and no lone surrogates. The shared vectors (CMP39-T07, T42), with a non-ASCII string and a key-order case, are binding where an implementation disagrees. Hashing exact file bytes avoids any number or Unicode question inside the pack. The loader reads each file once into memory, hashes those bytes and parses those same bytes; every later check, including the existing gate, runs on the in-memory bundle and never reads the store or a disk path again.

1.3 **Published pack version record** (`typ: country_pack_version`; `contracts/country-pack-record.schema.json`, the authority). Summary: every field is required unless the schema says optional; unknown keys refuse.

| Field | Content |
|---|---|
| `v`, `typ`, `kid` | `1`; `country_pack_version`; the signing key id |
| `keyEnv` | `production`, `staging` or `dev`; must equal the key's environment in the trust file and the deployment key environment |
| `publishId`, `publishedAt`, `publishedBy` | The publish record: ULID; RFC 3339 UTC time the publish service signed; staff subject who triggered the publish, which must be one of the two `signerId`s (so a third person cannot publish what two others approved without being recorded) |
| `packId`, `countryCode`, `componentId`, `version` | as in `pack.json`; must match it byte for byte after parse |
| `contentDigest`, `files` | 1.2 |
| `predecessor` | `{version, contentDigest}` of the highest published or withdrawn release with a lower semver than `version`, or `null` for the first; a republish names the same predecessor as the record it replaces |
| `supersedes` | `null`, or on a republish the `publishId` of the record it replaces: same `packId`, `version` and `contentDigest`, two fresh sign-offs, an active key |
| `changeKind` | `scheduled` or `urgent` |
| `followUp` | `{required: true, reviewRef}` when `urgent`; `{required: false}` otherwise |
| `diffDigest` | digest of the diff the signers were shown (CMP-038 defines the diff; the loader only binds it) |
| `evidenceRefs` | at least one `{id, sha256}` naming CMP-038 evidence items; the loader checks shape, never fetches |
| `signOffs` | exactly two entries, item 1.4 |

1.4 **Sign-off entry** (the record schema's `accountantSignOff` and `founderSignOff`). `role` (`market_accountant` or `founder`), `signerId` (stable staff identity subject), `signedAt`, `statementDigest`, `mfa: {assertionRef, method, authTime, boundTo: {signerId, statementDigest}}`; for the accountant also `name`, `market` and `signOffRef`; for the founder also `founderLogin`. `statementDigest` is the digest of the canonical JSON of `{packId, version, contentDigest, diffDigest, changeKind}`: each person signs off this exact content and diff. `assertionRef` points to the step-up event in the identity audit; `boundTo` names the person and statement that step-up was bound to (ADR-0047 F2; until F2 it is the publisher's attestation). Each entry may carry `signerSignature` (`format: "webauthn.get.v1"`, `credentialId`, `authenticatorData`, `clientDataJSON`, `signature`), the signer's own WebAuthn assertion over `statementDigest`; in `keyEnv: production` both entries must carry it and `mfa.method` must be `webauthn` (1.8). A change record's sign-offs use this same entry format (1.8).

1.5 **Envelope and signature** (defined here; the contract defers to this item). Token = `cpr1.` + base64url without padding of the payload + `.` + base64url without padding of the signature. The payload is canonical JSON as in 1.2, at most 64 KiB, parsed strictly: duplicate keys, unknown or missing keys, fractions, exponents, integers outside 0 to 2^53-1 and padding refuse. The ed25519 signature covers the ASCII bytes `country-pack-record-v1\n` followed by the payload bytes, so a signature from another key or record type (for example ADR-0068's grant) cannot verify here. The index (1.6) uses the same envelope with prefix `cpi1.` and domain string `country-pack-index-v1\n`. A change record has no envelope and no signature of its own: it is bound by the `sha256` the signed index lists for it (1.8).

1.6 **Country index, floor and withdrawal** (`typ: country_pack_index`, one per key environment and country; `contracts/country-pack-index.schema.json`, the authority). Fields: `v`, `typ`, `kid`, `keyEnv`, `countryCode`, `indexSeq` (integer from 1, plus one on every change), `predecessorDigest` (the digest of the exact payload bytes of the index with `indexSeq` minus one; `null` only at `indexSeq` 1), `issuedAt`, `published` (list of `{version, contentDigest, publishId}`, one entry per version; a republish replaces that entry's `publishId`), `withdrawn` (list of `{version, contentDigest, reasonRef}`; a withdrawn version never appears in `published` again), `floor` (lowest version any tenant may be pinned to), `followUpOpen` (list of `publishId`), `changeRecords` (list of `{id, kind, sha256}`). CMP-038 issues a new index on every publish, republish, withdrawal, floor raise, follow-up closure and key rotation (1.7). **`changeRecords` is a delta, not cumulative:** it lists only the change this index makes, so a publish, republish or rotation index carries `[]`, and a loader that is behind reads the indexes in between (item 2 step 3). A withdrawal, a floor raise and a follow-up closure need the same two-person sign-off as a publish, carried in the change record (1.8; outside production the loader checks only the index chain). **(P) Write order:** CMP-038 writes the new index to the store first, then sets the registry's per-country `minIndexSeq` to its `indexSeq` (3.1), so the registry never names a sequence the store does not yet serve. Rules the loader enforces: `withdrawn` entries never leave the list; `floor` never falls; `indexSeq` is at least the high-water mark, the pin's `indexSeqAtPin` and the registry's `minIndexSeq` (item 2 step 4); every index from the high-water mark to the latest links to its predecessor by `predecessorDigest` (item 2 step 3). Besides the latest index, records, bundles and change records, the `PackStore` read port serves `index(country, seq)`, one index by sequence, for that walk.

1.7 **Keys and loader trust files** (trust root as a reviewed data file: Q-656).
- A new KMS ed25519 key, inventory entry "country pack publish signing key"; the SEC-002 owner assigns its `S` number (ADR-0068 proposes `S24` on an unmerged PR, so no number is taken here). Used only through ADR-0038's `Signer`; only CMP-038's publish service workload identity may sign; key administration is a separate identity (SEC2-019). Production, staging and dev keys are separate.
- Verification keys live in one reviewed data file per key environment beside the loader, `components/compliance/country_pack/trusted_publish_keys.<keyEnv>.json` (built by CMP-042), outside every pack version; a build packages only its target environment's file and the loader reads only the file named by the deployment key environment, as ADR-0067 keeps `product_choice_paths.json`. Each entry: `kid`, `keyEnv`, `publicKey`, `status` (`active`, `retired`, `revoked`). Adding a key is a PR with the other founder's review, then a deploy; the store can never add a trusted key. An optional deployment deny-list (configuration) can only add revocations, so an emergency revocation does not wait for a PR. It is read at process start, so a deny-list entry takes effect only once every loader process restarts; the revocation runbook restarts them.
- **Only the deployment's own keys.** An entry whose `keyEnv` differs from the deployment key environment refuses every store-path load (`trust_config_unavailable` S), so the dev test key cannot reach production. Until CMP-045 ships (1.8) the production file holds no key, and a production deployment refuses every store-path load `store_path_not_live`. Tests of production behaviour use a key generated during the run, a fake deployment configuration and a fake `AssertionVerifier` (1.8), never a shipped file.
- **Signers** (Q-653) live in a second reviewed file beside the loader, `trusted_signers.json` (CMP-042): founder entries `{signerId, role: founder, founderLogin}`, each login in the `scripts/lanes.json` founders map; accountant entries `{signerId, role: market_accountant, market, name}`, the per-market roster of approved accountants, each a staff-realm identity with MFA always on (ADR-0047). Every entry also lists the signer's public WebAuthn credentials for 1.8. No `signerId` or login appears twice. Founders add or remove signers by a PR the other founder reviews; the loader refuses any signer not on it. An accountant who leaves is disabled in the staff realm at once, and the roster removal PR follows (Q-678); until it merges the loader still accepts that accountant on the roster (residual), and versions they signed earlier stay valid. A missing, unreadable or malformed trust file or signer file, or a configured deny-list that cannot be read, refuses every store-path load (`trust_config_unavailable` S).
- **Rotation, in this order** (CMP39-T46): (1) a deploy adds the new `kid` as `active` beside the old one, which stays `active`; (2) the publisher switches to the new key and issues a new index with it, `indexSeq` plus one, listing every published entry, and the registry's `minIndexSeq` follows in the 1.6 write order; (3) only in a later deploy, once every deployment's verified state and cache hold an index signed by the new key, the old key becomes `retired`. Retiring first would refuse every load, cache hits included, because every load re-runs its checks against the current trust file and a retired key never verifies an index (`key_retired` S). A record signed by a retired key still verifies if the current index, signed by an active key, lists its exact `contentDigest` and `publishId`. Every index on the chain walk (item 2 step 3) needs an active key too, as the contract says. Step (3) waits until, for every country, every deployment's high-water index is signed by the new key, so a normal walk never meets a retired key; a walk that does refuses `key_retired` until the runbook clears that country's verified state and an operator seeds it again (6).
- Revocation: a `revoked` key verifies nothing, record or index; versions it signed refuse until CMP-038 republishes them (`supersedes`, 1.3) under a new key with two fresh sign-offs, and a deployment whose chain walk reaches an index it signed refuses `key_revoked` until the revocation runbook clears that country's verified state and an operator seeds it again (6). Key loss (not compromise): loads continue, because the public key is in the trust file; publishing stops until a new key ships. Test vectors use a throwaway key whose private half is discarded after generation; its `kid` has `keyEnv: dev` and is refused in any other deployment.

1.8 **Two-person proof (Q-652): each signer signs with their own key.**
- With one publisher key, the sign-offs, their roles and MFA, and the index and its change records, are only the publisher's signed attestation; the loader can check it is complete and consistent (step 9), not that two people signed. In staging and dev that stays so, with `mfa.method` `totp` or `webauthn`.
- In `keyEnv: production`, every record sign-off and both sign-offs of every change record the loader verifies carry that signer's own passkey (WebAuthn) assertion over its `statementDigest`, in the sign-off's `signerSignature` (1.4), verified through an `AssertionVerifier` port against the signer's credential in `trusted_signers.json`; `mfa.method` must be `webauthn` (`signoff_assertion_invalid` S).
- **Assertion format: the contract's `signerSignature`** (`format: "webauthn.get.v1"`; contracts/country-pack-store.md (0.3.0, PR #362) assumption 4 and the record schema's `signerSignature`), checked as a WebAuthn get assertion (W3C WebAuthn Level 2 section 7.2; citation UNVERIFIED, checked in CMP-045): type `webauthn.get`, the staff origin and RP id from deployed code, user presence and verification flags set. **Challenge:** `clientDataJSON.challenge` is the base64url without padding of the 32 bytes SHA-256(`country-pack-signoff-v1` + LF + the ASCII `statementDigest`), the same rule for publish and change-record sign-offs. This domain-separated rule was proposed here and the contract adopted it in 0.3.0, so an assertion over a sign-off cannot be replayed for anything else; the contract states it and binds.
- **Change record: the contract's `country-pack-change-record.schema.json`** (written by CMP-038, read by the loader in production). Summary, the schema wins: `v` (`1`), `typ` (`country_pack_change_record`), `id`, `kind` (`withdrawal`, `floor_raise`, `follow_up_closure`), `countryCode`, `target` (`{version}` for a withdrawal or floor raise, `{publishId}` for a follow-up closure), `reasonRef`, `baseIndexSeq`, `baseIndexDigest`, `statementDigest`, `requestedBy`, `recordedAt`, `signOffs`; unknown keys refuse. It has no envelope and no publisher signature of its own: the signed index that lists it binds it by `changeRecords[].sha256`, the digest of the record's RFC 8785 canonical JSON (1.2). Its `statementDigest` is the digest of the canonical JSON of `{op: "pack_change", countryCode, kind, target, reasonRef, baseIndexDigest}`, so each signer approves one change against one exact index.
- **Verifying a change record** (production, item 2 step 3), for the one record an index lists (`change_record_invalid` S unless a sign-off code below applies):
  - fetch it by `id`; the fetched bytes must parse strictly and be exactly their own RFC 8785 canonical form, their digest must equal the listed `sha256`, and its `id` and `kind` must equal the listing entry;
  - `countryCode` equals the index's; `baseIndexSeq` is the listing index's `indexSeq` minus one and `baseIndexDigest` equals the listing index's `predecessorDigest`;
  - `statementDigest` recomputed and equal, and every sign-off's `statementDigest` equal to it;
  - sign-offs as in step 9 without `evidence.json` (`signoff_*` codes): exactly two, one `market_accountant` and one `founder`, different `signerId` and `assertionRef`, `boundTo` the entry's own `signerId` and `statementDigest`, 0 s at most `signedAt - authTime` at most 300 s, every `signedAt` at most `recordedAt`, `requestedBy` one of the two signers, in production each `signerSignature` verified. **Roster only:** a change has no `evidence.json`, so the founder `signerId` is checked against `founderLogin` in `trusted_signers.json` and the founders map, and the accountant `signerId` against that file's roster for the market equal to `countryCode`, with the same `name`, and not a founder; the accountant's `signOffRef` must be present but has nothing to be compared with (residual: the publisher's attestation);
  - the index makes exactly the change the record describes and nothing else: a **withdrawal** moves `target.version` from `published` to `withdrawn` with the same `contentDigest` and the record's `reasonRef`, never leaves `published` empty, and also drops that version's `publishId` from `followUpOpen` if it was open (no separate closure record: Eldon's #344 answer, as #360 does); a **floor raise** sets `floor` to `target.version`, a published version above the old floor; a **follow-up closure** removes `target.publishId` from `followUpOpen`.
- **Which indexes need a change record.** On every step of the chain walk (item 2 step 3), an index that adds a withdrawal, raises the floor or removes a `publishId` from `followUpOpen` must list exactly one change record that accounts for it; an index that lists no change record leaves `withdrawn`, `floor` and the existing `followUpOpen` entries unchanged. The contract allows a list; #360 writes at most one record per index, and the loader refuses an index listing more than one (`change_record_invalid`) until the contract says how several records in one index compose.
- **Production go-live of the store path waits until CMP-045 is built.** Until then the build has no `AssertionVerifier`, so a production deployment refuses every store-path load `store_path_not_live` in code as well as for want of a key (1.7), and the single publisher key publishes only to staging and dev. Residual: the index is signed by the publisher alone, so in production a compromised publisher can still withhold or delay, but cannot add a version or change a withdrawal, floor or follow-up without both signers' assertions (T06).

1.9 **Loader-side trust data never comes from the store.** `pack.schema.json`, the component manifest contract, the founders map (`scripts/lanes.json`), `product_choice_paths.json`, the registered component providers for `requires`, and the two trust files of 1.7 come from the deployed code. A published version that needs a provider version the deployment lacks is refused by the existing gate (`go_live_refused`); CMP-038's schedule must only target deployments that carry the provider.

1.10 **(P) Repo-bundled packs** stay for sandbox and test site classes (ADR-0059) and for unit tests. They carry no record.
- **One tenant entry**, `resolve_tenant_country_pack(context, company_overrides)` (CMP-044), serves all tenant work. `PinSource` returns `{siteClass, pin, minIndexSeq, cohort}`; `pin` is a tenant pin in the contract's `country-pack-pin.schema.json` format: a store pin (`source: store`, 3.1) or, for sandbox and test only, a repo pin (`source: repo`, no `contentDigest`, `publishId` or `indexSeqAtPin`, approval `repo_draft`). `cohort` (`canary` or `general`, 3.2) is not a pin field: `PinSource` reads it from the tenant's row in the tenant registry (Eldon's lane), not from the pin. A store pin always uses the store and never falls back to repo packs, whatever the store answers; a repo pin uses the entry's own private repo reader, so it works in any deployment; a repo pin on a production site class refuses `unsigned_repo_pack`; no pin refuses `pin_missing`.
- **Directory functions** (`load_country_pack`, `resolve_country_pack`) keep their signatures, default and gate behaviour, but refuse every call with `unsigned_repo_pack` when the deployment key environment is `production` (or absent), whatever `environment` the caller passes. The test packages set `dev` in their `tests/__init__.py` (CI runs `unittest discover` per package), so the existing calls, including the production-mode gate tests in `test_country_pack_go_live_gate.py`, `test_production_rules.py`, `test_production_review_fixes.py`, `test_pack_*.py` and `test_company_calendar.py`, run unchanged and keep their messages.
- **`company_calendar/settings.py`** gains `resolve_tenant_calendar_settings(context, ...)` on the tenant entry for tenant work; the existing `resolve_calendar_settings(country, packs_dir, ...)` stays as a directory helper under the same deployment guard. An import guard test fixes the allowlist of modules outside the package that may import the directory functions or that helper: `company_calendar/settings.py`, `company_calendar/__init__.py` (re-export) and the two test packages (CMP39-T32). Signing repo packs the same way is rejected below.

### 2. Loader rules (fail closed, in this order)
New refusals raise a `PackStoreRefusal(CountryPackError)` carrying a stable `code`. Existing refusal messages and classes are unchanged (tests pin them); the existing gate's reasons travel inside `go_live_refused`. Codes marked S also emit a platform security event (item 5).

|---|---|---|
| 1 | Tenant id from the authenticated context; site class, pin, `minIndexSeq` and cohort read through `PinSource`, never from caller arguments; repo and store pins as in 1.10. A production site class in a deployment whose key environment is not `production` refuses. A caller `environment` that differs from the site class refuses; a caller `version` that differs from the pin refuses; `allow_unpinned` and `allow_test_packs` refuse on the store path | `site_class_environment_mismatch` S, `environment_mismatch`, `pin_missing`, `registry_unavailable`, `version_not_pinned`, `unpinned_refused`, `unsigned_repo_pack` |
| 2 | Read the trust files and the verified state (1.7; no production key refuses `store_path_not_live`); fetch the country index. Only a store transport failure (no answer, timeout, store error status) may fall back to the verified cache (item 6); fetched bytes that fail any later step refuse with that step's code, never fall back | `trust_config_unavailable` S, `store_path_not_live`, `verified_state_unavailable`, `verified_state_unseeded`, `store_unavailable` |
| 3 | Latest index: strict parse of the contract's index fields (`predecessorDigest` included), active `kid` of this key environment (never retired or revoked), signature, `countryCode`; `published` versions unique and none of them in `withdrawn`. **Chain walk** (Eldon's #344 answer): when its `indexSeq` N is above the high-water mark H, read `PackStore.index(country, s)` for each s from N minus 1 down to H plus 1 and verify each the same way (active key only, 1.7); each index's payload digest equals the `predecessorDigest` of the one after it, and index H plus 1 has the stored high-water digest as its `predecessorDigest`. A missing index, an index with another `indexSeq` than the one asked for, or a broken link refuses (a transport failure is step 2's). Each step of the walk also passes step 4's floor and withdrawal rules and, in production, the change-record rules of 1.8, comparing index H plus 1 with the stored last verified index (item 6); the verified state keeps each change record it verified. Then raise the high-water mark and its digest by compare-and-set (a write never lowers it; if the stored mark is already higher, re-read the state and re-fetch the index once, then apply this step again). On the cache path an index below `minIndexSeq` is staleness, not tampering | `index_rollback` S, `index_equivocation` S, `floor_regression` S, `withdrawal_reversed` S, `cache_stale`, `verified_state_unavailable` |

### 3. Per-tenant pinning
3.1 **The pin lives in the tenant registry** (control plane, Eldon's lane), in the contract's pin format (`contracts/country-pack-pin.schema.json`, the authority). Summary: `v`, `typ` (`country_pack_pin`), `tenantId`, `source` (`store`, or `repo` for sandbox and test, 1.10), `countryCode`, `packId`, `version`, for a store pin `contentDigest`, `publishId` and `indexSeqAtPin` (the index sequence the registry verified when it pinned), `pinSeq` (plus one per change), `changeKind` (`initial`, `upgrade`, `rollback`, `republish`), `changedBy` (`{actorKind, subject, tokenId}`, a staff or service actor, never a tenant member), `approval`, `changedAt` and `auditId` (the one audit id of the change, #316 decision 6). `approval` is `accountant_boundary` (`{kind, ref, scheduleRef}`: `ref` names the accountant-approved point, Q-657, and `scheduleRef` the CMP-038 schedule) for an initial, upgrade or republish store pin; `founder_rollback` (`{kind, ref, approvedBy, stepUpRef, reasonRef}`, Q-655) for a rollback; `repo_draft` (`{kind, ref}`) for a repo pin. The tenant's rollout `cohort` (`canary` or `general`) is on the tenant's registry row, not in the pin (1.10). A new registry row in Eldon's lane builds the tenant version pin (Q-677). Per country the registry also holds `minIndexSeq`, advanced on every publish, republish, withdrawal, floor raise and follow-up closure in the write order of 1.6; `PinSource` returns it with the pin, so a withdrawal or floor raise after the pin still raises the loader's freshness floor without loader state. Tenants keep the exact version in their compiled artifact as today ([../compliance/country-pack-framework.md](../compliance/country-pack-framework.md) section 5); the registry pin is what the loader trusts. The loader reads the registry through `PinSource` and never writes it. Binding the pin to the digest means a store that serves another record for the same version number refuses (`pin_digest_mismatch`).

3.2 **Pin changes: `check_upgrade(tenant, target)`.** The CMP-038 schedule names a country, a target version and tenant cohorts, canary first; the registry calls `check_upgrade` for each tenant and for every pin change. It runs the full item 2 checks against the target, live from the store (a new or changed version never comes from the cache, Q-654: on a store failure it refuses `store_unavailable`), then the tenant's current company overrides merged against the target (the existing override rules), then the approval, then the rule for the direction, reading `compatibilityRange` as the versions a release may be upgraded from (founder answer, Q-677; the pack schema and the framework text do not yet say so). **Approval:** every store pin change except a rollback carries `accountant_boundary` approval with a non-blank `ref` and `scheduleRef`; another kind, or a blank one, refuses `pin_point_missing`. The loader checks it is present, not what it says (residual).
- **Upgrade** (target higher): the target's `compatibilityRange` contains the current version, and the target's `migrationRequired` is false (true, required on a major version by the framework, stops the automatic move until a named migration step exists, not in this ADR). The pin moves at the accountant-approved point its `approval.ref` names (Q-657).
- **Rollback** (target lower): the target was already signed (in `published`, not withdrawn, at or above the floor); the current version's `migrationRequired` is false and the target is inside the current version's `compatibilityRange`; the target's own policy, signed before the current version existed, is not used. **One founder approves** (Q-655): the approval is `founder_rollback`, its `approvedBy` a founder `signerId` in `trusted_signers.json`, its `stepUpRef` a fresh sign-in within 300 s (step-up, ADR-0047 item 4) and its `reasonRef` a non-blank written reason, and its audit record is written before the pin moves (`rollback_approval_invalid`). A rollback needs the founder's rollback approval only, no accountant-approved point (Q-677).
- **Republish** (same version): same `packId` and `contentDigest`, the target's `supersedes` equals the current `publishId`, a newer `publishId`, an active key.
- **Open follow-up** (Q-657): any move except a republish onto a target whose `publishId` is in `followUpOpen` refuses `follow_up_open` unless the registry puts the tenant in the `canary` cohort. Tenants already pinned to it keep loading it (item 4).
Only on a pass does the registry move the pin and emit a pin event. A failure leaves the pin, records the reason code and alerts.

3.3 **Rollback and downgrade, defined.** A *rollback* is a registry move to a lower version that is in the index, not withdrawn, at or above the floor, and passes `check_upgrade` (3.2) with its approval. A *downgrade* is anything else that would make a tenant run older content: a pin to a withdrawn or below-floor version, a store serving an older record or index, or a caller asking for a version other than the pin. The loader refuses every downgrade (item 2, steps 1, 4, 5, 7). When an older version must never run again, CMP-038 withdraws it or raises the floor.

3.4 **In-flight periods.** A pin change never applies backwards: the compiler stores the resolved locale with the compiled artifact (country-packs compiler step 5), so a change takes effect at the next compile and apply, and every load event records the version and digest used. The pack schema holds no rates or dated statutory values today: `tax` carries `taxCodesRef`, `filingPeriods` and `roundingRule`; where rates live is outside the pack (UNVERIFIED). Which treatment applies to a supply when a VAT period straddles a rate change (by invoice date, supply date or transitional rule) is a tax fact for each market: UNVERIFIED for Saudi Arabia, the UAE, Egypt and Qatar, routed to the market accountant through CMP-038's evidence. The loader decides none of it. Founder answer (Q-657): pins move only at accountant-approved points (`approval.ref` of an `accountant_boundary` approval, 3.1, 3.2), and packs carry no dated values, so no pack schema row is opened for them.

### 4. Urgent changes
The urgent path keeps the full two-person rule: the record says `changeKind: urgent` and `followUp.required: true`, and step 9 applies unchanged. The loader does not refuse an urgent version because its follow-up is open (refusing would block a legal change); every load, upgrade check and pin event carries `urgent: true` and `followUpOpen` from the index. CMP-038 closes the follow-up by a two-person `follow_up_closure` change record that removes the `publishId` from `followUpOpen`, or withdraws the version, which drops its open follow-up in the same record (1.8); the outcome is either confirmed, or superseded by a new version with a floor raised above the urgent one. While the follow-up is open, rollout stops at the canary cohort (Q-657, 3.2 `follow_up_open`).

### 5. Audit
- All events go through SEC-008's `AuditStore` port (decision 1 on #316); SEC-008 owns the format and the store, and the builds use a fake until it exists.
- **Tenant audit:** `country_pack.loaded`, `country_pack.load_refused`, `country_pack.upgrade_checked`; the registry emits `country_pack.pin_changed`. Identity (decision 2): the `memberRef` plus `token_id` of the member whose request caused the load; for a compile or apply job, the job's service identity (how SEC-008 records a service actor is UNVERIFIED). Tracing (decision 6): the caller's end-to-end `auditId` from the tenant context; the loader never mints a second one and adds no correlation id, because it makes no engine call. Other fields: tenant, site class, caller service, pack id, country, version, `contentDigest`, `publishId`, `kid`, `indexSeq`, source, `urgent`, `followUpOpen`, `approval.ref` for a rollback, reason code and step. Never a staff id (`signerId`, `publishedBy`, `changedBy`, rollback approver, seed operator), pack contents or envelope bytes; a refused envelope is recorded by its sha256.
- **Platform security stream** (decision 3; staff ids only here): codes marked S in item 2, `country_pack.index_advanced`, `country_pack.state_seeded` with the operator, and the staff side of each pin change and rollback approval (who, step-up time, reason). Each carries the same `auditId` and no tenant content.
- **Write-through** (Q-656): if the audit write of a store-path load, upgrade check, pin change or seed fails, it refuses `audit_unavailable`. This goes beyond #316 decision 4 (admin and money routes) by founder answer. Repo-path loads in sandbox and test log best effort.

### 6. Store outage and verified state
**Cached last verified version, at most 7 days (Q-654).** The loader keeps a verified state (behind a `VerifiedState` port): per country the high-water `indexSeq` and that index's digest, the highest floor, every withdrawal and (in production) every change record it has verified, plus the last verified index with `lastVerifiedAt` (the loader's clock when it last verified an index fetched from the store) and the bundle bytes and record for pinned versions. Only on a store transport failure (step 2) may it serve the tenant's pinned version from the cache, and only while `lastVerifiedAt` is not in the future and now minus `lastVerifiedAt` is at most 7 days (a code constant; configuration may set a shorter bound, and 0 turns the cache off). Past the bound it refuses `store_unavailable` and raises an operator alert. A new or changed version never comes from the cache (3.2). Every item 2 check still runs on the cached bytes against the current trust files, deny-list and the registry's current `minIndexSeq`, so a withdrawal or floor raise published during the outage refuses the cache as soon as the registry carries it. A registry outage always refuses (`registry_unavailable`), because the pin and `minIndexSeq` are never cached. When the loader runs: at compile and apply (compiler step 1 resolves the pack version) and whenever a component resolves pack values for a tenant, as `company_calendar/settings.py` does. Rationale: a tenant already on a verified version should not stop compiling, applying or resolving its calendar because the store blinked.

**Verified state** (Q-678). It lives in a durable in-country control-plane store with compare-and-set, shared by all loader instances of a deployment, never per instance; the loader reaches it only through the `VerifiedState` port (a fake until a later row wires the store); every update is an atomic compare-and-set that never lowers a high-water mark or floor and never drops a withdrawal. An unreadable state or a failed write refuses (`verified_state_unavailable`). In a `production` deployment an empty state (new deployment, after loss, or cleared by the revocation runbook, 1.7) never trusts the first index it sees: loads refuse `verified_state_unseeded` until a seed (`seed_verified_state(country)`) fetches and fully verifies the latest index, at or above the registry's `minIndexSeq`, and stores it as the high-water index. Only a staff operator with step-up (a sign-in within 300 s, ADR-0047 item 4) may run it, it is logged to the platform security stream (`country_pack.state_seeded` with the operator), and it is never automatic in production; any other caller refuses `seed_refused` S (Q-678). The seed walks no further back than that index: what it says about earlier withdrawals, floor raises and follow-up closures is the starting point the operator accepts (residual), and every change after it is checked change by change (item 2 step 3). Staging and dev deployments seed automatically on first load, with the same index checks.

## Alternatives rejected
- **Digest over re-serialised JSON.** Number and Unicode canonicalisation would need their own rules and tests; hashing the exact stored bytes needs none and the loader parses the bytes it hashed.
- **HMAC instead of a signature.** The loader would hold the minting secret, so a compromised loader host could publish packs (ADR-0068 item 6 makes the same point).
- **Trust keys from the pack store.** Whoever writes the store could then add a key; the trust root must be reviewed outside it.
- **Signing repo packs the same way and allowing them in production.** It adds a second publishing route outside CMP-038's two-person workflow; repo packs stay drafts for sandbox and test.
- **Refuse every load during a store outage.** Safe but it stops invoicing for tenants already on a verified version; kept as the behaviour after 7 days or with the bound set to 0.
- **Trust on first use of an empty verified state in production.** A store rolled back while the state was lost would be accepted; the registry's `minIndexSeq` and an audited seed replace it.
- **Refuse urgent versions until the follow-up closes.** It would block the legal change the urgent path exists for.
- **Revocation flags inside `evidence.json`.** ADR-0067's closed key set refuses them, and the pack under review must not decide its own validity; withdrawals live in the signed index.
- **Moving every existing production-mode test to the in-memory gate.** 39 calls rely on the `production` default and many more pass it; the deployment guard (1.10) keeps them unchanged at no loss of protection.

## Consequences
- Production tenants can only run pack content that CMP-038 published with both sign-offs recorded and that has not been withdrawn or fallen below the floor; the repo packs never reach production.
- Harder: production go-live of the store path waits for CMP-045 (Q-652); the loader gains two trust files, a store port, verified state with a seed step and an audit dependency; every production load needs the registry, and either the store or a fresh cache; CMP-038 must keep the index-then-registry write order.
- Residual, stated plainly: in staging and dev the loader cannot detect a compromised publish service or key (T06); in production, after CMP-045, the publisher alone can still withhold or delay. The loader proves records, not accountant qualifications (as ADR-0063 says; the reviewed roster is the control); it checks that an `accountant_boundary` approval's `ref` is present, not that the accountant approved it, and that a rollback approval's step-up and reason are present and fresh, not that they happened (both are the registry's attestation); a change-record accountant `signOffRef` has no `evidence.json` to be compared with; what the seed index says about earlier changes is the seed operator's starting point (6); an accountant who has left stays on the roster until the removal PR merges (1.7); tax transitions are not modelled (3.4, UNVERIFIED for all four markets).
- A withdrawal, a floor raise or a key revocation refuses every tenant still pinned to the affected version at its next load, store path and cache alike. CMP-038 must move those tenants' pins (upgrade, rollback or `republish`) before or together with that change, and alert on any tenant left behind.
- CMP-038 must produce exactly the contract's formats (contracts/country-pack-store.md (0.3.0, PR #362)) and pass the shared vectors (CMP39-T07, T42, T53), keep every index reachable by `PackStore.index(country, seq)` so a loader that is behind can walk the chain, and keep the index-then-registry write order; the registry must hold the pin and `minIndexSeq` of 3.1 and the cohort on the tenant's row. Tier 3 line-by-line review and a different-model security review are required before Accepted; neither is claimed here.
