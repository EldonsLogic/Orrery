## Decisions
- Journal design (contract 15.1: "a step that failed before taking effect is not listed"; phases are only `execute` and `compensate`): the `execute` entry is appended after the step took effect, not as a "pending then confirmed" pair (a `pending` phase would appear in `execution_journal()` and break the contract). The in-memory journal still marks the step executed before the durable write, so a journal write that fails after the effect ends `recovery_required` (the step is never reported as clean). A crash between the step and its journal entry leaves the operation to lease recovery, which already ends `recovery_required` (ADR-0028); no new window, since recovery never trusted the journal to decide that.
- State persistence: the write happens inside the finalize transaction, after `idem_complete` proved the lease, so a worker that lost its lease writes nothing. On failure the transaction rolls back and a second one stores `recovery_required` (stage `finalize`, event `blueprint.apply_failed`, audit result `recovery_required`), then a best-effort write keeps the tenant-database copy from claiming a ready site. This applies to every outcome, including no-effect ones (`rejected`, `already_applied`, `failed_clean`): fail closed was chosen over splitting the cases.
- Locations: the `location.disable` of a step without a definition (no kind) keeps the company-scoped Warehouse lookup, because the engine does not pass the kind to the backend; every compensation step carries its definition. Branch and department remain engine no-ops until open question 11 in `contracts/engine-adapter.md` (location elements: configuration or business records) is decided; not decided here.
- No ADR needed (no auth, tenancy, contract or compliance change).

Design. The operation store is the source of truth; the tenant-database state copy is a mirror. Adaptation of the coordinator's direction: a unique write token compare-and-set instead of a store-assigned version. The store has no revision or sequence column (adding one means a migration in both stores and the protocol), the only stale writers are the ones that write after the site lock is released, and a token the writer itself put there is enough to know it was overtaken. Same protection, no store schema change.
- The copy table gets a nullable `write_token` column (created with the table; added on first touch to a table made earlier, in `_ensure_state_table`, which `load_site_state` now runs too).
- `persist_site_state` takes `write_token` (what to store) and, optionally, `expect_token`. With `expect_token` it is a compare-and-set under `SELECT ... FOR UPDATE`: it replaces the copy only while the copy still carries that token (None: no token, or no row) and otherwise changes nothing. Without it the write is unconditional.
- Unconditional writes are only made while the writer holds the store's site lock: provisioning and the pending marker inside finalize (tagged with the run's token). The lock serialises them against every other run. Every write made after the lock is released is a compare-and-set: the mark-ready after the store commit expects its own marker, so a paused worker whose marker was overwritten changes nothing (finding 1).
- `_repair_state_copy(tenant)` rewrites the copy from the store when they disagree. It reads the copy first, then the store, skips a site whose lock is held (that run writes its own copy), and writes with `expect_token` = the token it read, so a run that got in between wins. Best effort, never raises. It runs in `recover_interrupted()` (for every site the store holds, through the new `site_tenants()`; the constructor and every stale-lock acquire call it), on a same-key replay, on `already_applied`, after a failed finalize copy write (replacing the unconditional best-effort write there), and after `sync_members` commits (replacing its unconditional post-commit write, the same stale-writer shape; the failure there no longer raises, because the store has already committed and the repair retries; same rule as the mark-ready).
- Hydration is unchanged and does not write: it runs only when the store has no row, so there is no store state for it to prefer. A leftover marker still blocks a hydrated site (fail closed).
- The copy is written whenever the run changed the store: a step took effect, the state moved, or the site content (applied, history, config, retained, sync version) differs from what the run started with. A clean refusal changes none of these and writes nothing (first-round finding 2 stays closed).
