# WEB-022: AG-UI protocol, paper spike for the chat-to-screen stream

Status: draft. Owner: eldon. Sources (accessed 2026-11-18): https://github.com/ag-ui-protocol/ag-ui and https://docs.ag-ui.com/concepts/events. Everything below about AG-UI comes from those pages and is UNVERIFIED by running code; this is a mapping on paper, not a running spike.

## Why
The platform has no defined stream between the AI layer and the chat screen (WEB-004, OPR-010). The Event stream contract is the audit log, not a live UI protocol. AG-UI is an open (MIT, per its README) event protocol for exactly this link. The question is whether to adopt its vocabulary as our wire format.

## Mapping: what the chat screen needs, and the AG-UI event that carries it
| Need | AG-UI events | Our rule |
|---|---|---|
| Streamed reply, Arabic or English | `TextMessageStart` / `Content` / `End` | Text is untrusted output: rendered as plain text, never as markup or links |
| Chat mode (discover, ask, act, change) | `RunStarted.input` or a `CUSTOM` event | The mode is set by the server from the session, never by model output |
| Showing a tool call and its progress | `ToolCallStart` / `Args` / `End` / `Result` | Display only. Tool ids come from the generated Tool API; arguments and results are summarised and redacted. The model cannot cause a browser action |
| Blueprint draft and diff | `StateSnapshot`, `StateDelta` (JSON Patch) | Send a reference and a short summary; the diff itself is fetched from our authenticated API |
| Approval request | `RunFinished` with outcome `interrupt` | The interrupt only displays the request. The approval is recorded through our own approval endpoint (ADR-0032, a recorded review); the resumed run carries the approval id, not the decision |
| Build, simulation and import progress | `StepStarted` / `StepFinished`, or `ActivitySnapshot` / `ActivityDelta` | Step names are our own ids, translated by i18n in the client |
| Errors | `RunError` | Our coded errors only; no engine names, stack traces or paths (ADR-0016) |
| AI-action budget and cost preview | `CUSTOM` with an allow-listed name | Typed payload, validated against a schema |
| Several agents working | `SubagentStarted` / `Finished` | Shown as activity; low priority |

## Do not use
- `Reasoning*` events: never send model reasoning to the browser.
- `Raw` events: never forward.
- Frontend tools and generative UI from agent output: no agent-triggered browser actions; only a small fixed set of typed components we own.
- CopilotKit UI components: we cannot confirm token-only styling or RTL (UNVERIFIED); use the wire format and our own components.

## Security rules for adoption
1. Every event is generated by our gateway from trusted state; model text is wrapped as data (SEC-003).
2. Event streams carry the session's tenant; the client never supplies tenant, role or caller.
3. Resume and approval requests are authenticated server calls, replay-safe and tied to one interrupt id.
4. The client ignores unknown event types and unknown `CUSTOM` names (fail closed).
5. Streams are logged to the event stream contract as facts (who saw what), not the other way round.

## Not verified
- The Interrupts page (exact `Interrupt` type and resume rules) and the frontend-tools description were not readable in the fetched material.
- Release cadence and the last commit date are not visible; the README's adopter list is the project's own claim.
- Arabic streaming, bidi handling in streamed chunks and the fit with our tokens and RTL rules need a code spike.
- Licences of the SDK packages must be recorded in the register (LEG-004) before use.

## Recommendation
Adopt the AG-UI event vocabulary as the chat-to-screen wire format, decided by a short ADR when WEB-004 starts. At that point run the code spike (stream a fixture conversation in Arabic through the TypeScript SDK into the preview app, with an approval interrupt) and pin the spec version. Do nothing before then.
