# Gateway local audit spool: specification before code (PLT-028)

Status: draft, revision 2.3 (Tier 3, security review by a different model before code)
Owner: partner
Plan ID: PLT-028 (G2)
Related: [ADR-0069](../decisions/ADR-0069-gateway-live-binding-audit-spool.md) sections 2.1 to 2.5, 2.10, 2.11, 5.5, 7; founder decisions on PR #316 (2026-11-25); [ADR-0038](../decisions/ADR-0038-secrets-management.md); [ADR-0041](../decisions/ADR-0041-durable-adapter-state-on-tenant-database.md); [ADR-0006](../decisions/ADR-0006-tenancy-site-per-tenant.md); [data-retention.md](../security/data-retention.md) section 8; Q-614

This is the local side of the ADR-0069 spool, built against a fake `AuditStore`: files, tables, transactions, admission, recovery and key rotation in one gateway instance. Forwarding is PLT-032's; this spec fixes only the local interface PLT-032 calls (section 6) and the local comparison rules it applies (4.7). Every choice marked **(P)** is proposed and may change in review without changing the structure.

**Precedence.** The founder decisions on PR #316 (2026-11-25, Eldon for both founders) override ADR-0069 where they differ, because ADR-0069 was merged as Proposed before that re-scope. This spec applies five of them: (D1) SEC-008 owns the record format and the `AuditStore` port; (D2) identity is the per-tenant `memberRef` plus `token_id`, with no global user id; (D3) platform security events go to SEC-008's platform security stream; (D4) ordinary routes are buffered and crash loss is accepted; admin and money routes are write-through; (D5) idempotency lives in the adapter only; the gateway does no dedupe. Eldon's answers on PR #335 (2026-11-26, for both founders) settle the rest: (A1) write-through means a synced commit on this instance's local volume before the action completes, then forwarding to the store of record; (A2) with the store unreachable at start, sign-in and reads keep working, ordinary actions buffer locally, admin and money actions still run, and the instance refuses everything only when its own local volume fails. His answers on the open calls of the `98b86a9` re-review (2026-11-26, for both founders) add: (A3) a store-side or key-side mismatch stops only `write_through` actions and alarms (4.8); (A4) the 30 s unconfirmed rule is an alert only; (A5) the money mark is platform-owned and set in code (3); (A6) sign-ins during an outage are counted as per-minute aggregates (4.6); (A7) admin denials are buffered like ordinary records (3); (A8) at most 8 `write_through` requests in flight per tenant (5.4). His answers of 2026-11-26 on the open calls of the `5c27107` re-review settle Q-675 and Q-676 and bring in his Q-673 answer on PR #355: (A9) every write route stays `write_through`, not only admin and money routes, and any exception needs its own ADR with measured disk-sync data (3, Q-675); (A10) the 4.8 reading of a store-side or key-side mismatch is agreed, only a platform operator with a spool-admin permission and step-up sign-in may run `reconcile_missing`, each run audited to the platform security stream, and SEC-008 closing a missing intent when its `reconcile` record arrives becomes a Q-614 conformance test (4.8, 6.7, Q-676); (A11) `caller_mismatch`, `tenant_in_payload` and any cross-tenant or region refusal are written durably, never buffered, and the platform security stream takes them (3, 6.8, Q-673).

## 1. Files, settings, units and MACs
- **(P) Files.** Three per instance on the encrypted in-country volume (ADR-0069 2.1): `spool-tenant.db`, `spool-preauth.db` and `spool-late.db`. The late file is empty unless the tenant file fails closed (4.2, 7.4). Each file has its own WAL, an advisory lock file `<name>.lock` and marker files, each created exclusively, file and directory fsynced, holding reason and time only: `<name>.failed` once it fails closed (7.4); `<name>.wt_stopped.store_mismatch` and `<name>.wt_stopped.intents_missing` while that stop holds (4.8). None is ever on a network file system.
- **(P) Library and connections.** Standard library `sqlite3` only. Start refuses if `sqlite3.sqlite_version_info < (3, 37, 0)`, which STRICT tables need. One writer connection per file opened with `isolation_level=None`, and one read connection for PLT-032's batch reads.
- **(P) Pragmas on every open,** each read back: `journal_mode=WAL`, `synchronous=FULL`; `fullfsync=ON`, `checkpoint_fullfsync=ON` (no-ops on Linux, they make a macOS developer run durable; production is Linux only); `foreign_keys=ON`, `secure_delete=ON` (M6), `cell_size_check=ON`, `trusted_schema=OFF`; `busy_timeout=5000`, `journal_size_limit=67108864`, `wal_autocheckpoint=1000`.
- **(P) Units.** Capacity is counted in integer units, never in measured bytes: a `records` row costs 1 unit; an `open_intents` row costs 2 units: the intent copy plus the reserved outcome; 1 unit = 4 KiB ceiling × overhead factor 2 = 8 KiB. So `U = 512 MiB / 8 KiB = 65,536` for `tenant` and `U_p = 8,192` (64 MiB) for `preauth`. A physical guard (5.3) backs the logical count.
- **(P) Record bytes.** `body` is the canonical record without `chain`: JSON with sorted keys, separators `,` and `:`, UTF-8, no NaN, at most 4,096 bytes. A larger body is a write failure (503 `audit_unavailable`), never truncated. **Inside `body`:** `instance_id`, `stream`, `seq` (assigned at commit in the transaction that appends the row; `null` in `late` rows, which sit outside the chain and are authenticated by the late-row MAC), `key_id`, `phase`, `audit_id`, `tenant_id` and `audit_class` (how the record is kept, not the route's class: `ordinary` for buffered records, a denial on a `write_through` route included (a security refusal excepted); `write_through` for intents, outcomes and `reconcile` records committed per request; `security` for the security refusals of 3, committed per request (A11); `band` for `aggregate` and `key_rotation`). **Identity, when verified (F3, D2):** `tenant_id`, `memberRef` (the per-tenant member reference from the membership check), `token_id`, `realm`, `session_version`, `mfa_satisfied`, `auth_time`. The token subject and any global user id are never written. **Provisional:** the field set is ADR-0069 5.1 with that change, and SEC-008 may change the record shapes (D1, D3). Only the indexed columns of section 2 are fixed here, so a shape change touches the record builder, not the schema.
- **(P) Keys.** Each key version `K` from the secret store (ADR-0038) gives two derived keys: `K_chain = HMAC(K, "seshna.spool.chain.v1")` and `K_mac = HMAC(K, "seshna.spool.rowmac.v1")`. Notation: `lp(x) = be32(len(x)) || x`.
- **(P) Chain.** `chain(seq) = HMAC-SHA256(K_chain[key_id], chain(seq-1) || body)`, with `chain(0)` = 32 zero bytes.
- **(P) First key of a fresh file (F9).** Creation is one transaction. It writes `owner` (epoch 1, new `boot_id`) and `checkpoint` (head 0, zero chain, `active_key_id` = the secret store's current version, which must load). If the store already has a checkpoint for this `(instance_id, stream)`, a fresh file under a used `instance_id` is a rollback (4.7, first row): a store-side mismatch, so the file starts under `store_mismatch` (4.8, A3) and the instance is replaced. With the store unreachable, the same check is the deferred 4.7 comparison (4.4 step 5); nothing is forwarded before it passes (A2).
- **(P) Open-row MAC.** `HMAC-SHA256(K_mac[key_id], lp("open") || lp(instance_id) || lp(stream) || lp(audit_id) || lp(tenant_id) || be64(seq) || lp(key_id) || be64(reserved_units) || chain || lp(intent_body))`.
- **(P) Late-row MAC.** `HMAC-SHA256(K_mac[key_id], lp("late") || lp(instance_id) || lp(audit_id) || lp(phase) || lp(tenant_id) || lp(key_id) || lp(body))`.
- **Column binding.** Every indexed column (`seq`, `phase`, `audit_id`, `tenant_id`, `key_id`, `audit_class`) must equal the same field in its `body` or `intent_body`. TX2 checks the row it closes; recovery step 4 checks every row.

## 2. Schema (`tenant` and `preauth`; `preauth` never has `open_intents` rows)
```sql
CREATE TABLE owner (one INTEGER PRIMARY KEY CHECK (one = 1), instance_id TEXT NOT NULL,
  stream TEXT NOT NULL CHECK (stream IN ('tenant','preauth')), epoch INTEGER NOT NULL CHECK (epoch >= 1),
  boot_id TEXT NOT NULL, schema_version INTEGER NOT NULL) STRICT;
CREATE TABLE checkpoint (one INTEGER PRIMARY KEY CHECK (one = 1),
  head_seq INTEGER NOT NULL CHECK (head_seq >= 0), head_chain BLOB NOT NULL CHECK (length(head_chain) = 32),
  pruned_through INTEGER NOT NULL CHECK (pruned_through BETWEEN 0 AND head_seq),
  pruned_chain BLOB NOT NULL CHECK (length(pruned_chain) = 32),
  prune_receipt_version INTEGER NOT NULL CHECK (prune_receipt_version >= 0),
  active_key_id TEXT NOT NULL) STRICT;
CREATE TABLE records (seq INTEGER PRIMARY KEY CHECK (seq >= 1),
  phase TEXT NOT NULL CHECK (phase IN ('intent','outcome','reconcile','key_rotation','aggregate')),
  audit_id TEXT CHECK (phase NOT IN ('intent','outcome','reconcile') OR audit_id IS NOT NULL),
  tenant_id TEXT NOT NULL, key_id TEXT NOT NULL,
  audit_class TEXT NOT NULL CHECK (audit_class IN ('ordinary','write_through','security','band')),
  chain BLOB NOT NULL CHECK (length(chain) = 32),
  body BLOB NOT NULL CHECK (length(body) BETWEEN 2 AND 4096),
  CHECK ((phase IN ('aggregate','key_rotation')) = (audit_class = 'band')),
  CHECK (phase NOT IN ('intent','reconcile') OR audit_class = 'write_through'),
  CHECK (audit_class <> 'security' OR phase = 'outcome')) STRICT;
CREATE UNIQUE INDEX records_audit_phase ON records(audit_id, phase) WHERE phase IN ('intent','outcome');
CREATE INDEX records_tenant ON records(tenant_id);
CREATE INDEX records_key ON records(key_id);
CREATE INDEX records_agg ON records(tenant_id) WHERE phase = 'aggregate';
CREATE TABLE open_intents (audit_id TEXT PRIMARY KEY, seq INTEGER NOT NULL UNIQUE,
  tenant_id TEXT NOT NULL CHECK (tenant_id <> ''), key_id TEXT NOT NULL,
  chain BLOB NOT NULL CHECK (length(chain) = 32),
  intent_body BLOB NOT NULL CHECK (length(intent_body) BETWEEN 2 AND 4096),
  reserved_units INTEGER NOT NULL CHECK (reserved_units = 1),
  row_mac BLOB NOT NULL CHECK (length(row_mac) = 32)) STRICT;
CREATE INDEX open_intents_key ON open_intents(key_id);
CREATE TABLE usage (tenant_id TEXT NOT NULL,
  audit_class TEXT NOT NULL CHECK (audit_class IN ('ordinary','write_through','security','band')),
  units INTEGER NOT NULL CHECK (units > 0), PRIMARY KEY (tenant_id, audit_class)) STRICT;
-- spool-late.db only:
CREATE TABLE late (audit_id TEXT NOT NULL, phase TEXT NOT NULL CHECK (phase IN ('intent','outcome')),
  tenant_id TEXT NOT NULL, key_id TEXT NOT NULL, body BLOB NOT NULL CHECK (length(body) BETWEEN 2 AND 4096),
  row_mac BLOB NOT NULL CHECK (length(row_mac) = 32), PRIMARY KEY (audit_id, phase)) STRICT;
```
- **`tenant_id` values.** `tenant` file: the verified tenant. `preauth` file: the unverified host tenant, **only if the validated host names a provisioned tenant**; otherwise `''` (F9). Platform rows (`key_rotation`, platform aggregates): `''`. A security refusal (3) follows the same rules: the other tenant that a token, payload or target names is written in `body` only, never in the `tenant_id` column.
- **`usage`** caches, per tenant and `audit_class`, `count(records)` plus `2 * count(open_intents)` (class `write_through`), with `'*'` rows per class for the file totals. A row that reaches 0 is deleted in the same transaction, so `preauth` (classes `ordinary`, `security` and `band` only) holds at most 3 × (provisioned tenants + 2) rows. Start recomputes and compares it (4.4 step 4).
- No foreign key from `open_intents` to `records`: the intent row is pruned after delivery while the open row stays (ADR-0069 2.4).

## 3. Route classes and transactions
**Route class (F1, N2).** Each `Route` declares in the route table, in code: `audit_class` (`ordinary` or `write_through`; an unclassified route is `write_through`, fail closed), the money mark and the `signin` marker (4.6). The money mark is platform-owned, set in code in the route table or the permission catalogue, and never tenant configuration (A5, Q-647). Registration refuses `ordinary` unless all of these hold: the permission is not admin-kind (ADR-0069 3.6) and not money-marked; the engine target is static (a route whose target comes from a request parameter is `write_through`); and the handler gets a **read-only upstream client**, bound at registration to an allow-list of static engine endpoints that the platform's endpoint table (code) marks as having no effect, or to a read-only engine credential. The HTTP verb decides nothing: an engine method reachable by GET may mutate (UNVERIFIED, 10). A call outside the allow-list raises before anything is sent. So every write route is `write_through`, not only admin and money routes (A9, Q-675); any exception needs its own ADR with measured disk-sync data.

**Reads on a `write_through` route (N6).** TX3 alone, with no intent before the handler, is used only for a read handler that registration binds to a read-only upstream client as above: an allow-list of no-effect engine endpoints or a read-only engine credential, where a call outside it raises before anything is sent. Every other request on a `write_through` route, GET included, is treated as a write: TX1 before the handler and TX2 for the outcome.

**`ordinary` routes (D4).** The outcome record goes to an in-memory buffer at enqueue (5.1 R), and a flusher commits the buffer in batches (TX9). The response does not wait for the flush, and a crash loses whatever was not flushed. Over a limit the record is counted instead (5.1); serving then is sound only because the route has no effect.

**`write_through` routes (A1).** The intent record is committed in this file under `synchronous=FULL` before the action's effect (TX1, before the handler), and the outcome record before the response (TX2 for writes, TX3 for reads bound to a read-only client, N6), except when TX2 fails after the effect: the real result is then returned and the outcome is retried or written to the late file (4.2, L1). PLT-032 then forwards both to the store of record. No store round trip is in the request path, so a store outage never blocks a `write_through` route (A2). Open rows (4.2), required receipts (6.3) and reconcile (4.4 step 7) apply to these routes only.

**Denials and validation failures** before any handler have no effect, so they are buffered as `ordinary` records on every route, admin routes included (A7). They draw on the ordinary budget, never on the `write_through` reserve (5.1). The security refusals below are the one exception.

**Security refusals (N5, A11, Q-673).** A refusal whose reason is in the closed set `SECURITY_REFUSALS`, fixed in code and changed only with this spec, is never buffered: `caller_mismatch`; `tenant_in_payload`; a cross-tenant refusal (a token, payload or target naming a tenant other than the verified one, or in `preauth` a token for a tenant other than the host's); and a region refusal (`region_policy_refused`, or any request refused because data or a call would leave its tenant's region). It takes TX12: one `security` record committed under `synchronous=FULL` in the file the request belongs to (`tenant` for a verified caller, `preauth` otherwise) before the refusal response is sent. TX12 uses only its own reserve `R_s` (5.1) and two token buckets (P): per source, at most 4 per 60 s (burst 4), where the source is the verified `(tenant_id, token_id)` in `tenant` and, in `preauth`, the peer address after the listener's trusted-proxy rules (PLT-029), IPv6 grouped by /64, written only as a keyed digest (M6 condition (c), 9); per file, at most 8 per second (burst 8), which bounds what TX12 adds to the writer queue (5.4) however many sources there are. Both buckets and `R_s` are checked in memory before the writer lock (5.2 step 1), so a request over them never enters the queue. The source table holds at most 4,096 entries per file, least recently used evicted; eviction only resets per-source fairness. When the record cannot be committed (over `R_s` or a bucket, under the 5.3 floor, a full disk, an I/O error on `COMMIT`, `key_missing`, or the file not `serving`), the request is still refused with its own code (never 429, never served), counted in the platform aggregate (`tenant_id = ''`; its body names at most 16 tenant and source-digest pairs, the highest counts, plus an `other` total, so it stays within 4,096 bytes), and `security_refusal_unrecorded` pages, at most once per file per minute (P). These rows and their counts go to the platform security stream only (6.8).

**Transaction rules.** Every write runs under the writer lock (5.4) as `BEGIN IMMEDIATE` ... `COMMIT`. Its first statement reads `owner.epoch`, and a mismatch stops the writer. Any exception before `COMMIT` is followed by an explicit `ROLLBACK`.

**An I/O error raised by `COMMIT` itself (F7)** fails the file closed at once: the connection is closed and no further transaction runs on it. Then TX1 never calls the handler and the client gets 503; TX3 answers 503 with no data (a read has no effect; the same holds when TX3 meets a `failed_closed` file or a full disk); TX2 takes the 4.2 late path; TX9 sends its batch to the late file; TX12 still sends its refusal, counted and paged (above); any other transaction is named in the page. The earlier rule (reopen, then read the durability point) is deferred and UNVERIFIED (10). A later revision may enable it only after its own test passes on the production volume type (GLB-T76). TX8 (quarantine destroy) was removed in revision 2.

| Id | Name | Statements inside one `BEGIN IMMEDIATE` | DP |
|---|---|---|---|
| TX0 | start | `UPDATE owner SET epoch = epoch + 1, boot_id = ?` | DP0 |
| TX1 | write-through intent | admission W (5.1); `INSERT records` (intent); `INSERT open_intents`; `UPDATE checkpoint` head; `usage` `write_through`, tenant and `'*'`, +3 | DP1 |

**WAL truncation after a drain (M6).** Hold `stream_guard` (6.1), which pauses PLT-032, close the read connection, and run `PRAGMA wal_checkpoint(TRUNCATE)`. The result must be `(busy = 0, log = 0)`; otherwise retry up to 10 times at 1 s, then page. Deprovisioning certification refuses without this result (UNVERIFIED: 10).

### 4.1 A record

### 4.3 Reservations
The only holder is an open row: TX1 takes +2 `write_through` units in `usage`, and TX2 or TX6 releases a net -1. It survives restart, every limit counts it in `'*'`, and every floor keeps `8 KiB × held` free (5.3). `ordinary` routes have no intent (3), so revision 2.1's ordinary-write reservation is gone.

### 4.4 Restart recovery (R3-1), per file

### 4.6 The `preauth` spool
Every `preauth` record is `ordinary`, buffered and flushed by TX9, except a security refusal (3), which takes TX12 in this file; a token for another tenant is one (A11, N5). The ordinary records cover unverified denials and listener events (ADR-0069 1.5, 3.2). They follow 4.1 under the `preauth` limits of 5.1. Over a limit, or with the file not `serving`, an ordinary request gets 429 `rate_limited` and an in-memory counter per reason goes up; a security refusal keeps its own code and is counted as in 3. `rate_limited` is Tool API section 7's retryable code ([tool-api.md](../../contracts/tool-api.md) section 7; the gateway's `ERROR_CODES`); #316 decision 7 adds codes and removes none (L5). **Sign-in during and after a store outage (A2, A6, N4).** A sign-in request is one on a route the route table marks `signin` (3): a static marker set in code at registration, platform-owned like the money mark, refused on a route with a parametrised target, never derived from path, verb or request content. The window opens when the `tenant` file is `waiting_store` or no report has been confirmed for 30 s, and is also open while either file is `key_missing` (4.8, A3). It closes only when a report is confirmed again **and** the `preauth` backlog has drained back within its R limit (5.1), so a sign-in record would be admitted again. Inside the window, a sign-in request that the `preauth` limits would refuse is served and its record is folded into the per-reason counters (`preauth_unrecorded`), written as per-minute aggregates (A6); within the limits, sign-in records are buffered one by one as usual; other unverified requests still get 429. So sign-in never gets 429 because the store is or was down; only a failed `preauth` file refuses it. Every 60 s, TX4 writes one aggregate of every reason's counts and the window. If that aggregate is refused, or the `preauth` file fails closed (its buffer is folded into the counters, 4.1), counting continues (`preauth_unrecorded` metric) and the counts go to the platform stream as a state event; the late file holds `tenant` rows only. Verified requests never call `preauth` admission. There are no `open_intents` and no tenant share.

## 5. Admission (R3-5)
### 5.1 Limits (P)
- **`tenant`:** `U = 65,536`; band `B = 0.01 U = 655` for `band` rows; `write_through` reserve `R_wt = 0.25 U = 16,384`; `security` reserve `R_s = 1,024` (8 MiB), used only by S; per-tenant shares `S_o = S_w = 0.20 U = 13,107`; write headroom `H_w = 4,096` that T never uses; platform slot `P = 16`; aggregate cap `A = 8`. **`preauth`:** `U_p = 8,192`; band 256; `R_s = 512`; `P = 16`; aggregate cap 64; no `write_through` rows. **Per file:** `ord` = `ordinary` units in `usage` plus `buffered` (unflushed records, all tenants, in memory); `wt` = `write_through` units; `sec` = `security` units; `band` = `band` units. **Per tenant t:** `ord[t]` (with `buffered[t]`) and `wt[t]`.

Since `ord ≤ 47,473` and `ord + wt ≤ 63,857`, ordinary records can never take the 16,384 units of `R_wt`; only S uses `R_s`; and `band ≤ B`, so the total stays within `U`: 63,857 + 1,024 + 655 = 65,536 (`preauth`: 7,424 + 512 + 256 = 8,192). The band holds 639 units for aggregates: at `A = 8` each, 79 tenants with full backlogs; beyond that, counters accumulate in memory. The last `P` units serve key rotation only. **Worked example (N1, the reviewer's two cases, GLB-T96):** with the store down, nothing is pruned. Tenant A reading at 2 per second has 13,107 read records after about 1.8 h; every later read is served and counted in A's aggregates, and A can still commit 6,553 admin or money writes (a finished write holds 2 units: TX1 +3, TX2 -1). Across the file, ordinary records stop at 47,473 units (at least four tenants at full share); every later ordinary request is served and counted, and `write_through` still has 16,384 units, 8,191 writes (two tenants or more), before W refuses. Reads on `write_through` routes (admin, parametrised) stop at `S_w - H_w`: after 9,011 such reads A still has 2,047 writes. With few ordinary records, `write_through` may use up to 63,857 units. **Security reserve (N5).** With the store down nothing is pruned, so a sustained flood at the per-file bucket uses `R_s` in 1,024 / 8 = 128 s (`preauth`: 512 / 8 = 64 s); later security refusals are refused, counted and paged. One source alone adds at most 4 a minute. With the store up, acknowledged rows free the reserve.

### 5.2 Algorithm
1. **Lock.** S first takes a token from both buckets of 3 and checks `sec + 1 ≤ R_s` on the mirror, under the buffer mutex only and before the writer lock; a request that fails goes to step 3 without entering the writer queue. W, T, X and an admitted S take the writer lock, run `BEGIN IMMEDIATE`, check the epoch, then take the buffer mutex for steps 2 to 4 up to (not across) `COMMIT`. An ordinary enqueue takes only the buffer mutex. Each path then reads the in-memory flags (`serving`, `failed_closed`, the 4.8 reasons, `writes_ready`, `waiting_store`, `last_confirmed`), the in-memory mirror of `usage`, `buffered` and the cached physical reading (5.3). Flags change only while both the writer lock and the buffer mutex are held. The mirror and `buffered` change only under the buffer mutex: a raise (TX1, TX3, TX11, TX12, enqueue) is applied with its check, before `COMMIT`, and undone under the mutex on `ROLLBACK`; a lowering (TX2, TX5, TX6) and TX9's move from `buffered` to `usage` are applied after `COMMIT` returns. So a reader may overstate usage but never understate it, and no path holds the buffer mutex during an fsync (5.4, L2).
2. **State checks.** Refuse W, T and new `write_through` requests if the file is not `serving` or `writes_ready` is cleared (X and S need only `serving`; S also needs a file that can append). Ordinary records are refused only with the instance not ready (local-volume failure, 4.8). **The 30 s rule is an alert, not an admission check (A4):** no confirmed report for 30 s raises `spool_unconfirmed` and pages after 300 s (P); it refuses nothing, at start or later. Then apply the path's floor (5.3).
3. **Limits.** Apply the path's 5.1 row (with `count(records_agg)` for G). On a W, T or X refusal: `ROLLBACK`, 503 `audit_unavailable`, no handler call. On an R refusal: serve the request and do not enqueue (`preauth`: 429, except sign-in). On an S refusal (before the lock, or under it with `ROLLBACK`): send the request's own refusal and page (3). In every case add 1 to the in-memory counter `(tenant, path, reason)`.
4. **Admit.** Otherwise insert and `COMMIT` (W, T, X, S; S then sends the refusal), or enqueue and add to `buffered` (R).
5. **Aggregates.** Every 60 s, for each tenant with a non-zero counter, TX4 writes one `aggregate` record: counts per path and reason, window start and end, at most 4,096 bytes. S counts go only into the platform aggregate (`tenant_id = ''`), never a tenant's (6.8). If it is refused, counting continues and the window grows.

A refused or counted request is not an admitted record. So `audit_drop_count`, which must stay 0, counts only admitted records lost outside a crash. A crash loses unwritten counts (residual, 9).

### 5.3 Physical guard (P)
Refreshed at most once per second under the writer lock. `H` = held open-row reservations. **Per file:** `size(db) + size(wal) + 8 KiB × H_file ≤ cap`, with a cap of 512 MiB for `tenant` and 64 MiB for `preauth`, and `H_preauth = 0`. The late file is bounded by 7.4. **Per volume:** `statvfs` free bytes ≥ `8 KiB × H + M`: `M_hi = 64 MiB` for W, T and R; `M_lo = 16 MiB` for G, K, X and S; no floor for O or TX10. The unit count stays the admission authority; this guard only catches a wrong overhead factor.

### 5.4 Writer lock and fsync queue (F8)
One tenant's reads never take the fsync queue per request: they join the shared TX9 batches (one fsync per batch), and the share `S_o` bounds them in units. (P) The writer lock is one FIFO queue for TX9 batches, TX1 to TX4, TX6, TX7, TX11, TX12 and PLT-032's TX5: **Batch hold.** TX9 holds the lock for one batch of at most 256 records, so a write-through commit waits at most one batch. **TX9 and the buffer mutex (L2).** Under the writer lock, TX9 takes the buffer mutex only to copy its batch, releases it before `BEGIN IMMEDIATE`, and takes it again after `COMMIT` returns to remove the batch from `buffered` and move its units to the `usage` mirror; on failure the batch stays where it was. Until then the batch stays in the buffer, so a crash still loses it (D4). **Per-tenant cap (accepted, A8).** A tenant may have at most 8 write-through requests in flight, counted from admission (TX1 for a write or a read treated as a write, request start for a TX3 read) until the outcome commits (TX2, TX3 or TX10). A ninth is refused at admission with 503 `audit_unavailable` for that tenant only, recorded by 5.2 step 5; an outcome is never refused, so the cap bounds that tenant's per-request fsyncs to 8 at a time. **Security refusals (N5).** TX12 adds at most 8 commits per second per file to this queue (the per-file bucket of 3), however many sources send them. **Reads off the lock.** PLT-032's batch reads and the read-only accessors use the read connection, never the writer lock.

## 6. Interface for PLT-032 (local side only; PLT-032 owns the protocol)
6.1 `stream_guard(stream)`: a mutex per stream. PLT-032 holds it across one store checkpoint read, `local_snapshot` and the 4.7 comparison. `apply_ack` and WAL truncation take it too (local half of R3-2).
6.2 `local_snapshot(stream)`, in one read transaction: `pruned_through`, `pruned_chain`, `prune_receipt_version`, `head_seq`, `head_chain`, and `chain_at(seq)` for `seq` in `(pruned_through, head_seq]`.
6.3 `apply_ack(stream, through_seq, wm_seq, receipt_version, receipts)` runs TX5. It is refused, with nothing written, unless: `through_seq ≤ wm_seq`; `receipt_version ≥ prune_receipt_version`; every `seq` in `(pruned_through, through_seq]` exists; every `write_through` row in that range has exactly one receipt (A1: receipts only where needed). Every other row needs a receipt only if it is `rejected` or in `conflict`; without one it counts as `committed`. Receipts at or below `pruned_through` are ignored, so a replay after a lost reply is a local no-op (R3-3 local half). `rejected` and `conflict` delete the row as `committed` does, increment `receipt_rejected_total` and page. What the store keeps is SEC-008's choice.
6.4 `read_batch(stream, after_seq, max_records = 500, max_bytes = 1 MiB)`: one short read transaction; rows in `seq` order.
6.5 `report_confirmed(stream, monotonic_time)` and `fail_closed(stream, reason)` are set under the writer lock and the buffer mutex. Confirmation is in memory only: after a restart nothing counts as confirmed until PLT-032 reports. It drives the 30 s alert (5.2) and the sign-in exception (4.6), never admission. `fail_closed` also writes the `<name>.failed` marker (1) before it returns; if the marker cannot be written, the instance stays not ready, retries every 5 s and pages, and a restart before it succeeds re-verifies the file under 4.4 step 4 (residual, 9). `stop_write_through(stream, reason)`, under the same locks, sets a 4.8 reason; PLT-032 calls it with `store_mismatch` when its 4.7 check before an acknowledgement fails, and it writes the `<name>.wt_stopped.store_mismatch` marker before it returns (on failure, as for `fail_closed`).
6.6 Read-only accessors: units per tenant and class, `buffered` per tenant, the 4.8 reasons, held reservations, `key_dependents(key_id)`, the oldest unforwarded `ts`, refusal counters, late rows.
6.7 The fake `AuditStore` implements `checkpoint(instance, stream)` and `list_open_intents(instance)`, filterable by `audit_class`; a delivered `reconcile` record closes its intent there (4.8). SEC-008 must do the same; that is a Q-614 conformance test (A10, Q-676). A direct late outcome exists only if Q-646 allows it.
6.8 **Stream routing (D3).** These go to SEC-008's platform security stream and never to a tenant's audit: every `preauth` row; every `security` row in either file and the security counts in platform aggregates, whatever their `tenant_id` (A11, Q-673); `tenant` rows with `tenant_id = ''`: `key_rotation` and platform aggregates; the state events `failed_closed`, `corrupt`, `waiting_store` and each 4.8 reason set or cleared, `key_missing` counts, rejected receipts, the missing intents of 4.4 step 7 and each `reconcile_missing` call, refused or not, with its operator (A10), and the fact (not the content) that a file has late rows. Only rows with a verified `tenant_id` whose class is not `security` go to the tenant audit, late rows included, flagged as late; the 7.4 drain routes by the same rule. Q-673 also sends `region_policy_refused`, PD refusals, provider key or auth failures and budget overrun alerts to this stream; apart from the security refusals of 3 they are model-gateway events (#355) that this spool does not record today (UNVERIFIED); recording one here needs this routing extended first. SEC-008 may change these shapes and this routing (D1, D3).

## 7. Failure semantics
### 7.1 Crash (SIGKILL) at each durability point
| Point | Crash before `COMMIT` returns | Crash after `COMMIT`, before the next step |
|---|---|---|
| DP0 | the kernel releases the lock; next start repeats | same |
| DP1 | no intent, no open row; handler not called; dropped connection | open row survives; recovery closes it `unknown_after_restart` (GLB-T01) |
| DP2 | open row survives; recovery closes it (GLB-T02) | outcome unforwarded; step 7 finds it (R3-1) |
| DP3 | no record; dropped connection; no effect | record kept; the response may be lost |
| DP4 | counts lost (residual) | record kept |
| DP5 | nothing pruned; the store returns the original receipts | pruned; open rows untouched (GLB-T30) |
| DP6 | that row stays open; the next start closes it, never twice (GLB-T31) | closed; recovery moves to the next row |
| DP7 | the old key stays active on that file | new key active; old key `verify_only` |
| DP9 | the batch and the rest of the buffer are lost (D4; at most 1,024 records) | batch kept; the rest of the buffer is lost |
| DP10 | the late outcome is lost; the open row survives and the drain reports it as unknown | late row kept; the drain forwards it |
| DP11 | no `reconcile` record; the id stays on the missing list | record kept; the next step 7 counts it |
| DP12 | no record and no refusal sent yet; the client sees a dropped connection; no effect | record kept; the refusal may be lost |

### 7.2 Disk full (`SQLITE_FULL`, or the 5.3 guard)
TX1 and TX3: `ROLLBACK`, 503, handler not called. TX2: real result returned, outcome retried, row and reservation kept. TX9: the batch stays buffered and, once the buffer is full, new ordinary records are counted (5.1 R); nothing buffered is dropped. TX12: `ROLLBACK`; the refusal is still sent, counted and paged (3). TX5 frees space. TX6 at start: stop at the failing row, `failed_closed`. Graceful shutdown flushes the buffer and retries queued TX2s for at most 30 s (P), then leaves the rest to TX10 or recovery. INF-001 sizes the volume so that `(U + U_p) × 8 KiB + 64 MiB` fits.

### 7.3 Corrupt file
A file is `corrupt` when SQLite reports `SQLITE_CORRUPT` or `SQLITE_NOTADB`, or when `quick_check` is not `ok`. It is then not ready, and a page goes out. It is never repaired, rebuilt or deleted in place; it is preserved for forensic reading, the deprovisioning probe and the key probe (4.5). (P) The instance is replaced with a **new `instance_id`** and a fresh spool, so no `seq` stream ever restarts (Q-633).

### 7.4 Leaving `failed_closed` (F5)
A file becomes `failed_closed` on any of these: a `<name>.failed` marker at start; a failed chain, binding, key-sequence or `row_mac` check under the keys that load (4.4 step 4, N7); a missing open row; an I/O error on `COMMIT`; a non-empty late file at start. A 4.7 mismatch, a missing intent or a key that cannot load is not a trigger: it stops `write_through` only (4.8, A3). The state is terminal for the file's instance. The instance reports not ready, still returns real results for requests already past their handler (4.2), and is replaced with a new `instance_id` (as in 7.3). (P) The exit has four steps:
1. **Preserve.** The file and `spool-late.db` stay read-only on the volume, which stays in the INF-001 inventory.
2. **Drain.** An audited, forwarder-only process takes the `flock` and appends nothing. It verifies the chain from the anchor; delivers `records` up to the last verifiable `seq`; delivers the late rows whose `row_mac` verifies; reports each open row with no late outcome as unknown (`unknown_after_failed_closed`; Q-633 decides how the store marks it); hands unverifiable rows to SEC-008 as flagged evidence, or keeps them for forensics. The same drain runs for the files of an instance replaced after `store_mismatch` or a lost key (4.8). After a 4.7 mismatch, "verifiable" ends at the store's watermark: every row above it, including rows appended during an outage, goes to SEC-008 only as flagged evidence.
3. **Destroy.** After the drain and any forensic hold, destroy the files under the deprovisioning or forensic approvals; the deprovisioning probe (ADR-0069 5.5) must then find none of them.
4. **Release keys.** The files count in `deps(k)` until they are destroyed; their key versions then retire through the 4.5 probe. The late file holds at most 1,024 + 256 rows per failure: the whole buffer plus one outcome per in-flight request (256 per instance, ADR-0069 4).

## 9. Open items, residuals and review findings
- **R3-1 (closed, subject to Q-630).** Closed by 4.4 steps 6 and 7 (GLB-T57, T31, T46). It needs `list_open_intents` to be complete at one checkpoint version and filterable by `audit_class`.
- **R3-4 (closed).** A key is kept while `deps > 0` and retired only after an active probe (4.5; GLB-T59 to T61, T75, T84).
- **R3-5 (closed).** Shares per class apply to W, T, R and the buffer, and ordinary records over a limit are counted (2.2); aggregates are capped inside a band; held reservations count in every limit (5; GLB-T54 to T56, T45, T73).
- **R3-2 and R3-3 (local half here).** 6.1 serialises snapshot and acknowledgement, and 6.3 makes a replay a no-op. The protocol itself is PLT-032's and SEC-008's.
- **M6 (P): a stated exception with conditions, pending Eldon (Q-629).** The per-tenant envelope rule ([data.md](../architecture/data.md) item 3; data-retention section 8) exists so that destroying one tenant's keys erases every copy. The spool is excepted because: (a) its volume key is per instance volume, wrapped by the regional `S10a`, never shared, and destroyed after a drain to zero; (b) the volume is never backed up, snapshotted or restored; (c) records hold only identifiers and keyed digests; (d) rows live only until they are forwarded, and `secure_delete=ON` plus the checked WAL truncation run before the deprovisioning probe certifies (GLB-T68). Residual: freed blocks may still hold old frames, readable only with the volume key. Rejected: per-tenant data keys for `body`, which would put a KMS unwrap in the request path.
- **Residuals.** A crash loses up to 1,024 buffered ordinary records (D4). Until the store acknowledges them, unforwarded rows can be removed undetected by someone with volume write access. That includes `write_through` records; this residual is accepted (A1), and with the 30 s rule an alert (A4) the window is bounded by capacity, not by 30 s. Ordinary records over a limit exist only as counts; during an outage a tenant reaches its 8 unforwarded aggregates after about 8 minutes of refusals, and later counts live only in memory and are lost on a crash. Reads on `write_through` routes get 503 past `S_w - H_w` per tenant during a long outage (5.1). Under `key_missing` nothing is appended, so ordinary records are counts in memory only; under `store_mismatch` the instance serves ordinary routes and forwards nothing until it is replaced (4.8). A rollback or a deleted file during a store outage is detected late, when step 5 runs, not at start; rows appended in between reach SEC-008 only as flagged evidence (7.4). During an outage, sign-in records over the `preauth` limit are counted, not recorded one by one (4.6). Open-row replay (F9): someone with volume write access and an old copy of the file can restore a closed open row whose MAC is still valid. Recovery then appends a second `unknown_after_restart` outcome. Only the store detects it, as a `conflict` on that `audit_id`, which pages. A late outcome is lost if TX10 fails and the process then exits; its intent survives. Refusal counts are lost on a crash. If the `<name>.failed` marker cannot be written and the process restarts first, the file is re-verified instead of staying failed (6.5). The same holds for a `wt_stopped` marker (N8): if the `store_mismatch` marker cannot be written and the instance restarts with the store down, `write_through` is served again until the deferred step 5 sets the reason. Security refusals (N5): during a store outage a sustained flood uses `R_s` in about 128 s (`preauth` 64 s), after which they are refused and counted only, and those counts are lost on a crash; with more than 4,096 rotating sources per-source fairness is lost, while the per-file bucket still bounds fsyncs. Under `store_mismatch` security rows are never forwarded, so `R_s` fills and stays full until the instance is replaced; later security refusals are counted and paged. Missing key (N7): rows under a key that cannot load cannot be checked locally. Someone with volume write access can still edit such rows, keeping column and body consistent, or relabel the oldest key segment (from the anchor to the first retained `key_rotation` record; with none retained, the whole file) to a version that does not load, and so turn a tamper there into `key_missing`. Nothing is then appended, the instance alarms, and the 7.4 drain hands those rows to SEC-008 only as unverifiable, flagged evidence.
