Status: draft
Owner: unassigned

Purpose: the product app. One chat plus role-based views, approval inbox, Settings > Branding, login page, tenant-branded documents. Screens: [docs/product/app-screens.md](../../docs/product/app-screens.md). Tokens: [docs/brand/tokens](../../docs/brand/tokens/tokens.json). Theming: [theming](../../docs/architecture/theming.md). ## Theme engine (BRD-005)
`theme/theme-engine.js` is the user theme preference (light, dark, system) with per-user persistence; see [theming](../../docs/architecture/theming.md). Run its tests with `node --test web/app/theme/` (Node 20, no packages).

## UI components (BRD-010)
`src/ui/` is the component library: Button, TextField, Select, Checkbox, DatePicker, Card, Badge, Alert, Spinner, Table, VisuallyHidden, Stack (import from `src/ui`). CSS Modules built only from brand tokens, logical properties only, no text inside components (every visible or aria string is a prop, so copy goes through i18n). DatePicker (WEB-016) keeps the value as a Gregorian ISO date, shows and grids it in Gregorian or Hijri (Umm al-Qura through `Intl`, no dependency), accepts typed Gregorian or Hijri with Latin or Arabic-Indic digits, and reports day/month-ambiguous input through `onAmbiguous` instead of guessing; week start is a prop; keyboard: arrows, Home, End, PageUp, PageDown, Enter, Escape. Date logic is in `src/ui/dateLogic.ts`. It will move to its own package later. See every variant on the preview page, Components section.

## Auth and error pages (WEB-017, UI only)
`/login/`, `/reset-password/`, `/reset-password/confirm/`, `not-found.tsx`, `error.tsx` and `global-error.tsx`, built from `src/ui` and tokens, copy under the `auth` and `errors` message namespaces. The forms do no real authentication: they call typed placeholder handlers in `src/lib/authPlaceholder.ts` (fixed results, no network, no credential stored or logged) until PLT-005 (identity service). Failure wording never says whether an account exists. The reset-confirm page does not read a token yet; that arrives with PLT-005.
The Arabic strings for these pages are unreviewed (ADR-0033) and need a native-speaker review before use with customers.
Still open under WEB-017 / ERP-016: own emails (reset and notifications) and print formats; no engine template may reach a customer (ADR-0016).

## RTL checks (QA-008)
Deterministic layout checks, no screenshot baselines:
- `web/scripts/check-rtl-css.mjs` (part of `pnpm lint`, also `pnpm check:rtl`) fails on physical-direction CSS in `app/src` and `marketing/src`: `margin|padding|border-left|right`, `left|right`, `float`, `text-align: left|right`, physical radii, `translateX`, `scaleX`. Use logical properties. If a physical value is truly right (symmetric or always-LTR content), add `/* rtl-ok: reason */` on the same line or the line above; the reason is required.
- `src/ui/rtl.test.tsx` renders the components and the auth forms in `dir="rtl"` and `dir="ltr"` and asserts the root `dir`, no inline `left`/`right`, LTR numeric inputs, logical end alignment for numeric table columns, and that theme modes (per tenant) never change `dir`. The components have no icon mirroring hook yet, so none is tested; add one with the first directional icon.
- Real browser screenshot diffs are NOT done: baselines are images and cannot be committed (AGENTS.md). Open question Q-143 asks where to store them. Tenant-branded documents (print formats) are not covered until ERP-016 produces them.

## Record screens (WEB-023, UI only, fixture data)
`src/records/` is a pure TypeScript layer: `buildListModel` (columns, filters, search, sort, pagination, linked-record cells), `buildFormModel` (types, required, read-only, hidden per `field_access` for the caller's roles) and `buildActions` (create, edit, amend, submit, cancel, transitions). Inputs are data: a Blueprint entity, the generated Tool API definitions and a `Caller` passed in by the shell; nothing reads the browser. Deny by default: a missing tool or role yields no screen, no field, no action. With several roles, hidden or read-only for any role wins. Risk gating: R0/R1 act directly, R2 asks for confirmation with a summary of the changes, R3, R4 and `agent_creatable=false` show as "Needs approval" and are never executed. `amend` appears only if an `<entity>.amend` tool exists (none today).
Components in `src/components/records/` (RecordList, RecordForm, ConfirmWrite, StatusBadge); pages `/records/<entity>/`, `/records/<entity>/new/` and `/records/<entity>/<id>/`, statically generated from the fixture in `src/records/fixture/` (a trimmed copy of the example Blueprint and its generated tools, synthetic rows, placeholder caller). All writes go through `submitAction`, a placeholder with a fixed result that never stores or logs values; it waits for the gateway (PLT-009). Not built yet: lines (child tables), saved views, bulk select, import, export, print, history and attachments. The Arabic strings under `records` are unreviewed (ADR-0033).

## App shell (WEB-003, UI only, placeholder session)
The authenticated area is the route group `src/app/(app)/` (no URL segment): `/home/` and the `/records/...` routes render inside `components/shell/AppShell`. Top bar: workspace switcher (a person can belong to several tenants, one token per tenant, ADR-0007; suspended memberships are listed but disabled; a refused switch keeps the current workspace and shows an alert), user menu (language, theme, MFA badge, sign-out), skip link, one `<main id="main">` (pages inside render no `<main>`), and a side navigation that becomes a drawer under 48rem (Escape closes it and returns focus). Navigation comes from `src/lib/navigation.ts`: an entity appears only if its `list` tool exists and one of the caller's roles may call it (`records/access.ts`, deny by default). States: loading, signed out, error (shell error boundary plus retry), no active workspace, and nothing to open.
`src/lib/session.ts` types the session after identity's claims (tenant id, roles, `mfaSatisfied`, `sessionVersion`) and holds a synthetic fixture and placeholder handlers (`placeholderSwitchWorkspace`, `placeholderSignOut`). `components/shell/SessionProvider.tsx` is the one place for the real auth wiring: it keeps the session in memory only, with no secret, no real call and no cookie (only the existing theme and language preferences are stored). Sign-out ends the in-memory session and goes to `/login/`; the login form is still the WEB-017 placeholder. Copy is under the `shell` message namespace; the Arabic is unreviewed (ADR-0033). Not built: real tenant token exchange, per-tenant branding in the shell (WEB-008), role-based views beyond the record lists (WEB-011), notifications.
Components in `src/components/records/` (RecordList, RecordForm, ConfirmWrite, StatusBadge); pages `/records/<entity>/`, `/records/<entity>/new/` and `/records/<entity>/<id>/`, statically generated from the fixture in `src/records/fixture/` (a trimmed copy of the example Blueprint and its generated tools, synthetic rows, placeholder caller). All writes go through `submitAction`, a placeholder with a fixed result that never stores or logs values; it waits for the gateway (PLT-009). Not built yet: lines (child tables), saved views, bulk select, print, history and attachments. The Arabic strings under `records` are unreviewed (ADR-0033).

## Bulk import and export (WEB-024, UI only, fixture data)
Pages `/records/<entity>/import/` and `/records/<entity>/export/`, linked from the list. Pure models in `src/records/`: `csv.ts` (in-repo reader and writer, delimiter detection, formula-safe cells), `importModel.ts` (`buildImportPlan`, `autoMap`, `checkMapping`, `validateRows`, `errorReportCsv`) and `exportModel.ts` (`buildExportModel`). Importable fields follow the create tool's `field_access` for the caller (hidden, read-only, computed and attachment fields never import; a required field the caller cannot fill blocks the import). Each cell is checked by field type (number, precision, date, option, link to a known record, phone, email, length, required); Arabic digits are accepted. Steps in `ImportWizard`: upload, map, preview (problem rows first), confirm. Nothing is written before the confirm step; the write is one bulk `create`, raised to R2 at least, shown with a change summary in `ConfirmWrite`, and sent through the `submitAction` placeholder (`SubmitRequest.rows`, waits for PLT-009, never executed). The error report is a CSV built in the browser. Export lists only fields the caller may see, using the list tool as permission. CSV only: Excel needs a server-side parser (DSC-011 connector) and is open question Q-179 (numbered to be confirmed at merge); the screens say so.

## Blueprint viewer (DSC-007, read-only, fixture data)
Route `/blueprint/` inside the `(app)` shell; nav item added in `SideNav` for any caller with a role the Blueprint defines. `src/blueprint/` is a pure layer: `buildBlueprintView(blueprint, caller, locale, pendingDiffOps)` returns sections (company profile, locations and departments, roles and who can do what, document flows, items and parties, numbering, tax and calendar settings, assistants (schema 0.4.0), pending changes) holding `blueprint.*` message keys and data, never English sentences, no engine or component names. `access.ts` is deny by default: owner and general manager see all, every other known role sees its own department (its roles, the records it may touch with hidden fields removed, its assistants); unknown roles see nothing. `flows.ts` lays out each workflow in columns; `components/blueprint/FlowDiagram` draws it as token-themed SVG (no dependency, mirrored in right-to-left, numbered edges with a numbered text list as the accessible equivalent). `pending.ts` folds the diff's impact classes into cosmetic, process, access and money (Q-226). Draft and UNVERIFIED badges (Q-228). Fixture: `src/blueprint/fixture/` (trimmed example Blueprint plus invented pending changes) until PLT-009. Arabic strings under `blueprint` are unreviewed (ADR-0033). Not built: editing, approval (DSC-009), version history and compare, rollback, branding and reports sections.

## Chat screen (WEB-004, UI only, scripted fake backend)
Route `/chat/` in the `(app)` shell (nav item "Chat"). `src/chat/` is the pure layer: `types.ts` (modes discover, ask, act, change; allow-listed events; `ChatPort` with send, cancel, respond, subscribe), `events.ts` (`parseChatEvent` drops unknown types and extra fields), `reducer.ts`, `text.ts` (strips bidi overrides and invisible characters; Enter sends, Shift+Enter is a newline, IME composition never sends), `suggestions.ts` (prompts per role, generic fallback), `useChat.ts`, and `fake.ts` plus `fixture.ts` (scripted `ChatPort` used by tests and by the page until the real AG-UI client, WEB-026, replaces it; `@ag-ui/client` is not a dependency yet). Components in `src/components/chat/`. Rules: model text is a React text child in an isolated `dir="auto"` bubble (no markdown, no HTML, no links); the mode never grants access and the label says so; act and change need a confirm card that never confirms itself; a pending approval shows "sent for approval" and links to the approval inbox (no approve action in chat, ADR-0044); the activity list shows tool name, risk class and outcome only; errors use `chat.errors.<code>` keys with an unknown fallback. Arabic strings under `chat` are unreviewed (ADR-0033). See Q-255.

## Login with tenant branding (WEB-008, UI only, fake port)
`/login/` renders `components/login/BrandedLogin`: the WEB-017 form plus a brand block (tenant logo and display name, or the platform mark and name when there is none). The tenant comes from the hostname only (`src/components/login/host.ts`, ADR-0007; no session exists before sign-in; the query string and hash are ignored) and is resolved through the typed `TenantBrandingPort`; the only implementation is `fake.ts` (synthetic tenants in `fixture.json`, values produced by `docs/brand/tools/derive_tenant_theme.py`) until the tenant token endpoint exists. Locally, `sample-trading.localhost` and `example-foods.localhost` map to those synthetic tenants; any other host shows the platform look. For a dev look at a fixture tenant, `/login/preview/?tenant=sample-trading` (or `example-foods`) works only when `NEXT_PUBLIC_LOGIN_PREVIEW=1` is set at build time (off by default; never the production login). `branding.ts` treats the branding as untrusted: slug, token names (only the six primary-derived tokens), values and logo URL (https or same-origin path) are checked, half a theme falls back to the platform look, and the CSS is scoped to `[data-tenant]` for light, system dark and explicit dark. Authentication is still the WEB-017 placeholder (no credential handled). Arabic strings unreviewed (ADR-0033). Logos: a same-origin path must be one plain file under `/icons/` or `/brand-assets/` (no query, fragment, `..` or encoded characters); an https logo must come from an origin listed in `NEXT_PUBLIC_ASSET_ORIGIN` (none by default; no userinfo, port or IP literal). Token values must be hex colours (one translucent shape for `--state-selected`) and the label must reach 4.5:1 on the primary, hover and pressed colours in both themes, else the platform look shows. A brand needs a display name.
Follow-ups before a real adapter (review of #275): host resolution is in place (synthetic map only); the gateway must resolve the real subdomain (tenancy-and-identity.md) and rate-limit tenant lookups, since a host probe still reveals which tenants exist; the inline `<style>` needs `'unsafe-inline'` or a nonce under a strict CSP, so move to the planned `/tenant/tokens.css` (open point Q-97).
Not built: login background asset, favicon, per-tenant branding in the shell.
